## Problem Statement

Without an autonomous code producer between an APPROVED plan and the Test Runner, the relay pipeline halts at plan-APPROVED — the autonomous portion that was supposed to run untouched is broken at its third step. Asking an LLM to implement inline at run-time produces unreliable, untraceable, ungoverned changes that drift from the plan's atomic-task contract; tests get silently weakened with no rubric guard; oscillation goes undetected; no per-attempt diff audit exists. Until this stage exists, `/relay-execute` cannot run end-to-end, the Test Runner has no working tree to operate on, and the relay value proposition (one prompt → PR) stays hypothetical.

## Evidence

- The relay command surface decision in `docs/decisions.md` (2026-04-19) explicitly lists `/relay-implement <plan-path>` and `/relay-code-review <worktree>` as separate, mandatory commands of the canonical 12-command surface; both are still unimplemented.
- `docs/api-reference.md:41` lists `/relay-implement` as a planned writer (input: approved plan; output: implementation committed to worktree).
- `docs/api-reference.md:49` lists `/relay-code-review` as a planned reviewer (input: worktree diff; output: APPROVED or CHANGES_REQUESTED).
- `PRPs/prds/plan-authoring.prd.md` (shipped 2026-04-25) is the closest sibling and the structural precedent — same writer/reviewer split, same Decision Gate emission, same auto-flip-on-rubric-pass pattern past the interactivity boundary.
- `PRPs/prds/test-runner.prd.md` defines the per-attempt artifact layout under `PRPs/reports/<feature>/attempts/<N>/`; this PRD extends that layout with `phase-<N>/attempts/<i>/diff.patch` for symmetric implementer audit artifacts.
- LLM code-hallucination evidence: arXiv 2409.20550 (UTSA / VT / OU multi-LLM study) reports 43.53% task-requirement conflicts, 31.91% factual-knowledge conflicts, and Pass@1 between 0.04% and 10.40% on raw generation — directly motivating the structured retry budget (`max_implement_retries = 3`) and the structural rubric.
- Scaffolding-hallucination evidence: arXiv 2604.20202 (Hallucination Inspector) defines phantom imports / constructors / constants as a high-frequency failure mode; AST cross-referencing achieves 100% precision — supporting the static layer of D4.
- Logic-error-as-the-real-danger evidence: Simon Willison (2025-03) — *"errors that pass compilation but produce incorrect logic happen all the time and require manual testing and code review skills to catch"*. Direct motivation for D4's semantic layer, the third and primary value layer.
- Oscillation evidence: agentwiki.org common agent failure modes catalogs the two canonical patterns (same-action-repeat, two-state-alternation) and the production case of a Claude Code sub-agent executing `npm install` 300+ times consuming 27M tokens — directly supporting D7's always-on oscillation detection.
- Hard-ceiling precedent: SWE-agent (NeurIPS 2024, arXiv 2405.15793) caps LLM calls at 100 per instance; OpenHands CodeAct 2.1 sets 100 iterations per instance — precedent for the dual cap (`max_implement_retries` + `max_implement_minutes`).

## Proposed Solution

Build two new agents and two new commands that mirror the writer/reviewer split pattern proven by the PRD pair (interactive) and the Plan pair (autonomous, auto-flip), adapted for the implementation stage. The `implementer` agent (color: green) consumes one APPROVED plan per invocation, executes the plan's Step-by-Step Tasks in order via `Edit`/`Write` directly in the working tree (D2), runs the plan's Validation Commands Levels 1–3 after all tasks complete (D6), and either returns code or — when the plan's existing tests appear to contradict the PRD — emits a `TEST_CONTRACT_DISPUTE` verdict with structured evidence (D9 Layer 1). The `code-reviewer` agent (color: magenta) is read-only over the repo, runs a three-layer rubric (structural / static / semantic per D4) with a universal `R-X` rule that blocks any diff modifying test files unless an upheld dispute exists (D9 Layer 0), and operates in two modes — standard for code review, arbitration for dispute resolution — with arbitration verdicts `{DISPUTE_REJECTED, DISPUTE_UPHELD_TEST_WRONG, DISPUTE_UPHELD_PRD_AMBIGUOUS}`. The `/relay-implement` command runs the internal writer↔reviewer loop (`max_implement_retries = 3` / `max_implement_minutes = 45` / `max_disputes_per_session = 2` per D7), captures `git diff <base-commit>` to `PRPs/reports/<feature>/phase-<N>/attempts/<i>/diff.patch` after each attempt (D2), detects oscillation always-on (D7), and on APPROVED rubric performs all three post-approval mutations (D8): plan trailing block flip to `*Implemented: <date>*\n*Status: IMPLEMENTED*`, plan move to `PRPs/plans/completed/`, source PRD row N flip from `in-progress` to `complete`. The `/relay-code-review` command is the standalone reviewer surface — D5 keeps both commands single-role; multi-plan orchestration is `/relay-execute`'s job. The reviewer auto-flips on rubric pass (interactivity boundary; D1) and writes one JSON line per verdict to `PRPs/plans/<basename>.code-review.jsonl` (D10).

## Key Hypothesis

We believe a writer/reviewer pair that mirrors the proven plan-stage pattern, anchored on the upstream `prp-implement` section reference but adapted for relay's autonomous-pipeline constraints — tests-as-rebuttable-contract escape valve, three-layer (structural / static / semantic) rubric, oscillation detection always on, dual budget caps (retry + wall-clock), per-attempt diff capture — will produce APPROVED implementations for ≥70% of APPROVED MVP plans on the first writer→reviewer round, and reduce Test Runner failures attributable to implementation defects below 25% of total Test Runner runs once telemetry is available. We'll know we're right when (a) the first three real plans run through `/relay-implement` reach APPROVED in ≤2 retries, (b) the Test Runner's GREEN rate post-`/relay-implement`-APPROVED is ≥80%, (c) `/relay-execute` can be wired without a per-stage workaround for missing code, and (d) zero R-X test-modification incidents reach the Test Runner once the rubric is live.

## What We're NOT Building

- **A bundled command (writer + reviewer in one).** The internal loop inside `/relay-implement` is NOT bundling — it has the same shape as `/relay-test`'s per-attempt loop. The writer/reviewer split decision (2026-04-19) still applies.
- **`/relay-worktree` dependency.** Separate future command. Per D3, `/relay-implement` works in cwd against the current branch when no worktree exists.
- **TDD Writer / TDD Reviewer (B7 / B8).** Deferred opt-in. The MVP surfaces a deferred-B7/B8 message on `DISPUTE_UPHELD_TEST_WRONG` arbitration verdict; bounce-back implementation comes when B7/B8 ship.
- **A `--dry-run` flag** (could-item; manual-debugging convenience).
- **A `--from-attempt <N>` resume flag** (could-item; recovery convenience).
- **Cross-plan / multi-phase orchestration.** Orchestrator's job (`/relay-execute`).
- **Browser / Database / Manual validation Levels 4–6 baked into the agent contract.** Per-project plan content if applicable; not part of the fixed agent contract.
- **Reopening an IMPLEMENTED plan via tooling.** Manual hand-edit (status flip back to APPROVED + move from `completed/`) is the documented escape hatch.
- **Re-grounding via research subagents.** Plan-writer's grounding is the source of truth; implementer has no `Task` tool (D11).
- **Persisting research blobs.** Could-item; mirrors plan-authoring's deferral. Implementer doesn't even invoke research per D11.

Baseline (before `/relay-implement` + `/relay-code-review`): all implementations hand-written or driven via `/prp-implement` and re-shaped manually to fit relay paths; no rubric guard against silent test weakening; no oscillation detection; no per-attempt diff audit; downstream Test Runner has no upstream code producer in the autonomous pipeline.

## Acceptance Criteria (test scenarios)

Mandatory. Each criterion is an observable scenario the feature must satisfy. `docs/context/methodology.md` declares `tdd: false`; these criteria seed the tests the Implementer (this very feature, dogfooded) writes alongside the agent and command code.

- **AC-1 Happy-path APPROVAL with full mutations:** Given an APPROVED plan `PRPs/plans/<basename>.plan.md` with all Step-by-Step Tasks complete and all VALIDATE commands passing on the first attempt, when `/relay-implement <plan-path>` runs, then (a) the working tree carries the implementation diff against the base commit, (b) `PRPs/reports/<feature>/phase-<N>/attempts/1/diff.patch` exists and contains the full diff, (c) the plan trailing block flips from `*Status: APPROVED*` to `*Implemented: <YYYY-MM-DD>*\n*Status: IMPLEMENTED*`, (d) the plan file moves to `PRPs/plans/completed/<basename>.plan.md`, (e) the source PRD's Implementation Phases row N `Status` cell flips from `in-progress` to `complete`, (f) one APPROVED entry with all rubric items passing is appended to `PRPs/plans/<basename>.code-review.jsonl`, and (g) the command exits with the success summary.

- **AC-2 Internal loop on first-attempt VALIDATE failures:** Given Step-by-Step Tasks that fail one or more Validation Commands on the first attempt, when `/relay-implement` runs, then the internal writer↔reviewer loop emits CHANGES_REQUESTED with the failing rubric items as feedback, re-invokes the implementer with the feedback, and retries up to `max_implement_retries = 3` (4 attempts total). On any attempt's APPROVED rubric, normal completion (AC-1 mutations). On retry exhaustion, the command HALTs with outcome `FAILED_AFTER_N_RETRIES` and the full attempt history (every attempt's `diff.patch` + `code-review.jsonl` entry) is preserved on disk.

- **AC-3 TEST_CONTRACT_DISPUTE arbitration:** Given the implementer emits a `TEST_CONTRACT_DISPUTE` verdict (instead of code) carrying structured evidence `{ disputed_tests, prd_refs, claim, proposed_resolution }`, when the code-reviewer arbitrates, then (a) the dispute consumes one attempt of the budget (counted toward `max_implement_retries`), (b) the reviewer enters arbitration mode and emits one of `{DISPUTE_REJECTED, DISPUTE_UPHELD_TEST_WRONG, DISPUTE_UPHELD_PRD_AMBIGUOUS}`, (c) the verdict is appended to `code-review.jsonl` with `mode: "arbitration"` and the full `dispute_evidence` block, and (d) the next loop step matches the verdict — `DISPUTE_REJECTED` triggers a mandatory-code next attempt; `DISPUTE_UPHELD_TEST_WRONG` surfaces a deferred-B7/B8 message and HALTs the session structurally; `DISPUTE_UPHELD_PRD_AMBIGUOUS` HALTs structurally for human PRD update.

- **AC-4 R-X universal test-modification rule:** Given any code-reviewer run, when the implementer's diff modifies one or more files matching the project's test glob (detected from the plan's Files-to-Change rows or from the validation command targets) and the implementer did NOT emit a `TEST_CONTRACT_DISPUTE` verdict, then rubric R-X fails with a structured reason listing every modified test file path. R-X fires regardless of whether `docs/context/methodology.md` has `tdd: true` or `tdd: false` (universal rule per D9 Layer 0).

- **AC-5 max_disputes_per_session cap:** Given more than `max_disputes_per_session = 2` `TEST_CONTRACT_DISPUTE` attempts in a single `/relay-implement` session, when the third dispute is attempted, then the loop refuses the dispute with a HALT carrying outcome `FAILED_DISPUTE_CAP_EXCEEDED` and surfaces the cap as actionable feedback in the structured halt message. Disputes are counted from `code-review.jsonl` entries where `mode: "arbitration"`.

- **AC-6 Worktree graceful degradation:** Given `/relay-implement` is invoked while the cwd is not inside a git worktree set up by `/relay-worktree` (or no worktree path exists at the conventional location), when the command runs, then it works in cwd against the current branch (D3 graceful degradation), still computes `<base-commit>` as `git merge-base HEAD <base-branch>`, and still writes `diff.patch` artifacts to `PRPs/reports/<feature>/phase-<N>/attempts/<i>/`. `<feature>` is the plan's basename minus `-phase-<N>-<slug>.plan.md`; `<N>` is parsed from the same filename pattern (mirrors plan-reviewer R8c).

- **AC-7 Time budget exhaustion:** Given `max_implement_minutes = 45` elapses before `max_implement_retries` are exhausted, when `/relay-implement` aborts, then the outcome is `FAILED_TIME_BUDGET_EXCEEDED` (distinct from `FAILED_AFTER_N_RETRIES`). The command writes the partial attempt history to disk before HALTing and the structured HALT message names the elapsed wall-clock + remaining retries.

- **AC-8 Oscillation detection:** Given the implementer's diff in attempt N reverts files altered in attempt N-1 (set intersection of files modified between the two attempts' `diff.patch` files, with reversion = same file modified to a state byte-equal to attempt N-2 or earlier), when `/relay-implement` detects this, then the command aborts with outcome `FAILED_OSCILLATION_DETECTED` *before* exhausting `max_implement_retries`. The structured HALT names the oscillating files.

- **AC-9 No `.claude/` writes:** Given any invocation of `/relay-implement` or `/relay-code-review`, when any artifact is written (`diff.patch`, `code-review.jsonl`, plan move, PRD edit, halt-state files), then no resolved write path contains `/.claude/` or starts with `.claude/`. This invariant is checked by both the command and the agents (universal anti-pattern from `docs/anti-patterns.md` lines 60–66).

- **AC-10 Code-reviewer rubric: all items recorded, no short-circuit:** Given the code-reviewer runs in either mode (standard or arbitration), when it appends a verdict line to `code-review.jsonl`, then the line's `rubric` array contains exactly one entry per rubric item the reviewer evaluated (one of each, no duplicates, no extras), each with a boolean `passed` field. CHANGES_REQUESTED entries include a non-empty `reason` on every failed item. APPROVED entries set every `passed: true`. Standard-mode rubric items: R-S1 (every Step-by-Step Task addressed), R-S2 (every Files-to-Change row touched), R-S3 (every plan AC-A satisfied), R-L1 (Level-1 STATIC_ANALYSIS / lint passes), R-L2 (Level-2 type-check / unit-test passes), R-L3 (Level-3 INTEGRATION / markdown-lint passes), R-SEM (semantic review: business-rule consistency, bugs, security gaps), R-X (no test files modified without an upheld dispute). Arbitration-mode entry instead carries a single `arbitration` rubric item with `verdict ∈ {DISPUTE_REJECTED, DISPUTE_UPHELD_TEST_WRONG, DISPUTE_UPHELD_PRD_AMBIGUOUS}` plus the full `dispute_evidence` block. Symmetric with plan-reviewer AC-10.

- **AC-11 Source-PRD precondition:** Given a plan whose source PRD's Implementation Phases row N `Status` cell is NOT `in-progress` when `/relay-implement` starts (e.g., the cell is still `pending` indicating the plan-writer's back-fill never ran; or already `complete` indicating prior implementation), when the command runs precondition checks, then it HALTs with a precondition error explaining the state mismatch (cite the cell value, the expected value, the file path, and the row number) and writes nothing. The user is directed to either re-run `/relay-plan` or hand-edit the cell.

- **AC-12 Standalone /relay-code-review surface:** Given a working tree with a code diff against the base branch and a plan file `<basename>.plan.md` (path passed as argument), when `/relay-code-review <plan-path>` runs, then it invokes the code-reviewer agent in standard mode with no internal loop, appends one verdict to `PRPs/plans/<basename>.code-review.jsonl`, and surfaces APPROVED or CHANGES_REQUESTED to the caller. The command does NOT perform the post-approval mutations (D8) — those are `/relay-implement`'s exclusive responsibility.

- **AC-13 Auto-flip on rubric pass without user dialogue:** Given the code-reviewer's standard-mode rubric (R-S*, R-L*, R-SEM, R-X) all pass on the final attempt of `/relay-implement`, when the writer↔reviewer loop concludes, then the reviewer auto-emits APPROVED, the command performs D8 mutations, and the only user-facing surface is the success summary — no "Aprovar?" prompt, no confirmation gate (interactivity boundary; D1).

- **AC-14 Decision Gate halt on missing source:** Given any of `docs/decisions.md`, `docs/anti-patterns.md`, or `docs/context/architecture.md` cannot be read at the implementer's Phase 0 setup or the code-reviewer's Phase 0 setup, when the command runs, then it HALTs with the byte-exact message `"I cannot emit the Decision Gate evidence block without reading <missing-file>. Please ensure the file exists at <target_root>/<relative-path> and re-run /relay-implement (or /relay-code-review). No code has been changed and no review has been run."` No `diff.patch` is written; no `code-review.jsonl` line is appended. (Symmetric with `plan-writer` Phase 3.1 and `prd-writer` Phase 7.1.)

## Users & Context

**Primary User**
- **Who:** the relay developer (manually invoking commands during Pilar 2 / Pilar 3 development) and the future `/relay-execute` orchestrator agent (automated invocation in production). Same primary persona as the Plan Authoring PRD.
- **Current behavior:** writes implementations by hand against APPROVED plans, asks the LLM ad-hoc, or uses `/prp-implement` and re-shapes the output manually to fit relay's `PRPs/` paths and Decision Gate conventions. No autonomous code-rubric exists; tests get silently weakened with no rubric guard; no per-attempt audit artifact lands on disk.
- **Trigger:** a plan has just been approved (`*Status: APPROVED*`) and its source PRD's row N is `in-progress`; the next pipeline stage needs working code in the worktree before the Test Runner can run.
- **Success state:** an APPROVED `<basename>.code-review.jsonl` entry exists; the plan has been moved to `PRPs/plans/completed/` with `*Status: IMPLEMENTED*`; the source PRD's row N is `complete`; the Test Runner can proceed without re-derivation.

**Job to Be Done**
When an APPROVED plan lands and a feature phase needs implementation, I want code auto-written from the plan and auto-validated against a structural+static+semantic rubric (with a universal test-modification guard), so that the Test Runner can run on real code without me re-deriving context, the orchestrator can proceed without per-stage workarounds, and silent test weakening is detected at the rubric layer rather than caught only by the post-green reviewer downstream.

**Non-Users**
- The Plan Writer / Plan Reviewer (prior stage; produces the plan input).
- The Test Runner / `post-green-reviewer` (downstream consumers; operate on the worktree state `/relay-implement` leaves behind).
- Anyone needing Browser / Database / Manual validation Levels 4–6 baked into the agent contract — those go in the per-project plan body if applicable, not into the agent contract.

### MVP Scope

The MVP is the **Must** rows above plus all four **Should** rows. Five files created (two agents + two commands + docs updates), one autonomous writer/reviewer loop closed, three post-approval mutations atomic. With these, an APPROVED plan can run autonomously through code-writing and review, unblocking the Test Runner step of Pilar 2 and the `/relay-execute` orchestrator that depends on `/relay-implement` → `/relay-code-review`.

**Could** rows are deferred pending dogfood evidence. **Won't** rows are out of scope for this PRD entirely.

### User Flow

**Happy path — autonomous orchestration (`/relay-implement`):**

1. Plan reaches `*Status: APPROVED*` (existing plan pair); source PRD row N is `in-progress`.
2. Orchestrator (or developer) runs `/relay-implement PRPs/plans/<basename>.plan.md`.
3. Command emits Decision Gate evidence block at the command level. Reads `methodology.md`, plan, source PRD; verifies preconditions including AC-11 (PRD row N == `in-progress`).
4. Internal loop attempt 1: `implementer` reads the plan, executes Step-by-Step Tasks via `Edit`/`Write` in the working tree, runs Validation Commands Levels 1–3 after all tasks complete (D6).
5. After attempt: command captures `git diff <base-commit>` to `PRPs/reports/<feature>/phase-<N>/attempts/1/diff.patch`; oscillation check vs prior attempts; budget timer check.
6. `code-reviewer` runs in standard mode: R-S* / R-L* / R-SEM / R-X. Result APPROVED → D8 mutations → exit. Result CHANGES_REQUESTED → re-invoke implementer with the failing rubric items as feedback (attempt 2). Loop until APPROVED or budget exhausted.
7. Implementer may instead emit `TEST_CONTRACT_DISPUTE`: `code-reviewer` arbitrates → `DISPUTE_REJECTED` forces code on next attempt; `DISPUTE_UPHELD_*` → structured HALT (D9 Layer 2 + Layer 4).
8. On APPROVED: D8 mutations: plan flip `*Status: IMPLEMENTED*`, plan move to `PRPs/plans/completed/`, PRD row N flip `in-progress` → `complete` (best-effort atomic with rollback note on partial failure). Final summary emitted.
9. Test Runner consumes the worktree.

**Standalone `/relay-code-review` flow:**

1. Developer hand-edits code in the worktree against an APPROVED plan.
2. Developer runs `/relay-code-review PRPs/plans/<basename>.plan.md`.
3. Command emits Decision Gate evidence block; runs the `code-reviewer` in standard mode, single-shot (no internal loop).
4. Result APPROVED or CHANGES_REQUESTED, jsonl entry appended, exit. No D8 mutations.

**HALT flows:**

- Precondition fail (AC-11, AC-14) → exit before any agent invocation; nothing written.
- Retry budget exhausted → `FAILED_AFTER_N_RETRIES` HALT with full attempt history on disk.
- Time budget exhausted → `FAILED_TIME_BUDGET_EXCEEDED` HALT with elapsed wall-clock named.
- Oscillation detected → `FAILED_OSCILLATION_DETECTED` HALT with oscillating files named.
- Dispute cap exhausted → `FAILED_DISPUTE_CAP_EXCEEDED` HALT with dispute history named.
- Dispute upheld → structured HALT for human PRD update or B7/B8 bounce-back (deferred in MVP; message surfaced).

## Technical Approach

**Feasibility:** HIGH. Direct adaptation of the shipped plan-stage writer/reviewer pair; section template draws from the upstream `prp-implement.md` reference; Decision Gate machinery and review.jsonl plumbing already exist in the relay codebase. The novel parts are the universal R-X rule (test-modification guard with dispute escape valve), three-layer rubric, oscillation detection, and the dual-budget envelope — each is additive and small, and each has external evidence supporting its design.

### TDD routing

Current value of `tdd` in `docs/context/methodology.md`: **false**. TDD track inactive — tests written alongside implementation. Acceptance Criteria seed those tests.

### Architecture Notes

- **Same writer/reviewer split pattern as the Plan stage.** Clone the file structure of `plugins/relay/agents/plan-writer.md` and `plan-reviewer.md`, adapting phase content. Frontmatter conventions preserved (`name`, `description`, `model: sonnet`, `color`, `tools`).
- **Autonomous reviewer with auto-flip.** Past the interactivity boundary; no user dialogue. Symmetric with `plan-reviewer`; canonical divergence from `prd-reviewer`'s "Aprovar?" gate.
- **`implementer` tool allowlist:** `Read, Write, Edit, Glob, Grep, Bash, BashOutput, KillBash`. **No `Task`** — re-grounding is forbidden (the plan is the source of truth; plan-writer already grounded). **`Bash` is open at the agent layer**; the project's `.claude/settings.json` allowlist (generated by context-builder per the 2026-04-19 decision) is the security gate (D11).
- **`code-reviewer` tool allowlist:** `Read, Write, Glob, Grep, Bash, BashOutput`. Read-only over the repo. **`Write` only for `code-review.jsonl`**. **`Bash` restricted by prompt** to read-only operations (lint, type-check, `git diff`/`log`; no mutations). **NO `Edit` tool** — divergence from `plan-reviewer` documented in Decisions Log; consistent with the read-only review philosophy.
- **Plan / PRD mutations (D8) and audit-log writes performed by the COMMAND, not the agents.** Keeps mutation responsibility in one place; agents stay focused on their core role.
- **Per-attempt `diff.patch` is `git diff <base-commit>` captured after each attempt** (NOT just the per-attempt incremental delta — each diff is the cumulative diff against base, since attempts stack). Stored at `PRPs/reports/<feature>/phase-<N>/attempts/<i>/diff.patch`.
- **`<feature>` derivation** from plan filename pattern `<feature>-phase-<N>-<slug>.plan.md`: parse the prefix before `-phase-<N>-`. `<N>` from the same pattern. Fallback to `unknown` with a clear diagnostic if the pattern doesn't match (mirrors plan-reviewer R8c soft-fail).
- **Decision Gate evidence emitted by both commands at command invocation;** both agents' Phase 0 setups consult the three sources independently and HALT with the byte-exact message of AC-14 if any source is unreadable.
- **Oscillation detection: command-level pre-flight check** before each retry. Computes the set of files altered by attempt N's diff vs attempt N-1's; if the intersection contains ≥1 file whose final content in attempt N is byte-equal to the content in attempt N-2 or earlier, abort with `FAILED_OSCILLATION_DETECTED`.
- **Budget envelope:** the command starts a wall-clock timer at invocation; checks before each retry. First-to-expire wins (`max_implement_minutes` vs `max_implement_retries`). Disputes consume from the retry budget. Outcome codes are distinct.
- **Test Runner C4 symmetry:** `PRPs/reports/<feature>/phase-<N>/attempts/<i>/` is the same shape used by the Test Runner. The Test Runner already understands this layout; per-attempt `diff.patch` is a new file added under the same path.
- **`code-review.jsonl` schema** (extends plan-reviewer's): `{ timestamp, attempt, verdict, mode: "standard"|"arbitration", rubric: [...], dispute_evidence?: {...}, action: "rubric_fail"|"revalidation_fail"|"final_flip", user_message: "" }`. Append-only via `Read` + concat + `Write`.

| Risk | Likelihood | Mitigation |
|------|------------|------------|

**Market Context**

- **SWE-agent (NeurIPS 2024, [arXiv:2405.15793](https://arxiv.org/abs/2405.15793))** — caps LLM calls at 100 per instance; argues that ACI (Agent-Computer Interface) design — not model scale — determines whether plan-driven agents can fix real GitHub issues. Direct precedent for the "hard ceiling" pattern (`max_implement_retries` + `max_implement_minutes`).
- **OpenHands CodeAct 2.1 (Nov 2025, [openhands.dev](https://openhands.dev/blog/openhands-codeact-21-an-open-state-of-the-art-software-development-agent))** — single-agent strong baseline (53% SWE-Bench Verified) with no documented writer+reviewer architecture; supports `AgentDelegateAction` but no formal review loop or arbitration. Confirms relay's writer+reviewer split is novel territory rather than a borrowed pattern.
- **agentwiki.org common agent failure modes ([agentwiki.org](https://agentwiki.org/common_agent_failure_modes))** — same-action-repeat + two-state-alternation are the canonical oscillation failure modes; production case of a Claude Code sub-agent executing `npm install` 300+ times consuming 27M tokens; prescribes loop detection via action hashing + iteration limits 50–100. Direct support for D7's always-on oscillation detection.
- **arXiv 2409.20550 (UTSA / VT / OU multi-LLM hallucination study, [arXiv:2409.20550](https://arxiv.org/pdf/2409.20550))** — 576K samples across 16 LLMs; 43.53% task-requirement conflicts, 31.91% factual-knowledge conflicts, 24.56% project-context conflicts; Pass@1 between 0.04–10.40% on raw generation. Direct support for D9's "tests as rebuttable contract" + D7's structured retry budget.
- **arXiv 2604.20202 (Hallucination Inspector, [arXiv:2604.20202](https://arxiv.org/html/2604.20202))** — defines "Scaffolding Hallucination" (phantom imports / constructors / constants); AST cross-referencing achieves 100% precision and substantially outperforms LLM-as-judge approaches. Supports D4's static-layer rubric value.
- **arXiv 2601.19106 (deterministic AST hallucination detection, [arXiv:2601.19106](https://arxiv.org/html/2601.19106))** — 100% precision, 87.6% recall, 77% auto-fix rate on a code-hallucination benchmark; proposed as "lightweight semantic linter" rather than full agent loop.
