Decision Gate

A mandatory cognitive control mechanism that every relay agent must pass through before planning, coding, or reviewing. The gate forces explicit consultation of the project's recorded decisions, anti-patterns, and architecture so that the AI never silently re-evaluates a settled question.

This is not documentation — it is enforcement

The Decision Gate is the difference between "the agent should know the rules" and "the agent proved it read the rules." Without it, rules in docs/decisions.md are advisory; with it, they are binding.

Why the gate exists

LLM agents have no long-term memory across tasks. Every invocation starts fresh, reading the prompt and whatever context was handed in. Without an explicit ritual, the agent is free to re-solve problems the team already solved — picking a different PRP artifact path, inferring a different max-retries budget, activating TDD on a heuristic, etc.

Three concrete failure modes motivated the gate:

  1. Silent drift. A reviewer agent reads the current code, not the decisions.md. If the code disagrees with a decision, the reviewer has no way to know which one is authoritative. It will often side with the code.
  2. Re-invention. A planner agent "designs" the retry loop from scratch each time, producing slightly different budgets, backoff strategies, and abort conditions across runs. Non-determinism where it's harmful.
  3. Anti-pattern resurrection. A pattern we explicitly forbade (e.g., writing artifacts to .claude/) looks locally reasonable when the agent stumbles onto it. Without being told "don't do this," it does it.

The gate addresses all three by forcing the agent to state, in output, which decisions and anti-patterns apply before it proceeds. The statement is the evidence that the consultation happened.

When the gate activates

Every agent in the pipeline must run the gate at these trigger points:

  • Before planning — Plan Writer (before producing the plan), PRD Writer (before drafting the PRD).
  • Before coding — Implementer (before editing any file), TDD Writer (before generating tests).
  • Before reviewing — any reviewer (Plan Reviewer, PRD Reviewer, TDD Reviewer, post-green reviewer).
  • Before a Test Runner attempt — after classification flips to RETRY_NEEDED, before the Implementer consumes the feedback.

Reads (exploration, search, grep) do not trigger the gate. Pure analysis that produces only a report also doesn't. The gate guards actions that produce artifacts or change state.

Mandatory consultation sources

At each activation, the agent must open and scan these files in the target project (or the plugin repo, if operating there):

docs/decisions.md
The settled choices. The agent finds the entries that touch the current task and treats them as binding.
docs/anti-patterns.md
The forbidden moves. The agent checks whether its planned action matches any anti-pattern; if so, it halts.
docs/context/architecture.md
Component boundaries, allowed dependencies, artifact paths. The agent confirms its plan respects them.
docs/context/constraints.md
Project-level "do-not" list: frameworks, languages, patterns disallowed. The agent confirms its plan doesn't invoke any.
docs/context/methodology.md
Methodology declarations. test_frameworks is the activation gate for the test pair — non-empty runs it, [] or no file skips it silently; tdd selects only the ordering (true test-first, false test-after). docs_sync and figma_track gate their own opt-in flows the same declared, non-heuristic way. Details.
docs/domain/areas/*.md
Bounded contexts for the task. The agent identifies which area(s) the change touches and respects each area's specific invariants.

Missing files are not a pass. If docs/decisions.md is absent, the agent must abort with a clear message: "Decision Gate source missing — run *init first." The gate fails closed.

The evidence block

After consulting the sources, the agent emits an evidence block at the top of its output. The block is how the gate is audited — a reviewer (human or another agent) can spot-check it against the source files. A well-formed evidence block looks like: 

--- Decision Gate ---
Task: Implement B4 auto-correction loop wiring in /relay-test
Sources consulted:
  - docs/decisions.md       (entries 7, 8, 9, 10)
  - docs/anti-patterns.md   (sections 1, 5, 7)
  - docs/context/architecture.md (pipeline stages, Test Runner boundary)
  - docs/context/methodology.md  (test_frameworks: [] — test pair inactive)
  - docs/domain/areas/*.md  (no areas touched — infra-only change)
Binding decisions for this task:
  - max_test_retries = 3 (entry 7): loop budget
  - max_test_minutes = 30 (entry 8): time budget
  - PRPs/ artifact root (entry 6): all writes to PRPs/reports/<feature>/
Applicable anti-patterns to avoid:
  - #1 weakening tests to turn green → loop only edits implementation, never tests
  - #7 writing under .claude/ → artifacts go under PRPs/
Plan:
  [rest of the output follows]
----------------------

The block is short on purpose — 8-15 lines, not a full re-quote of the sources. It proves the agent read and identified the relevant items. The body of the output must be consistent with everything listed.

Halt conditions

When the gate identifies any of the following, the agent halts and surfaces the conflict to the human instead of proceeding:

  1. Planned action matches a documented anti-pattern. Example: planning to mark a failing test as @skip to reach green — matches anti-pattern #1.
  2. Planned action contradicts a decision. Example: proposing to write a PRD to .claude/PRDs/ — contradicts decision #6 (PRPs/ artifact root).
  3. Planned action violates architecture boundaries. Example: a Test Runner agent proposing to write source files — Test Runner is read-only against the implementation.
  4. Required source is missing. Example: docs/context/methodology.md not found — project wasn't initialized, gate aborts.

Halts are not silent — the agent emits a clearly-labeled HALT record explaining which rule blocked it and what the human can do (update the decision, add an exception, or rethink the task).

Exemptions

The gate is expensive in tokens — it requires reading multiple files and producing a structured preamble. To keep the cost proportional, a narrow exemption applies:

Micro-change exemption

Single-file edits that do not modify any exported symbol, public contract, or configuration value may skip the full gate. A short "consulted decisions #N" note suffices.

Concretely: typo fixes, comment-only edits, formatter-only changes, localized internal refactors. The Implementer itself decides whether the exemption applies and logs the decision.

The exemption is not available for: new files, deletions, config changes, schema changes, cross-file refactors, test-file edits (any), or anything touching CI/pipeline config. When in doubt, run the full gate.

Interaction with the reviewer loop

Writer/reviewer pairs use the gate twice — once at write time, once at review time. The reviewer's gate pass is specifically looking for things the writer might have missed; it's an independent consultation, not a cross-check of the writer's evidence block.

If the reviewer's gate flags a decision the writer ignored, the review returns CHANGES_REQUESTED with the decision ID as feedback. The writer's next iteration addresses it, and the cycle continues until the reviewer's gate is clean.

Adding a new binding source

If a new category of rule emerges (e.g., a security policy document), adding it to the gate requires three steps:

  1. Create the source file at a stable path and fill it with concrete rules.
  2. Add the file to the "Mandatory consultation sources" list in docs/decision-gate.md (the plugin-side canonical version of this page).
  3. Update the evidence block template in the relevant agent prompts (Writer, Reviewer, Implementer) to include the new source.

Do not expand the source list lightly — every new source adds tokens to every gate pass. Prefer consolidating into docs/decisions.md or docs/anti-patterns.md when the rule fits.

Enforcement: soft today, harder tomorrow

Currently enforcement is prompt-level — the gate ritual is described in each agent's system prompt, and the evidence block is self-reported. A future hardening (not yet implemented) would:

  • Add a PreToolUse hook that blocks the agent's first write until an evidence block is present in the session.
  • Lint the evidence block structure and reject malformed ones.
  • Cross-check that decisions cited in the block actually exist in docs/decisions.md.

These are planned for Phase 5 (CI/CD integration) along with other deterministic enforcement layers. In the meantime, the post-green reviewer and human PR review are the backstops.
