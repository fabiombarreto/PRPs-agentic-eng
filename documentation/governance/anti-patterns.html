Anti-patterns

Patterns that look correct from a local perspective but are forbidden at the project level. The AI must not implement anything listed here — even when the generated code or suggested approach seems reasonable. Anti-patterns are consulted via the Decision Gate before every planning or implementation step.

1. Weakening or deleting tests to make the loop turn green

Anti-pattern

What it is: An agent edits, skips, or removes failing tests in order to satisfy the "all tests pass" exit condition of the Test Runner loop.

Why it's forbidden: Optimizes for "verde" instead of "correto". The loop is supposed to fix the implementation, not the contract. The post-green reviewer (B5) exists precisely to catch this.

What to do instead: Fix the implementation, or — if the failure exposes a real requirement gap — abort and surface the conflict to the human.

Carve-out (NOT weakening): legitimate retirement of an obsolete test (its behavior-under-test is gone from the in-scope criteria) or a redundant test (a proven duplicate), performed by the approved test pair, recorded in the suite manifest's lifecycle ledger, and validated by test-reviewer's R-LIFECYCLE-LEGITIMATE. The post-green reviewer accepts a removal or skip only when it matches an APPROVED ledger entry; every unmatched removal — and every removal when no manifest exists — still blocks. The implementer and the auto-correction loop still author zero test-file changes. See decision 41.

Areas affected: Test Runner (B1–B5), auto-correction loop (B4), test pair (test-writer, test-reviewer).

2. Writing tests that mirror the implementation instead of the requirements

Anti-pattern

What it is: test-writer produces tests that encode specific implementation choices (internal method names, private data shapes, mocked collaborators that presuppose a design) instead of requirements from the PRD. In test-first this mirrors an imagined implementation; in test-after the risk sharpens — the tests can mirror the actual code just written, exerting no independent pressure.

Why it's forbidden: Tests and implementation are then born coupled and exert no design pressure on the code — the core failure mode of AI-driven testing.

What to do instead: test-writer derives tests from PRD requirements and observable behavior. test-reviewer rejects suites that leak implementation details (R-IMPL-LEAK), rely on excessive mocks, or contain trivial asserts — in both modes.

Areas affected: test pair (test-writer, test-reviewer).

3. Emitting secret values in run reports or logs

Anti-pattern

What it is: Test Runner captures stdout/stderr that contains API keys, tokens, or other credentials and writes them verbatim into the execution report or PR body.

Why it's forbidden: Reports can end up in public PRs; any leak is an incident. The A4 component mandates redaction; B6 (report) must apply the filter.

What to do instead: Indicate only presence/absence of credentials. Redact values known to be secret at the source using the three-layer redaction policy.

Areas affected: Test Runner infra (A4), report generator (B6).

4. Activating the test pair by heuristic

Anti-pattern

What it is: Inferring that a project wants relay-authored tests from the existence of a test folder, a high test count, or a CI job, and enabling the test pair automatically — or inferring the tdd: value the same way.

Why it's forbidden: Activation is a methodology declaration, not a side effect of having tests; silent activation surprises teams. And tdd: selects ordering (test-first versus test-after), which must not be guessed.

What to do instead: Read docs/context/methodology.md. The single activation gate is a declared framework: a non-empty test_frameworks runs the pair in both modes; test_frameworks: [] or missing frontmatter skips it silently. The tdd: value only selects ordering — true is test-first, false is test-after — never whether the pair runs. The context-builder skill MUST create this file in every *init run with tdd: false and test_frameworks: [] as the defaults, so the pair is opt-in by declaring a framework.

Areas affected: orchestrator activation, context-builder skill, test pair (test-writer, test-reviewer).

Corrected 2026-08-06

This item previously said the gate was "exactly one key: tdd: true | false", with tdd: false skipping the pair. That was superseded on 2026-07-10 (decision 41) and the page had not caught up. This repository is its own counterexample: it declares tdd: false and test_frameworks: ["node:test"], and the pair is active in test-after mode.

5. Relying on interactive permission prompts in the autonomous loop

Anti-pattern

What it is: Shipping pipeline steps that require per-command confirmation in Claude Code, breaking the "single prompt → PR" promise.

Why it's forbidden: Component C1 of the Phase 2 plan mandates .claude/settings.json with an explicit allowlist; without it, the auto-correction loop halts on its first bash command.

What to do instead: Declare all required commands in the plugin's versioned settings allowlist. Never rely on the human to approve individual tools during an autonomous run.

Areas affected: permissions (C1), orchestrator autonomy.

6. Injecting plugin defaults into the target project's decisions.md

Anti-pattern

What it is: The context-builder skill (or any future agent) writes plugin-level defaults — max_test_retries: 3, tdd: false default, PRP root path, etc. — into the target project's docs/decisions.md as if they were decisions the project made.

Why it's forbidden: Conflates two different purposes. decisions.md records project decisions that the AI must not re-evaluate; plugin defaults are relay's own contracts and live in relay's repo. Copying them into every target project creates drift — when relay updates a default (e.g., after telemetry), target projects keep the stale value, and *update mode correctly refuses to overwrite human-validated content.

What to do instead: Plugin defaults stay in the plugin (hardcoded in agent prompts or in a future plugin config file). Target projects record in their decisions.md ONLY when they explicitly override a default, with the rationale. Visibility of inherited defaults is a separate concern — deferred to the Phase 2 config design (.relay.yaml or equivalent).

Areas affected: context-builder skill, future Docs Updater, future plugin-config generators.

7. Writing pipeline artifacts under .claude/

Anti-pattern

What it is: An agent writes a PRD, plan, Test Runner report, TDD suite, or any other pipeline artifact somewhere under .claude/ (e.g., .claude/PRPs/prds/foo.prd.md).

Why it's forbidden: Claude Code enforces hardcoded permission prompts on writes to .claude/. Each prompt interrupts the autonomous portion of the pipeline. The permission guards are intentional and have no bypass.

What to do instead: Write to PRPs/ at the target repository root: PRPs/prds/, PRPs/plans/, PRPs/reports/<feature>/. Every agent that produces an artifact MUST use this root.

Scope / exception: This rule applies to pipeline artifacts — things produced during an autonomous run. It does NOT apply to .claude/settings.json, which is setup configuration written once by the context-builder during *init. See PRP artifact paths.

Areas affected: PRD Writer, Plan Writer, TDD Writer, Test Runner report (B6), observability (C4), Docs Updater, orchestrator.

8. Treating plugins/prp-core/ as active relay code

Anti-pattern

What it is: Extending, importing from, or documenting plugins/prp-core/ as if it were part of the relay plugin surface — e.g., generating domain areas from it, referencing its /prp-* commands as relay features, or editing its files as part of relay development.

Why it's forbidden: prp-core is the upstream Wirasm plugin kept on disk as a format reference. Mixing it into relay couples relay to upstream evolution and blurs ownership. See docs/decisions.md.

What to do instead: Read prp-core files when you need to see how a Claude Code skill/command/agent/hook is structured. Never cite or import them as part of relay.

Areas affected: plugin scope, documentation scope.

9. Flipping figma_track (or any opt-in gating key) by heuristic

Anti-pattern

What it is: Inferring that a project wants the Figma track active from Figma-shaped filenames, .fig references, pasted Figma URLs, or design-tool mentions in commit history, and flipping figma_track: true automatically instead of by explicit human or command action.

Why it's forbidden: figma_track follows the same non-heuristic contract already established for docs_sync and tdd: default-false on *init, preserve an already-set value on *update, and backfill only when the key is entirely absent. A run whose behavior depends on Figma involvement being detected rather than declared reintroduces exactly the "forgot to check" versus "doesn't apply" ambiguity the declaration model exists to prevent.

What to do instead: Read figma_track from docs/context/methodology.md frontmatter only. It flips to true solely via a human edit or the explicit confirmation step of /relay-design-map — never by detection. Enforced deterministically by the gating-structure check, extensible to future keys by appending to its registry.

Areas affected: context-builder skill, npm run validate (gating-structure check), the Figma implementation track.

10. Querying the Figma MCP from a dispatched writer/reviewer agent

Anti-pattern

What it is: A Task-dispatched agent calls a Figma MCP tool directly, instead of reading only the Figma evidence already persisted to disk by the interactive command that dispatched it.

Why it's forbidden: Confirmed technically reachable by the 2026-07-22 spike (decision 44), but the baseline architecture deliberately keeps every Figma MCP call in the interactive command's own session, so the entire autonomous stretch of the pipeline stays structurally independent of Figma and MCP availability and context-budget management stays centralized.

What to do instead: Dispatched agents read Figma facts exclusively from the persisted evidence bundle the calling command writes before dispatch. This is enforced structurally, not just by instruction: those agents carry no Figma-MCP tool and no Bash or WebFetch in their allowlists.

Scope note: The rule targets Task-dispatched agents. design-spec-writer is inline-adopted by /relay-design-spec and never dispatched, so it queries the Figma MCP directly in its own session by design — the premise does not apply to an inline-adopted role.

Areas affected: design-map-writer, design-map-reviewer, research-design, visual-verifier, /relay-design-map.

11. Inferring formatter_cmd's value or invocation source outside its declared discovery chain

Anti-pattern

What it is: Any component — context-builder, /relay-write-test, or a future consumer such as the /relay-implement preflight — infers a project's formatter command, or decides to invoke one, from a signal outside the two sanctioned sources: the formatter_cmd: key in docs/context/methodology.md frontmatter, and package.json's scripts.format. Concretely: detecting a formatter from installed devDependencies (prettier, eslint --fix, black, etc.), the presence of a config file (.prettierrc, .eslintrc), a file extension, or any other environmental heuristic.

Why it's forbidden: formatter_cmd follows the same non-heuristic contract already established for tdd, docs_sync, and figma_track — deterministic emission/preserve/backfill, never invented. /relay-write-test's discovery chain is deliberately closed to exactly two ordered branches so an autonomous, unattended Bash formatter invocation is always traceable to a human-authored declaration, never to environment sniffing. The invocation runs with no human review before it executes, so an incorrectly inferred command is a worse failure mode than a correctly-skipped one.

What to do instead: Read formatter_cmd from docs/context/methodology.md frontmatter; when absent, read package.json's scripts.format; when neither exists, record the omission explicitly and skip the formatting step — never silently, and never by falling back to a third, heuristic branch.

Areas affected: /relay-write-test command (formatter discovery chain), context-builder skill (formatter_cmd emit/preserve/backfill), any future formatter_cmd consumer (e.g. /relay-implement's preflight).

12. Treating an R-SEM finding as self-executing test-edit authorization

Anti-pattern

What it is: A code-review R-SEM finding (or any other reviewer finding) that implies or requests a test-file change is treated by the implementer — or any other agent — as itself authorizing an edit to the test, bypassing the TEST_CONTRACT_DISPUTE channel.

Why it's forbidden: R-X strict already forbids the implementer from editing test files directly, and the code-reviewer's own read-only charter reinforces it. Neither guard has an implicit exception for the reviewer's own finding: an R-SEM row is a record of semantic disagreement, not a delegation of authority. The 2026-08-26 arbitration ruled explicitly that TEST_CONTRACT_DISPUTE remains the mandatory channel even when it was the reviewer's own R-SEM row that requested the change.

What to do instead: When a prior_feedback entry cites an R-SEM row requesting a test change, read it as identifying what to fix in the implementation, never as license to edit the disputed test directly. If the implementer genuinely believes the test contradicts the PRD, open TEST_CONTRACT_DISPUTE instead of editing it.

Areas affected: code-reviewer agent (R-SEM section), implementer agent (targeted revision mode / dispute guidance).

13. Opening TEST_CONTRACT_DISPUTE for formatting

Anti-pattern

What it is: The implementer submits a TEST_CONTRACT_DISPUTE claim over a formatting-only difference in a test file — whitespace, indentation, quote style, or any other non-semantic difference — rather than a genuine semantic contradiction with the PRD.

Why it's forbidden: TEST_CONTRACT_DISPUTE is the channel for semantic contradiction between a test's expectations and the PRD; it is not a pressure valve for formatting. Formatting has its own dedicated prevention mechanism (the formatter_cmd discovery chain and command-layer invocation, plus /relay-implement's preflight), which was deliberately chosen over allowing formatting disputes as an alternative.

What to do instead: A formatting-only mismatch is resolved by the test-formatting prevention preflight (/relay-write-test's formatter invocation, /relay-implement's preflight), never by disputing the test's contract. Reserve TEST_CONTRACT_DISPUTE exclusively for genuine semantic contradictions with the PRD.

Areas affected: implementer agent (dispute channel), test-formatting prevention preflight.

14. Sleeping, retrying, or backing off against a Figma MCP quota error

Anti-pattern

What it is: Responding to a Figma MCP quota-exhaustion error with a sleep-and-retry loop, capped exponential backoff, or any "try again" rung in a degradation ladder — instead of aborting immediately and recording how far the run got.

Why it's forbidden: Backoff is the correct response to a per-minute bucket and useless against Figma's MCP limits, which are per-day (200 on Starter/Professional, 600 on Organization) and per-month (6 on every View/Collab seat). An observed hand-written REST script slept through five attempts against a monthly bucket and enriched zero nodes — it converted a fast, legible failure into a slow, opaque one. A ladder whose only recovery rung is "try again" reproduces the original defect while appearing to handle it. Figma's MCP documentation also defines neither 429 nor Retry-After, so there is no reset signal to back off toward: any wait interval would be invented.

What to do instead: Abort and record. HALT with FAILED_FIGMA_QUOTA_EXHAUSTED (detected by error class/string, never by HTTP status), capture the partial call_log and the named rung into the evidence bundle, and leave a checkpoint so the next invocation costs only the delta. Promise no reset time — the MCP reset window is undocumented in every source consulted. The narrow exception is get_code_connect_map, whose pre-existing non-fatal path is unchanged: a quota error there records code_connect: unavailable(quota-exhausted) and the run continues, because the bundle is already as complete as that run intended.

Areas affected: /relay-design-map command Phase B, the Figma degradation ladder, any future Figma MCP consumer.

15. Wholesale confidence downgrade on a degraded Figma rung

Anti-pattern

What it is: Reacting to a degraded rung (DEGRADED_NO_ENRICHMENT and friends) by downgrading every row of docs/design/component-map.md at once — or by overwriting a row that carries a human verified_at.

Why it's forbidden: A degraded rung means some evidence is missing, not that all of it is worthless. Variant axes remain recoverable from the Figma component's own Prop=Value name without any node enrichment, which is exactly how 17 rows were legitimately CONFIRMED in an observed zero-enrichment bundle; a wholesale rule would have destroyed them and turned an honest partial result into a useless one. Silently overriding a human verified_at is the same failure as flipping a gating key by heuristic — machine degradation must not quietly erase a human judgment.

What to do instead: Downgrade surgically. Rows whose Props/variant mapping relies only on name-derivable variant axes may remain CONFIRMED; rows depending on non-variant properties (booleans, TEXT, INSTANCE_SWAP, or anything not derivable from the name) may not. A row carrying a human verified_at is never downgraded by the rule — flag it for re-verification instead. R-DM7 fails a map whose declared completeness contradicts its bundle, or whose CONFIRMED rows depend on property data the bundle marks unenriched.

Areas affected: design-map-writer agent, component-map-template.md, design-map-reviewer agent (R-DM7).

16. Clearing an R-X match on anything other than the computed equivalence report

Anti-pattern

What it is: A code-reviewer marks an R-X-matched test path as cleared on its own reading of the diff — "only comments changed", "the assertions look the same" — or stretches an arbitration outcome to manufacture a clearance the schema does not offer, instead of running executable-content-hash.mjs and honouring its report. The mirror image is an implementer asserting the same thing in a dispute claim.

Why it's forbidden: R-X exists so that "my edit was harmless" is never self-certified, and that is exactly what the equivalence step preserves: the clearance is legitimate ONLY because a third-party script computed it and both hashes are in the verdict for anyone to re-run. Comment-stripping done by eye is also unreliable in precisely the way the field guard's own defect demonstrated — its comment strip silently consumed the tail of every https:// line, blinding the check to the lines it existed to read.

What to do instead: Run the script over exactly the matched paths and treat cleared: false, an unsupported extension, an ambiguous source, or a script that cannot run as a plain R-X match. Record the failing paths verbatim. Purely additive, AC-grounded change is DISPUTE_UPHELD_NEW_COVERAGE in arbitration — with its numstat precondition verified, not claimed — never a clearance invented in standard mode.

Areas affected: code-reviewer agent (R-X Steps X.2/X.3, arbitration), implementer agent (dispute discipline), /relay-implement (hard rule 9).

17. Mutating a target project's working tree from a review agent

Anti-pattern

What it is: A review agent — test-reviewer, post-green-reviewer, or any future reviewer holding Bash — runs git stash, git checkout, git restore, git reset or git clean against the project under review, typically to isolate a clean state so a RED/GREEN legitimacy check is more conclusive.

Why it's forbidden: These agents are routinely pointed at a developer's live tree with uncommitted work in it, and cannot tell it from a disposable one. A stash that is never popped — interrupted run, failed command, a later halt — destroys work the agent was never asked to touch. This happened in the field on 2026-08-28 and nearly cost a full phase.

What to do instead: Read the tree as it is (git diff, git show, the files on disk). When a check genuinely needs a state you cannot have, emit the legitimacy row with passed: null and a reason naming what could not be independently re-verified. Bash(git stash*) is deliberately absent from the recommended allowlist; do not re-add it.

Areas affected: test-reviewer agent, post-green-reviewer agent, resources/settings-allowlist.md.

Adding a new anti-pattern

When review identifies a pattern that should be permanently forbidden:

  1. Edit docs/anti-patterns.md in the plugin repo following the template at the bottom.
  2. Each entry: What it is, Why it's forbidden, What to do instead, Areas affected.
  3. Mark [INFERRED - VALIDATE] if the rule is implied by consistency or comments rather than explicitly documented.
  4. If a counterpart decision exists (the positive rule), also add it to docs/decisions.md.
  5. Update this HTML page with a link to the new entry.
Decision Gate enforcement

Every agent consulting the Decision Gate must read this file. A forbidden pattern in an agent's plan is a HALT — the agent must flag the conflict rather than proceed.
