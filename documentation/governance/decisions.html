Decisions

The stable technical and process choices that define how relay works. Every entry is dated, explains the context that forced the choice, what was decided, and the reason the chosen option beat the alternatives. Once a decision is listed here, the AI must not re-evaluate it — this is the protection the Decision Gate enforces.

Canonical source

This page mirrors docs/decisions.md in the relay plugin repo. When the two drift, the .md file is authoritative. Entries are added here as they're committed there.

Entries

1. Marketplace-based distribution

Date
2026-04-19
Context
The repository needs a way to be installed into Claude Code users' environments.
Decision
Ship relay as the sole plugin of a marketplace declared at the repo root (.claude-plugin/marketplace.json). Plugin metadata at plugins/relay/.claude-plugin/plugin.json.
Reason
Marketplace is Claude Code's first-class distribution mechanism.

2. prp-core as reference

Date
2026-04-19
Context
relay incorporates ideas from Wirasm's prp-core plugin. The repo keeps a full copy of prp-core under plugins/.
Decision
plugins/prp-core/ is a read-only reference for file format and agent design; it's not merged into, extended, or imported by relay.
Reason
Keeps upstream evolution independent from relay's own evolution. Lets relay own its prompts without forking.

3. Phased rollout

Date
2026-04-19
Context
Building an end-to-end autonomous delivery pipeline in one step is infeasible.
Decision
Five ordered phases: Foundation (context-builder + decision-gate) → Testing (Test Runner + self-correction loop) → Agents (single-command orchestrator) → Approval (merge + docs updater) → CI/CD integration.
Reason
Each phase produces something verifiable and unlocks the next, avoiding a big-bang release.

4. TDD opt-in only

Date
2026-04-19
Context
Phase 2 includes an optional TDD Writer/Reviewer pair (B7/B8) that runs between Plan Reviewer and Implementer.
Decision
The TDD track activates only when the target project explicitly declares TDD in its context-builder output. Heuristics (test folder exists, high coverage, etc.) MUST NOT activate the track.
Reason
Explicit declaration prevents surprising projects that happen to have tests but don't practice TDD as a methodology.

5. Methodology declaration file

Date
2026-04-19
Context
The TDD opt-in decision mandated explicit declaration but left the storage location and format open.
Decision
Every project initialized by the context-builder skill receives a docs/context/methodology.md file with YAML frontmatter as the single source of truth. The TDD track reads exactly one key: tdd: true | false. Additional methodologies (BDD, pair-review, branching policy) may be added as new frontmatter keys without breaking the tdd contract.
Reason
A dedicated file is unambiguous for agents to parse, survives prose rewrites that could eat an embedded section, and scales to other methodology declarations. Absence signals a setup bug rather than "TDD off."

6. PRP artifacts under PRPs/

Date
2026-04-19
Context
The upstream prp-core convention wrote PRDs, plans, reports under .claude/PRPs/. Claude Code applies hardcoded permission prompts on writes to .claude/.
Decision
All pipeline artifacts — PRDs, implementation plans, Test Runner reports, TDD initial suites, observability logs — are written under PRPs/ at the target repo root. Nothing pipeline-produced goes under .claude/.
Reason
Claude Code's permission guards are intentional and have no bypass. Using a sibling folder keeps artifacts versionable, auditable, and writable by the autonomous loop without per-file consent prompts.

7. max_test_retries = 3

Date
2026-04-19
Context
Component B4 is the auto-correction loop (run → classify → correct → re-run). A retry default was proposed but not nailed down semantically.
Decision
Default 3. Counter counts correction attempts after the initial run (so the suite runs at most 4 times per session). Flakiness retries (B3 detects non-determinism) do NOT count. Oscillation aborts BEFORE exhausting the budget. Value 0 is forbidden.
Reason
1–2 aborts prematurely on second-tier bugs. 5+ wastes expensive E2E time when the loop is stuck. 3 matches literature on agentic correction loops (Ralph, SWE-Agent) and common CI retry policies.
Override
Heavy E2E (>5 min per run) → lower to 2. Fast unit-only → raise to 5.

8. max_test_minutes = 30

Date
2026-04-19
Context
max_test_retries bounds correction attempts but not wall-clock. A slow E2E suite (15 min × 4) burns 67 minutes before retry-exhausted abort.
Decision
Default 30, covering total session wall-clock. Independent of retries — whichever exhausts first wins. Outcome codes distinct: FAILED_AFTER_N_RETRIES vs FAILED_TIME_BUDGET_EXCEEDED. Value 0 forbidden.
Reason
Covers typical medium projects with 2x headroom. Forces heavy-E2E projects to consciously raise the budget or shrink the feature.

9. Layered execution: adaptive

Date
2026-04-19
Context
Planning doc §10 proposes layered execution (unit → integration → E2E) to save time; open question was whether it should be automatic or opt-in.
Decision
Adaptive: the context-builder detects layer signals (separate directories, markers, commands, scripts) in Phase 1 and activates layered execution automatically when signals are found. Flat execution when no signals. Override via future .relay.yaml.
Failure behavior
Failure at layer N skips subsequent layers. Each retry re-runs from layer 1.
Reason
Pure automatic risks false-positive abort decisions. Pure opt-in leaves benefit on the table. Adaptive: activate when signals are strong, report the reason, let the team override.

10. Interactivity boundary

Date
2026-04-19
Context
Original framing was "one prompt → PR." In practice, the highest-leverage moment to catch scope drift is during PRD authoring. Fixing those issues after implementation cascades rework across every stage.
Decision
The pipeline has an explicit interactivity boundary at PRD approval. PRD Writer + PRD Reviewer run the full 6-phase Q&A loop with the user. Plan, TDD, Implementer, Code Reviewer, Test Runner, Report + PR Creator run autonomously after PRD approval.
Reason
Minutes of dialog save hours or days of downstream rework. Net win on confidence and total time-to-PR.

11. PRD template forked from prp-core

Date
2026-04-19
Context
relay needs a canonical PRD shape that downstream agents can rely on, that humans can reason about, and that carries relay-specific contracts.
Decision
Fork prp-core's output template. Preserve the 6-phase Q&A flow. Add three mandatory extensions: Decision Gate evidence block as header, Acceptance Criteria (test scenarios) section, TDD routing note.
Reason
Reuse a proven structure; fork (not link) prevents upstream changes from silently altering relay's contract.

12. Command surface

Date
2026-04-19
Context
Goals: every stage individually invokable (testing, manual intervention); orchestrator composes them; naming clean; reuse prp-core familiarity where it exists.
Decision
Ship 12 commands + 1 placeholder. Writers produce artifacts; reviewers validate existing artifacts (including hand-edited). Orchestrator invokes them in fixed order and loops writer→reviewer pairs on CHANGES_REQUESTED.

13. .claude/settings.json policy

Date
2026-04-19
Context
Component C1 of Phase 2 requires .claude/settings.json to carry pre-approved permissions so the autonomous loop doesn't stall on permission prompts.
Decision
Narrow patterns, never broad. Allowlist patterns specific to detected commands. Catch-all patterns (Bash(*), Bash(git *), etc.) are forbidden.
Invariant denylist applied to every project. Destructive operations always require human confirmation (git push --force, git reset --hard, rm -rf outside .worktrees/, sudo, global installs, curl | sh, docker system prune, GitHub API mutations).
Generated by the context-builder from Phase 1 stack detection, not by the pipeline itself.
Exception
.claude/settings.json is setup config, not a pipeline artifact. Context-builder writes it once during *init (interactive). The autonomous pipeline only reads, never writes under .claude/.

14. Secret redaction policy

Date
2026-04-19
Context
Test Runner captures stdout/stderr into versioned reports that travel with the PR. Without redaction, any inadvertent env-var print leaks the secret.
Decision
Three-layer policy:
  1. Layer 1 (invariant defaults) — env name wildcards (*KEY*, *TOKEN*, *SECRET*, *PASSWORD*, *CREDENTIAL*, *AUTH*), exact-match URL env vars (DATABASE_URL, REDIS_URL, etc.), value regex for well-known secret formats (AWS, Stripe, GitHub PAT, JWT, PEM, OpenAI, Anthropic, Google).
  2. Layer 2 (per-project extensions) — PRPs/redaction-extensions.txt, created empty by context-builder.
  3. Layer 3 (documented non-redacted) — semi-sensitive values left alone by default (service-account non-key fields, git hashes).
URL handling
Connection strings replaced integrally with [REDACTED_URL]. No parse-and-partial — parsers fail on passwords with special characters.
See also
Redaction policy reference.

Adding a new decision

When a new stable decision is made (typically during PRD authoring or during a review), follow this protocol:

  1. Edit docs/decisions.md in the plugin repo with a new entry using the template at the bottom of that file.
  2. Include date, context, decision, reason, and areas affected.
  3. If a counterpart anti-pattern exists (the inverse rule), add it to docs/anti-patterns.md as well.
  4. Update this page with a link to the new entry.
Decision Gate enforcement

Once a decision lands here, every subsequent agent reading this file via the Decision Gate must treat it as settled — no re-evaluation. That's what makes decisions stable.
