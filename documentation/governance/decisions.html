Decisions

The stable technical and process choices that define how relay works. Every entry is dated, explains the context that forced the choice, what was decided, and the reason the chosen option beat the alternatives. Once a decision is listed here, the AI must not re-evaluate it — this is the protection the Decision Gate enforces.

Canonical source

This page mirrors docs/decisions.md in the relay plugin repo. When the two drift, the .md file is authoritative. Entries are added here as they're committed there.

Entries

1. Marketplace-based distribution

Date
2026-04-19
Context
The repository needs a way to be installed into Claude Code users' environments.
Decision
Ship relay as the sole plugin of a marketplace declared at the repo root (.claude-plugin/marketplace.json). Plugin metadata at plugins/relay/.claude-plugin/plugin.json.
Reason
Marketplace is Claude Code's first-class distribution mechanism.

2. prp-core as reference

Date
2026-04-19
Context
relay incorporates ideas from Wirasm's prp-core plugin. The repo keeps a full copy of prp-core under plugins/.
Decision
plugins/prp-core/ is a read-only reference for file format and agent design; it's not merged into, extended, or imported by relay.
Reason
Keeps upstream evolution independent from relay's own evolution. Lets relay own its prompts without forking.

3. Phased rollout

Date
2026-04-19
Context
Building an end-to-end autonomous delivery pipeline in one step is infeasible.
Decision
Five ordered phases: Foundation (context-builder + decision-gate) → Testing (Test Runner + self-correction loop) → Agents (single-command orchestrator) → Approval (merge + docs updater) → CI/CD integration.
Reason
Each phase produces something verifiable and unlocks the next, avoiding a big-bang release.

4. TDD opt-in only

Date
2026-04-19
Context
Phase 2 includes an optional TDD Writer/Reviewer pair (B7/B8) that runs between Plan Reviewer and Implementer.
Decision
The TDD track activates only when the target project explicitly declares TDD in its context-builder output. Heuristics (test folder exists, high coverage, etc.) MUST NOT activate the track.
Reason
Explicit declaration prevents surprising projects that happen to have tests but don't practice TDD as a methodology.

5. Methodology declaration file

Date
2026-04-19
Context
The TDD opt-in decision mandated explicit declaration but left the storage location and format open.
Decision
Every project initialized by the context-builder skill receives a docs/context/methodology.md file with YAML frontmatter as the single source of truth. The TDD track reads exactly one key: tdd: true | false. Additional methodologies (BDD, pair-review, branching policy) may be added as new frontmatter keys without breaking the tdd contract.
Reason
A dedicated file is unambiguous for agents to parse, survives prose rewrites that could eat an embedded section, and scales to other methodology declarations. Absence signals a setup bug rather than "TDD off."

6. PRP artifacts under PRPs/

Date
2026-04-19
Context
The upstream prp-core convention wrote PRDs, plans, reports under .claude/PRPs/. Claude Code applies hardcoded permission prompts on writes to .claude/.
Decision
All pipeline artifacts — PRDs, implementation plans, Test Runner reports, TDD initial suites, observability logs — are written under PRPs/ at the target repo root. Nothing pipeline-produced goes under .claude/.
Reason
Claude Code's permission guards are intentional and have no bypass. Using a sibling folder keeps artifacts versionable, auditable, and writable by the autonomous loop without per-file consent prompts.

7. max_test_retries = 3

Date
2026-04-19
Context
Component B4 is the auto-correction loop (run → classify → correct → re-run). A retry default was proposed but not nailed down semantically.
Decision
Default 3. Counter counts correction attempts after the initial run (so the suite runs at most 4 times per session). Flakiness retries (B3 detects non-determinism) do NOT count. Oscillation aborts BEFORE exhausting the budget. Value 0 is forbidden.
Reason
1–2 aborts prematurely on second-tier bugs. 5+ wastes expensive E2E time when the loop is stuck. 3 matches literature on agentic correction loops (Ralph, SWE-Agent) and common CI retry policies.
Override
Heavy E2E (>5 min per run) → lower to 2. Fast unit-only → raise to 5.

8. max_test_minutes = 30

Date
2026-04-19
Context
max_test_retries bounds correction attempts but not wall-clock. A slow E2E suite (15 min × 4) burns 67 minutes before retry-exhausted abort.
Decision
Default 30, covering total session wall-clock. Independent of retries — whichever exhausts first wins. Outcome codes distinct: FAILED_AFTER_N_RETRIES vs FAILED_TIME_BUDGET_EXCEEDED. Value 0 forbidden.
Reason
Covers typical medium projects with 2x headroom. Forces heavy-E2E projects to consciously raise the budget or shrink the feature.

9. Layered execution: adaptive

Date
2026-04-19
Context
Planning doc §10 proposes layered execution (unit → integration → E2E) to save time; open question was whether it should be automatic or opt-in.
Decision
Adaptive: the context-builder detects layer signals (separate directories, markers, commands, scripts) in Phase 1 and activates layered execution automatically when signals are found. Flat execution when no signals. Override via future .relay.yaml.
Failure behavior
Failure at layer N skips subsequent layers. Each retry re-runs from layer 1.
Reason
Pure automatic risks false-positive abort decisions. Pure opt-in leaves benefit on the table. Adaptive: activate when signals are strong, report the reason, let the team override.

10. Interactivity boundary

Date
2026-04-19
Context
Original framing was "one prompt → PR." In practice, the highest-leverage moment to catch scope drift is during PRD authoring. Fixing those issues after implementation cascades rework across every stage.
Decision
The pipeline has an explicit interactivity boundary at PRD approval. PRD Writer + PRD Reviewer run the full 6-phase Q&A loop with the user. Plan, TDD, Implementer, Code Reviewer, Test Runner, Report + PR Creator run autonomously after PRD approval.
Reason
Minutes of dialog save hours or days of downstream rework. Net win on confidence and total time-to-PR.
See also
Interactivity boundary concept page.

11. PRD template forked from prp-core

Date
2026-04-19
Context
relay needs a canonical PRD shape that downstream agents can rely on, that humans can reason about, and that carries relay-specific contracts.
Decision
Fork prp-core's output template. Preserve the 6-phase Q&A flow. Add three mandatory extensions: Decision Gate evidence block as header, Acceptance Criteria (test scenarios) section, TDD routing note.
Reason
Reuse a proven structure; fork (not link) prevents upstream changes from silently altering relay's contract.

12. Command surface

Date
2026-04-19
Context
Goals: every stage individually invokable (testing, manual intervention); orchestrator composes them; naming clean; reuse prp-core familiarity where it exists.
Decision
Ship 12 commands + 1 placeholder. Writers produce artifacts; reviewers validate existing artifacts (including hand-edited). Orchestrator invokes them in fixed order and loops writer→reviewer pairs on CHANGES_REQUESTED.
See also
Commands reference for the full table.

13. .claude/settings.json policy

Date
2026-04-19
Context
Component C1 of Phase 2 requires .claude/settings.json to carry pre-approved permissions so the autonomous loop doesn't stall on permission prompts.
Decision
Narrow patterns, never broad. Allowlist patterns specific to detected commands. Catch-all patterns (Bash(*), Bash(git *), etc.) are forbidden.
Invariant denylist applied to every project. Destructive operations always require human confirmation (git push --force, git reset --hard, rm -rf outside .worktrees/, sudo, global installs, curl | sh, docker system prune, GitHub API mutations).
Generated by the context-builder from Phase 1 stack detection, not by the pipeline itself.
Exception
.claude/settings.json is setup config, not a pipeline artifact. Context-builder writes it once during *init (interactive). The autonomous pipeline only reads, never writes under .claude/.

14. Secret redaction policy

Date
2026-04-19
Context
Test Runner captures stdout/stderr into versioned reports that travel with the PR. Without redaction, any inadvertent env-var print leaks the secret.
Decision
Three-layer policy:
  1. Layer 1 (invariant defaults) — env name wildcards (*KEY*, *TOKEN*, *SECRET*, *PASSWORD*, *CREDENTIAL*, *AUTH*), exact-match URL env vars (DATABASE_URL, REDIS_URL, etc.), value regex for well-known secret formats (AWS, Stripe, GitHub PAT, JWT, PEM, OpenAI, Anthropic, Google).
  2. Layer 2 (per-project extensions) — PRPs/redaction-extensions.txt, created empty by context-builder.
  3. Layer 3 (documented non-redacted) — semi-sensitive values left alone by default (service-account non-key fields, git hashes).
URL handling
Connection strings replaced integrally with [REDACTED_URL]. No parse-and-partial — parsers fail on passwords with special characters.
See also
Redaction policy reference.

15. Plan filenames carry the source PRD phase number and slug

Date
2026-04-25
Context
The api-reference shorthand treated each feature as one plan, but plan-writer generates one plan per Implementation Phases row. A <feature>.plan.md name cannot express that 1-to-many relationship and collides whenever a PRD has more than one phase.
Decision
Plans are written to PRPs/plans/<feature>-phase-<N>-<slug>.plan.md. plan-reviewer's R8c validates the back-reference between the filename and the source PRD's row.
Reason
Per-phase plans match the unit of work the Implementer actually consumes, stay grep-friendly, and make orchestrator bookkeeping trivial — row N's PRP Plan cell points at exactly one plan.

16. R-COH-* rows are additive to plan-reviewer's rubric array

Date
2026-04-28
Context
The reviewer-coherence-layer appends R-COH-* rows to the same rubric[] array R1–R8 populate, but AC-10 of plan-authoring.prd.md read "exactly 8 objects… no extras", which would forbid them.
Decision
AC-10's "no extras" wording is relaxed to "R1–R8 always present, no duplicates among R1–R8, plus zero or more R-COH-* rows". Its no-short-circuit intent is preserved verbatim. The APPROVED PRD is not mutated; this entry is the operative contract.
Reason
AC-10's purpose was to forbid short-circuit, and that purpose is invariant to array length. The literal cap was a design-time choice for an 8-item rubric that predated the additive layer.

17. code-reviewer gains Task; its rubric array becomes additive too

Date
2026-04-28
Context
Phase 3 of reviewer-coherence-layer adds an R-COH-* layer to code-reviewer plus a read-only code-reviewer-semantic sub-agent invoked via Task. Two contracts in implementation-authoring.prd.md blocked it: D11's tools allowlist and AC-10's "no extras".
Decision
Task is added to code-reviewer's allowlist solely to invoke the read-only sub-agent; Edit remains absent forever and the sub-agent itself has no Bash and no Write. AC-10 is relaxed the same way as the plan-reviewer half. Arbitration mode is unchanged.
Reason
D11's purpose was read-only review philosophy, which bounded delegation to a read-only sub-agent extends rather than violates. Recording both relaxations in one entry keeps the related contract changes adjacent in the audit log.

18. Synthetic true positives satisfy the coherence layer's ≥1-TP gate

Date
2026-04-28
Context
The Phase 4 dogfood found relay's own APPROVED artifacts too well-authored to surface any real-world true positive at N=2–3, so AC-6's "≥1 TP per reviewer, real-world only" would have failed the release gate despite the layer demonstrably working on a synthetic fixture.
Decision
A reviewer with a dedicated synthetic regression fixture satisfies the ≥1-TP requirement from that fixture. A reviewer without one, whose real-world sample surfaces zero, has the requirement deferred to the cement-target reassess pass against ≥10 production runs. The ≤25% false-positive ceiling and the sample-size minimums are unchanged.
Reason
AC-6's intent was to prove the layer catches what it should without fabricating. A clean real-world corpus is a measurement-method limitation, not a layer-accuracy bug; synthetic fixtures are the correct validation path at MVP scale.

19. Implementer Bash is gated by the project allowlist, not a per-agent one

Date
2026-04-30
Context
The implementer needs Bash to run the plan's Validation Commands. A per-agent pattern allowlist would duplicate the project-level .claude/settings.json allowlist context-builder already generates.
Decision
The implementer declares Bash openly at the agent layer; the security gate is the project's .claude/settings.json allowlist and denylist. No second agent-level allowlist is added.
Reason
Reuses existing security plumbing and matches test-runner's precedent. A duplicate allowlist would diverge under maintenance and create silent gaps.

20. code-reviewer has no Edit tool

Date
2026-04-30
Context
plan-reviewer holds Edit because it flips plan status directly. code-reviewer must never mutate plan or PRD status — D8 makes the three post-approval mutations exclusively the command's responsibility.
Decision
code-reviewer's allowlist is Read, Write, Glob, Grep, Bash, BashOutput, Task, deliberately omitting Edit. Write is prompt-gated to its own code-review.jsonl.
Reason
Tool-level enforcement of the read-only philosophy. Even if the prompt drifted and instructed a status mutation, the absent tool makes it impossible — defense in depth between prompt and capability.

21. D8 post-approval mutations are best-effort atomic, with no write-ahead log

Date
2026-04-30
Context
/relay-implement performs three filesystem mutations on APPROVED: the plan status flip, the move to PRPs/plans/completed/, and the source PRD row flip. A transactional WAL was considered.
Decision
Best-effort atomic. Each mutation is attempted in order; the first failure captures partial state to halt.json with manual_recovery_steps and emits an actionable rollback note. Successful mutations are not rolled back — recovery is documented, not automatic.
Reason
A WAL adds replay logic and post-crash hooks disproportionate to three filesystem operations on one repo. If telemetry later shows recurrent partial failures, a follow-up decision can introduce one.

22. PRPs/plans/completed/ is the canonical archive path

Date
2026-04-30
Context
Upstream prp-core archives implemented plans under .claude/, which relay's no-.claude/-writes rule forbids because the permission guard would interrupt the autonomous loop on every archive.
Decision
Implemented plans are archived at PRPs/plans/completed/<basename>.plan.md by /relay-implement's Mutation b, with the directory created on demand.
Reason
Aligns with the PRPs-at-repo-root convention, preserves prp-core's archive semantics without the permission-prompt failure mode, and keeps the layout grep-friendly and version-controllable.

23. Per-attempt diff.patch artifacts under phase-<N>/attempts/<i>/

Date
2026-04-30
Context
The internal writer↔reviewer loop runs up to four attempts, and each attempt's cumulative diff must be auditable. The Test Runner's flat per-feature layout has no room for the per-phase tier the implementer needs.
Decision
After every attempt, the command writes git diff <base-commit> to PRPs/reports/<feature>/phase-<N>/attempts/<i>/diff.patch plus a record.json carrying attempt, verdict, files changed, validation and base commit.
Reason
Cumulative per-attempt diffs are the audit trail for bounded-retry behavior; the phase-<N>/ tier prevents collision when one feature ships through several invocations, while reusing the Test Runner's directory shape.

24. Plugin manifest version is bumped on every minor or major release cut

Date
2026-04-30
Context
Claude Code keys its plugin cache on the manifest version. The manifest sat frozen at 0.1.0 across nine changelog releases, so users who had already installed the plugin kept loading stale assets and never saw newly-shipped commands or agents.
Decision
The manifest version is kept in lock-step with the most recent versioned changelog release. Every minor or major bump must include a matching plugin.json bump in the same commit; a patch requires one only when it ships an asset under plugins/relay/.
Reason
Cache invalidation is keyed by version, not by git SHA or content hash. Without the bump the cache silently serves stale assets, and manual cache clears are a workaround rather than a contract.

25. Orchestrator dispatch is inline protocol adoption via Read

Date
2026-05-01
Context
/relay-execute must sequence five downstream command protocols without duplicating their logic. The alternative was replicating each protocol into a dedicated sub-agent.
Decision
The orchestrator reads each downstream command file at runtime and executes its protocol in the same conversation context. No sub-agents are spawned for the orchestration layer; each command still dispatches its own internal agents.
Reason
Replication would fork the protocol logic and create a maintenance liability on every downstream change. Inline adoption is the manual pattern relay's developer already follows, formalized as an autonomous loop, with zero new agents.

26. The source PRD's Implementation Phases table IS the state machine

Date
2026-05-01
Context
The orchestrator needs a phase-state representation that supports idempotent re-entry after a halt, without a separate state file.
Decision
Each row's Status cell is the authoritative phase state, re-read from the PRD on every invocation. No orchestrator-state.json is maintained.
Reason
The table is already canonical through plan-writer's back-fill discipline, so idempotency follows from re-reading it. An event-sourced durable-execution engine would be over-engineering at relay's scale.

27. Retry budgets compose: each command owns its own, the orchestrator adds two

Date
2026-05-01
Context
Composed commands each carry internal loop budgets. The orchestrator needs session-level bounds without overriding contracts whose retry semantics it does not know.
Decision
Downstream budgets are untouched. The orchestrator adds exactly two: max_plan_review_retries and max_orchestrator_minutes, both non-zero, with distinct HALT codes so the failing layer is unambiguous.
Reason
Per-stage budgets are authoritative within their stage. A session-level wall clock prevents runaway multi-hour runs independently of any one stage, and distinct codes make post-hoc debugging unambiguous.

28. The test pair is the only authorized creator of test files

Date
2026-05-06
Context
Three real-world halts showed that R-X strict — which blocks any test-file edit by the implementer — left no autonomous path forward when a feature's acceptance criteria required new test files.
Decision
The pair is the only authorized mechanism for creating test files, and R-X strict is preserved verbatim. The symmetry is bidirectional: the pair writes tests but never production code; the implementer writes production code but never tests.
Reason
R-X exists to stop the implementer passing tests by weakening them, and that purpose is invariant to who creates them. Introducing an authorized author preserves the invariant while unblocking the pipeline.
Superseded in part
The tdd: false self-skip half was superseded on 2026-07-10 (entry 41); the sole-author invariant was kept and extended.

29. relay-worktree architecture: path, primitive, bootstrap, gitignore, fallback

Date
2026-05-11
Context
Claude Code's native EnterWorktree hardcodes .claude/worktrees/ and auto-cleans on session exit, both of which conflict with relay's path convention and its pipeline lifecycle.
Decision
Worktrees live at .worktrees/<feature>/, created by shelling out to git worktree add, with idempotency detected via git worktree list --porcelain. Per-worktree setup is delegated to a project-owned scripts/worktree-bootstrap.sh or .ps1 run with a 60-second timeout, whose failure is non-fatal. context-builder *init auto-appends .worktrees/ to .gitignore, and a worktree-creation failure falls back to the cwd rather than halting.
Reason
The path avoids the .claude/ permission gate entirely and the lifecycle survives across invocations. Delegating setup to a project-owned script keeps relay out of Docker and dependency orchestration; the worktree is an optimization, not a correctness requirement, so its failure must not halt the pipeline.

30. Absent test framework is a silent self-skip, not an infra failure

Date
2026-05-12
Context
Two parallel dogfood sessions reached contradictory outcomes from identical inputs because /relay-test conflated "no framework configured by design" with "framework configured but infra broken", halting on both.
Decision
With test_frameworks: [] or a missing methodology file, /relay-test emits Test framework inactive and exits 0 — symmetric in shape and position to the test pair's own self-skip. A declared framework with broken infra still halts strictly. /relay-test-review inherits the skip through the natural absence of run.json.
Reason
Symmetry with the established methodology-keyed self-skip pattern, and the industry norm: pytest's exit code 5, Jest and Vitest's --passWithNoTests, GitLab's skipped-vs-failed distinction all separate "nothing to run" from "run and broke".

31. phase_type differentiates the rubric for scaffold phases

Date
2026-05-14
Context
Three consecutive orchestrator runs on a project scaffold failed R-COH-VALIDATE-FRAMEWORK-MISMATCH, which requires each VALIDATE command's first token to match a declared test framework. A config-only bootstrap has no application code to exercise; its legitimate validation is filesystem-oriented.
Decision
plan-writer populates a phase_type row in plan Metadata (scaffold, docs, feature), and the framework-mismatch check exempts the non-feature values.
Reason
The framework-first-token rule was calibrated for feature phases. Forcing a scaffold to satisfy it produces performative tests that exist only to pass the rubric rather than to validate the deliverable.

Decision
Description-only mode is a registered future capability and explicitly NOT implemented until a dedicated PRD is approved.
Reason
Registering the intent prevents agents from adding ad-hoc PRD-bypass logic without a formal design pass, while aligning the roadmap.
Superseded

33. PRD-less /relay-plan: shipped

Date
2026-06-16
Context
Entry 32 registered description-only mode as future work and forbade implementation before a dedicated PRD existed. That precondition was satisfied by relay-plan-prd-less-mode.prd.md.
Decision
Description mode is implemented across the planning and implementation chain: a non-.prd.md argument routes to a description-only entrypoint, producing a flat PRPs/plans/<slug>.plan.md with no PRD back-fill, and the downstream commands branch accordingly.
Reason
The stated precondition was met — the capability was designed, reviewed and approved rather than added ad hoc. This entry supersedes entry 32's "not yet implemented" framing.

34. Runnable worktree environments: registered future feature

Date
2026-05-15
Context
relay-worktree established the worktree as a file-isolation boundary and deferred everything that makes the application actually runnable inside it.
Decision
Evolving each worktree into a self-contained runnable environment is a registered future feature, not yet implemented.
Reason
Registering it prevents the deferrals from being silently re-decided inside bootstrap scripts or agent prompts, and names the full strategy surface so a future PRD starts from a scoped problem.

35. Pillar 3 is three commands: commit, PR, approve

Date
2026-05-18
Context
The original surface listed /relay-pr as a single command doing commit, push and PR creation in one shot.
Decision
Pillar 3 splits into /relay-commit (local only, no push), /relay-pr (push plus PR) and /relay-approve (merge plus cleanup plus docs sync).
Reason
Separating commit from push gives a local, reversible checkpoint before any network-visible action. git reset HEAD~1 is harmless; a prematurely-opened PR needs closing or a revert.

36. /relay-execute never commits or opens a PR

Date
2026-05-18
Context

69. Plan-review gating becomes materiality-aware: blocking vs advisory rubric classes

Date
2026-08-06
Context
Plan-review's first-attempt CHANGES_REQUESTED rate rose from 0.33 (April 2026) to 0.60 (August 2026) as the rubric grew from 8 to 27 distinct check ids. A cross-project audit of 353 verdicts over 193 plans in 7 repositories, classifying all 280 failing rubric rows individually, found only about 16 percent of them substantive — the gating function rejected a whole plan for any failure, material or not.
Decision
Every check id carries a statically declared class: blocking | advisory in a new partition table. blocking gates the verdict; advisory is evaluated, recorded and surfaced but never gates on its own. Failing rows carry the class in review.jsonl, an absent field reads as blocking, and a one-way escalation valve lets a single advisory finding be emitted as blocking with a justification. Newly added checks default to advisory.
Reason
A static per-check partition bounds LLM variance better than per-finding judged severity, mirroring GitHub code scanning's per-rule severity plus per-finding triage. Keeping the verdict binary rather than adding a third state means no orchestrator or state-machine change — advisories live entirely in the payload. The advisory-by-default rule inverts the incident-driven ratchet that grew the rubric while the failure rate climbed.

70. Retry convergence ratchet narrows blocking scope on re-review

Date
2026-08-07
Context
Across consecutive failing plan-review attempts, 33 rubric items newly failed against 31 that repeated — the loop had no fixed point. Decision

Per-section hashing applies the void check exactly where the writer's own revision contract promises nothing changed. The hashes are invoker-supplied because the reviewer's tool allowlist is a recorded capability contract, not something a bug fix widens.

75. Usage-metrics collection gets a 1% token budget

The third rule records a real circularity honestly rather than letting a plausible percentage become unfalsifiable.

The usage-metrics PRD's Success Metrics row, recorded in its review log as a human-authorized amendment. Reopens per-phase cost attribution, which had been excluded for lack of a join key a command may now afford to write. Both budgets are relay-level constants hardcoded in /relay-design-map and declared twice — in the command body and in the frontmatter description — following the restatement convention the design commands already use.
Reason
A budget declared only in prose is invisible to anyone reading the command's contract; declaring it in both places is what makes exhaustion behavior predictable rather than surprising. Metadata exhaustion is explicitly non-fatal: it records a truncation flag and continues.

78. Quota exhaustion is detected by error class, never by HTTP status

Date
2026-08-05
Decision
A terminal halt code FAILED_FIGMA_QUOTA_EXHAUSTED, distinct from the MCP-unavailable code. Detection is by error class and error string, never by HTTP status code.
Reason
Figma's MCP documentation names neither a 429 status nor a Retry-After header, so a status-code check would be guessing at a contract that does not exist. The observed exhaustion string is what the pipeline actually receives.

79. Response to quota exhaustion is abort-and-record; retry and backoff are rejected

Date
2026-08-05
Decision
On a quota-class error relay aborts and records. No sleep, no backoff, no retry rung. The partial call log is captured and the run halts with the named code.
Reason
A retry against an exhausted quota cannot succeed and spends the operator's remaining budget discovering that. Recording the partial log makes the next run cheaper; retrying makes it more expensive.

80. Cost preflight declares and asks; it never auto-refuses

Date
2026-08-05
Decision
Before any data call, the command probes whoami, reads seat and tier where exposed, and when the estimated cost exceeds the documented ceiling it declares the estimate and the ceiling and requires an explicit affirmative reply.
Reason
Declaring and asking keeps the human in the decision. Auto-refusing would substitute relay's estimate for the operator's judgment about their own quota, on data (seat and tier) the response does not always expose.

81. The evidence bundle is additive; only a complete scan may retire an entry

Date
2026-08-05
Decision
Evidence writes are additive — a partial run merges into the bundle rather than replacing it, and the call log is cumulative across runs. Each entry carries a last-seen scan generation, and only a scan reporting an untruncated inventory may retire one.
Reason
A partial run that replaced the bundle would silently destroy evidence a complete earlier run had gathered. Constraining retirement to complete scans keeps absence meaningful: an entry disappears because it is gone, not because the scan ran out of budget.

82. The run checkpoint lives outside the evidence directory

Date
2026-08-05
Decision
The checkpoint is written to a state directory deliberately outside the evidence directory, and exclusion from the agents' read surface is enforced by path rather than by a dotfile naming convention.
Reason
Both design-map agents are instructed to read every file under the evidence directory. A checkpoint inside it would be read as evidence. Enforcing by path rather than by a leading dot means the guarantee does not depend on every future reader honoring a naming habit.

83. Confidence downgrade under degraded enrichment is surgical, never wholesale

Date
2026-08-05
Decision
When a scan completes without enrichment, the confidence downgrade applies only to the mappings that enrichment would have informed — not to the map as a whole.
Reason
A wholesale downgrade discards verified mappings that had nothing to do with the degraded step, which both loses real information and trains the reader to ignore the confidence column.

84. Rubric-count assertions are re-derived from live headings, never hardcoded

Date
2026-08-05
Decision
The design-map and design-spec rubric-count assertions re-derive the count from a live grep of the rubric headings and fail loudly on drift, rather than asserting against a hardcoded literal.
Reason
A hardcoded count silently stops describing the rubric the moment a check is added, and the test keeps passing while the assertion has become meaningless. Deriving it makes the drift the failure.

85. Plugin-owned resources live in the plugin tree, not in docs/context

Date
2026-08-05
Decision
The plugin-owned resource templates live at plugins/relay/resources/, moved with git mv and leaving no stubs behind. Every citation uses the plugin-root placeholder form.
Reason
Plugin installation is a verbatim copy of the plugin directory with no include or exclude field, so a resource outside that tree reaches no installed user — the templates were unreachable for every install. Two validate checks now enforce the citation form and the resource's existence.

86. Usage metrics ships phases 1–4; phase 5 is deferred, not dropped

Date
2026-08-14
Context
The 2026-08-13 entry registered per-project usage metrics as a future capability and blocked implementation pending an approved PRD. That PRD was approved and driven through the orchestrator; four of its five phases are complete.
Decision
Records what exists: the codebook resource, a dependency-free materializer with a query subcommand, a tracked metrics directory with its two git control files, and the metrics-isolation check. The no-agent-reads rule is enforced twice, because it has two channels — a check over prompt text, and a -diff attribute over git plumbing, which no grep can see.
Reason
A registration entry never followed by a shipped entry leaves the repository claiming a capability is unbuilt long after it is in use. Recording the deferral reason is load-bearing rather than tidy: the orchestrator's halt artifact is gitignored, so without this entry the only durable statement of why phase 5 stopped would be a note inside the PRD.
Known gaps
The corpus holds one project, so the cross-project value proposition is untested against real data. The version axis was nominal until the 0.32.0 release cut gave it its first real transition.

87. The visual gate measures drift from the last approved capture, not distance from the Figma export

Date
2026-08-20
Context
Measured on a real project rather than reasoned about: three captures of one screen diffed against the same Figma reference scored 2.6035% and 2.4614% for two genuinely broken layouts and 2.5139% for the correct one — a negative separation no threshold can order, and unmoved by two masking strategies. Against a previous capture of the same frame the same three separated cleanly, over a 0.0000% noise floor.
Decision
A frame is diffed against its own last human-approved capture whenever one exists; that is the only basis whose number gates. With no approved capture the diff still runs against the Figma export but the frame is NO_BASELINE — advisory, never a pass — and degrades through the existing ladder as DEGRADED_NO_BASELINE. /relay-visual-approve promotes an approved capture to baseline through a feature-level registry of pointers. The pixelmatch tolerance becomes basis-dependent, and every diffed frame now writes an inspectable diff overlay that was previously computed and discarded.
Reason
The gate stops claiming to measure fidelity-to-design and starts measuring regression-since-approval, which is the only automatic number the mock-data reality supports; the human comparison against the design is what the human approval tier already provides. Re-tuning the threshold on the old basis was rejected on the measurement: with a negative separation, no value admits the correct render and rejects the broken ones.
Accepted cost
On a frame's first render the automatic gate contributes nothing, which is why an unbaselined frame degrades loudly instead of quietly passing.

88. Six field-reported pipeline defects fixed at the surface that produced them

Date
2026-08-20
Context
The same field session recorded six defects outside the visual gate: a capture script with no baseURL against Design Specs that write relative routes; an attempt-shaped record written into the run-level run.json, which one reviewer refused and another waved through; a plan rubric that checks an acceptance criterion exists but not that it is pertinent, and can deadlock against the coherence layer; a missing default paragraph that cost three retries per occurrence; a purity gate tripped by the sentinel comments naming the endpoint it hunts for; and a validation that matched a string in a manifest while the dependency was never installed.
Decision
Each fix lands at the surface that produced the defect, not the one that noticed it — the writer emits the paragraph by default, the runner is forbidden the artifact it corrupted, the rubric names the PRD as the cause of an impasse the plan cannot resolve locally, and the halt message names the shipped test pair it had been calling unshipped.
Reason
Each absence cost multiple autonomous retry cycles, which is the expensive kind of cheap bug. The rubric additions deliberately add no new check id: this repository derives rubric counts from live headings, so a new id would ripple through the arithmetic for a diagnostic better attached to the row it qualifies.

89. Test-formatting prevention runs at the command layer, never inside test-writer

Date
2026-08-26
Context
The test-formatting-prevention-preflight PRD (approved 2026-08-26) diagnosed a structural conflict: code-reviewer's R-X guard fails any test-glob match in the implementer's diff window outright, no grace period, while a formatter-enforcing project's mandatory Level 1 gate routinely finds an approved suite not formatter-clean — the test pair has never had a formatting step. A field arbitration burned a full TEST_CONTRACT_DISPUTE round (~100k tokens) to authorize a change later verified as semantically empty. Phase 2 of that PRD ("Prevention") ships the fix's first half: formatting on write.
Decision
Formatting ownership sits at the command layer (/relay-write-test), never inside the test-writer agent, whose tools allowlist stays Bash-free. The command's new Phase A.4 collects the suite's touched-file set from the just-written test manifest, discovers a formatter through a deterministic three-branch chain (formatter_cmd: in docs/context/methodology.md frontmatter → package.json's scripts.format → an explicitly recorded skip, never a fourth heuristic branch), and when found invokes it scoped to that exact touched-file list — never a glob, never the whole repo. The outcome is appended to the suite manifest as a ## Formatting Outcome section and surfaced as a second command-owned confirmation line; a failing or unconfigured formatter records and continues rather than halting. test-reviewer reads the section for informational awareness only — never a rubric input.
Reason
Granting Bash to test-writer so it could format its own output was rejected as widening the one deliberately Bash-free agent in the pipeline, mirroring why code-reviewer stays read-only. The command layer already owns dispatch sequencing between the Writer and test-reviewer, so it is the natural owner of a step that runs between them. Scoping the invocation to the explicit touched-file list is the direct mitigation for the PRD's formatter-over-reach risk. This entry covers Prevention only — the PRD's Phase 3 ("Preflight", normalizing test-file formatting before base_commit/diff_target capture) is separate, not-yet-shipped scope.

90. Test-file formatting is normalized before base_commit/diff_target capture

Date
2026-08-27
Context
Entry 89 (Prevention) covers suites born inside /relay-write-test but explicitly leaves two gaps: a suite already approved before Prevention shipped, and a suite whose test files are re-touched by a later formatter-config change. Both leave the <diff_target>..HEAD window R-X inspects containing formatting-only content.
Decision
/relay-implement's Phase A.1 preflight runs the same three-branch formatter-discovery chain as Prevention, scoped to the canonical test globs, and normalizes any unclean test file before base_commit/diff_target is captured. git diff --name-only <diff_target>..HEAD -- <test-globs> is empty for formatting-only content regardless of suite provenance, and formatting is never treated as TEST_CONTRACT_DISPUTE subject matter.
Reason
Prevention alone cannot reach a suite approved before it shipped or one that drifts from a later formatter-config change — only a baseline-time normalization closes both gaps without an R-X carve-out; running preflight before base_commit capture keeps R-X's text and enforcement byte-identical.

91. Reviewer findings are never self-executing test-edit authorization

Date
2026-08-27
Context
The 2026-08-26 arbitration on assistente-pessoal ruled that a code-review finding requesting a test change does not itself authorize the implementer to make that change — a ruling that, before this entry, lived only in the arbitration transcript.
Decision
code-reviewer.md's R-SEM section and implementer.md's dispute guidance both now state explicitly that a reviewer finding requesting a test-file change is not self-executing authorization to edit that test. TEST_CONTRACT_DISPUTE remains the sole channel for a genuine semantic contradiction with the PRD, even when the reviewer's own finding identified the need for a test change.
Reason
R-X strict already forbids the implementer from editing a test file directly; without this prose, an R-SEM row could be misread as an implicit exception because it comes from the reviewer rather than from the implementer's own judgment.

92. R-X clears a matched test path only through a script-computed executable-content hash

Date
2026-08-28
Context
A field review on assistente-pessoal hit both structural gaps in D17's guard at once. New tests written to evidence a review's own findings trip R-X and force an arbitration round whose outcome nobody contests, and DISPUTE_UPHELD_TEST_WRONG — which presumes an existing wrong assertion — had to be recorded as a "closest available fit". Worse, an edit that changed only a docstring and one describe() title, with every it() and expect() verified byte-identical, was flagged by R-X and then correctly REJECTED in arbitration, because with no assertion changed there is no test-vs-AC contradiction to arbitrate: the flag was simultaneously raised and unclearable.
Decision
R-X gains a Step X.2 executable-content equivalence check. After the unchanged file-level match, plugins/relay/scripts/executable-content-hash.mjs normalizes both revisions of each matched path — dropping comments, Python docstrings, and the test-title string literal of a describe/it/test/context/suite call — and hashes what remains; the path clears if and only if the hashes match, and both hashes are recorded verbatim in the verdict. Every other string literal and the callee survive into the hash, so a changed expected value or an added .skip never clears. Fail-closed throughout. Separately, arbitration gains a fourth outcome, DISPUTE_UPHELD_NEW_COVERAGE, for additions whose git diff --numstat shows zero deletions on every cited path.
Reason
R-X's content-blindness exists so that "my edit was harmless" is never self-certified, so the fix replaces self-certification with computation rather than relaxing the rule — the same shape as the 2026-08-03 R-COH-VALIDATE-FRAMEWORK-MISMATCH exemption, whose second condition makes the claim verifiable. Additive content is deliberately NOT cleared mechanically: a purely additive diff can still neuter existing tests through a new global hook, so it stays a judged outcome with a bounded precondition. Composes with entries 89 and 90 — formatting is still prevented upstream and is still never a dispute subject; Step X.2 is not a formatting carve-out.

93. Review agents never mutate the target working tree

Date
2026-08-28
Context
test-reviewer (B8) ran git stash on a live working tree to isolate a state for its RED legitimacy check. The intent is sound, but the tree held a developer's uncommitted work and an open phase, and a stash that is never popped — interrupted run, failed command, later halt — destroys it. Nothing in either reviewer's prose forbade it, and the recommended allowlist actively pre-authorized Bash(git stash*).
Decision
test-reviewer gains Hard constraint 2b and post-green-reviewer a working-tree rule: git stash, git stash pop, git checkout, git restore, git reset and git clean are forbidden, with no "temporarily" exception. A check that would need a tree state the agent cannot have degrades explicitly to passed: null with a reason naming what could not be re-verified. Bash(git stash*) is removed from resources/settings-allowlist.md, with its absence documented in place.
Reason
These agents are pointed at trees they do not own and cannot tell a live tree from a disposable one. The degraded path already exists and is designed for exactly this, so the fix costs no capability. Provisioning a dedicated worktree was rejected: it makes the stash safe where provisioned but leaves the unsafe behavior legal everywhere else, and the allowlist entry would still invite it.

94. Worktree base for a declared member is its Base cell, defaulting to current

Date
2026-09-01
Context
D11 resolved a worktree's base as --base → origin/main → origin/master → HEAD, so the current checkout was reached only when both remote defaults failed — which does not happen in any repository whose default branch exists on the remote. Reproduced on a repository checked out on dev with origin/main present: the worktree would be cut from main, silently.
Decision
For a member declared in a ## Repository topology section, that member's Base cell governs. current or an empty cell resolves to the member's checked-out HEAD; any other value is a named ref verified with git rev-parse --verify. The D11 chain is preserved verbatim for every project that declares no topology.
Reason
git worktree add's own documented behavior with no commit-ish is to branch from the current checkout, so D11 overrode git's default without recording why. Restoring current as the default for declared members restores git's semantics rather than inventing new ones. The same defect stays live for projects with no topology, deliberately: AC-1 of the source PRD guarantees their base resolution is unchanged, and honoring an approved criterion while recording the exposure was preferred to silently exceeding scope.

95. The base preflight is the fourth interactivity-boundary extension

Date
2026-09-01
Context
Three extensions were sanctioned before this one: PRD approval, the Design Spec pair, and /relay-visual-approve. The third used HALT-and-resume rather than dialogue because /relay-execute drives many phases across one long unattended run, and a synchronous dialogue only works inside a single unbroken interactive turn.
Decision
/relay-execute gains precondition P7 — Base preflight and confirmation: with a topology declared it resolves every editable member's base, emits one table, and requires ONE confirmation before the orchestration loop begins. A member whose base does not resolve halts before any confirmation and before any worktree exists. With no topology declared it is a complete no-op.
Reason
A precondition runs before the unattended run starts, in the turn the operator invoked — so it can dialogue while the loop stays prompt-free. That preserves the "no interactive prompts in the autonomous loop" anti-pattern rather than carving an exception into it. Confirming N members once is also strictly cheaper than N confirmations inside the loop, which is the shape the 2026-07-27 reasoning rules out.

Adding a new decision

When a new stable decision is made (typically during PRD authoring or during a review), follow this protocol:

  1. Edit docs/decisions.md in the plugin repo with a new entry using the template at the bottom of that file.
  2. Include date, context, decision, reason, and areas affected.
  3. If a counterpart anti-pattern exists (the inverse rule), add it to docs/anti-patterns.md as well.
  4. Update this page with a link to the new entry.
Decision Gate enforcement

Once a decision lands here, every subsequent agent reading this file via the Decision Gate must treat it as settled — no re-evaluation. That's what makes decisions stable.
