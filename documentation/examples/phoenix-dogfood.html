Phoenix dogfood — end-to-end walkthrough

On 2026-04-21 relay ran its Test Runner against a real target project (Phoenix) to prove the full loop — normalizer, classifier, auto-correction hand-off, post-green review, final report. This page walks through the artifacts that run produced, what they show, and what the run surfaced for future hardening.

Artifacts on disk

Everything described here lives under PRPs/reports/dogfood-2026-04-21/ in the Phoenix repo. Re-read the files alongside this page when debugging — they are the source of truth.

The target project

Phoenix is an internal service with a Python backend (FastAPI + pytest) and a TypeScript frontend (React + Vitest + Playwright E2E). It was selected as the first dogfood target because it exercises three traits relay had to support:

  • Mixed-framework test output (pytest JUnit XML + Playwright JUnit XML).
  • Docker Compose infra with a Postgres service (to exercise the db_unreachable subcause paths).
  • A non-trivial existing test suite (130+ tests) so "GREEN" actually means something.

The invocation

The dogfood run did not execute a full /relay-execute (there was no feature to build). Instead it exercised the Test Runner surface directly with a synthetic JUnit XML fixture to prove the normalizer + classifier + report generator chain end-to-end: 

/relay-test . --feature dogfood-2026-04-21 --fixture fixtures/mixed-pytest-playwright.xml

The fixture seeded a known set of pass/fail/skip counts so the expected verdict was predictable. The run produced a full set of Test Runner artifacts.

Issues the dogfood surfaced

A dogfood is only useful if it breaks things. Phoenix exposed four:

1. .gitignore pattern collision
Phoenix's pre-existing .gitignore had reports/ (unrooted), which swallowed PRPs/reports/ too. Fix: changed to /reports/ (root-anchored). Context-builder's *update mode now checks for this exact pattern and warns.
2. Oscillation detector edge case
The initial detector considered only filename sets. Phoenix had a scenario where two attempts touched the same file but edited non-overlapping hunks — a false positive. Fix: added content-reversion check (attempt N+1 must actually revert lines attempt N added). See Handling failures.
3. Redaction regex too permissive
The initial AWS key regex (AKIA[0-9A-Z]+) matched a benign constant in a Phoenix test fixture. Fix: tightened to AKIA[0-9A-Z]{16} and added a negative-lookahead for quoted test-only contexts. See Redaction policy.
4. Report > 50KB on high skip counts
Phoenix had 47 skipped tests in one exploratory branch, and the report bloated past 50KB when it listed each. Fix: report now paginates skip lists — inline first 20, links the rest to attempts/<N>/skipped.json.

What was deferred

Two scenarios the dogfood intentionally did not cover:

  • A real RETRY_NEEDED → GREEN cycle. Without /relay-implement, the loop still halts on the first RETRY_NEEDED. The dogfood used a pre-passing fixture. Phase 3 (Agents) of the overall rollout is where this gets proven end-to-end.
  • TDD track execution. Phoenix has tdd: false. A separate TDD-enabled target is queued for the next dogfood.

Lessons learned

  1. Synthetic fixtures are enough to validate the normalizer + classifier + report chain. A full end-to-end loop with real code changes would add signal but cost hours; the synthetic run is 60 seconds and catches structural issues.
  2. Redaction regexes need real-world input. No amount of unit testing on the redaction filter would have surfaced issue #3. Running on a repo with real fixture values did.
  3. Pre-existing conventions collide. Issue #1 was entirely a Phoenix-side .gitignore habit that relay never saw during design. Future target projects will hit other pre-existing conventions — context-builder's job is to detect and warn, not to silently fix.
  4. Write the dogfood artifacts into the plugin repo as a reference. Keeping PRPs/reports/dogfood-2026-04-21/ committed (both in Phoenix and mirrored in the plugin for doc reference) lets future contributors eyeball what a real run looks like without re-running.

Replaying the dogfood

If you want to re-run the dogfood locally against Phoenix (or a similar target):

  1. Clone the target and run *init with relay enabled.
  2. Validate the [INFERRED - VALIDATE] items the skill flags.
  3. Make sure Docker is up: docker ps returns successfully.
  4. make test-bootstrap to warm the images.
  5. /relay-test . --feature dogfood-$(date +%Y-%m-%d).
  6. Read PRPs/reports/dogfood-*/run.json and compare against this page's expected shape.

If anything doesn't match, the first place to look is the normalizer output (attempts/1/record.json → normalized). That's the junction between "framework did whatever it does" and "relay has a canonical view."
