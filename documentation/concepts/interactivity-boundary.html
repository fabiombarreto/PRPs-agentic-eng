The interactivity boundary

The single most important design choice in Pillar 2. This page explains what it is, why it exists, where the line runs, and how each stage behaves on each side of the line.

What it is

Pillar 2 (Implementation) is interactive up to PRD approval and autonomous from there on. This split is not an accident of implementation — it's the deliberate answer to a question every AI pipeline faces: at what moment does human judgment create the most value?

Interactive
PRD Writer runs a 6-phase Q&A with you. PRD Reviewer can loop back with you until the PRD is approved.
↓
Autonomous
Plan → Worktree → TDD (opt-in) → Implementer → Code Review → Test Runner → Post-green Review → PR. You come back to an open PR (or a clear abort).

Why the split exists

The cost of misunderstanding scales with how late it's caught

Consider a feature described ambiguously. The AI guesses one interpretation; the guess propagates through the plan, the tests, and the code. The cost to fix the ambiguity depends entirely on when you catch it:

at PRD stage
A 30-second clarifying question. You type two sentences. The PRD Writer revises. Total cost: minutes.
at plan stage
The plan is wrong; regenerate. The tests may also need rewriting. Cost: tens of minutes, plus your time context-switching back in.
at implementation stage
Code was written against the wrong understanding. Tests were written against the wrong understanding. Now both need revision. Cost: hours, and you have to re-review a bigger diff.
at test stage (green on wrong behavior)
Silent wrong. Ships. Caught by users or by QA weeks later. Cost: incident-level.

The interactivity boundary puts the human exactly where catching misunderstanding is cheapest — the PRD — and frees the human from being a scheduler for the rest of the stages where LLM judgment is reliable given a good PRD.

Interaction is expensive when it's cheap

The opposite failure mode is over-interacting. Asking the human to approve every intermediate step feels safe but wastes their attention on things where they can't actually add value — "Do you approve this Plan?" is answerable only by re-reading the PRD, and if the PRD was right, the Plan is almost certainly right too.

The AI asking unnecessary questions trains the human to stop paying attention, and then real questions get rubber-stamped too. The boundary design is: ask only where the answer unlocks information the AI actually needs. PRD stage qualifies. Plan-approval-step-N does not.

Where the line runs

On the interactive side

/relay-prd <description> runs the PRD Writer, which drives a six-phase Q&A based on the inherited prp-core flow:

  1. Initiate — confirm the AI understood the feature request.
  2. Foundation — who has this problem, what is it, why now, how do we measure success.
  3. Grounding — market + codebase research (via specialized sub-agents).
  4. Deep dive — vision, primary user, job to be done, non-users, constraints.
  5. Technical grounding — feasibility, existing infrastructure, risks.
  6. Decisions — MVP, must-haves, hypothesis, out-of-scope.

After the PRD is generated, the PRD Reviewer can loop back with you if it finds issues. The boundary closes only when the PRD status flips from DRAFT to APPROVED.

On the autonomous side

From PRD approval onward, /relay-execute <prd-path> runs the full chain without interaction. Each writer/reviewer pair loops internally on CHANGES_REQUESTED with a retry budget; each can also abort with a structured reason.

The pipeline interrupts the human only in two cases:

  • An agent exhausted its retries without converging. Example: the Test Runner hit max_test_retries with the same legitimate failure across attempts. The pipeline writes a diagnostic and stops; you decide whether to raise the budget, change the PRD, or fix manually.
  • An unrecoverable infra issue. Example: Docker not running, test framework missing, settings.json absent. The pipeline writes a clear abort reason; you fix the environment and re-run.

It does not interrupt for "approval" of intermediate outputs. Those are captured in the artifact tree (PRPs/reports/<feature>/) for post-run audit, not for mid-run approval.

Implications

The PRD becomes the contract

Because everything downstream is autonomous, the PRD has to be unambiguous enough that any downstream agent reading it can act correctly. That's why relay's PRD template (see docs/context/prd-template.md in the plugin repo) has a mandatory Acceptance Criteria section — concrete observable scenarios, phrased as "given X, when Y, then Z". When TDD is active, these scenarios become the input to the TDD Writer. When TDD is inactive, they still serve as the contract that the Implementer's tests verify.

Abort is a feature, not a failure

A good autonomous pipeline knows when to stop. relay's autonomous portion has six specific outcome codes the Test Runner can emit, each with a distinct recovery path:

GREEN
Suite passes. Proceeds to post-green review.
FAILED_AFTER_N_RETRIES
The correction loop exhausted max_test_retries. The failure is persistent — the human decides whether to dig in or revise the PRD.
FAILED_TIME_BUDGET_EXCEEDED
The run hit max_test_minutes while still making progress. Raise the budget or shrink the feature.
FAILED_OSCILLATION
The Implementer's fix for attempt N reverted lines the Implementer wrote in attempt K. Signals a PRD-level conflict: the code can't satisfy two requirements simultaneously.
FAILED_INFRA_UNRECOVERABLE
Docker down, declared framework not present in tree, settings.json absent when a framework is declared. Fix the environment and re-run. (Framework-not-declared-at-all is a graceful self-skip, not this halt — see below.)
skipped_no_test_framework (graceful, exit 0)
As of v0.11.1: when docs/context/methodology.md has test_frameworks: [] or the file is absent, /relay-test's Phase 0 gate emits Test framework inactive (test_frameworks: []). Skipping. and exits 0; orchestrator_run_log records the outcome. Symmetric with /relay-write-test's test_frameworks: [] self-skip; no human handoff required.

Each of these is a precise handoff back to the human with enough context to decide what to do. None of them require the human to understand why a specific test failed — just to decide which recovery applies.

Pillar 3 is explicitly triggered

The boundary applies within Pillar 2 (Implementation). Pillar 3 (Approval) is a separate concern with its own boundary: /relay-approve <pr> is triggered manually — you decided the PR is good. Once triggered, its internal steps (merge, Docs Updater, Docs Reviewer) run autonomously, but Pillar 3 as a whole is a conscious human act.

Consequences for the tooling

  • Two slash commands, not one. /relay-prd is interactive; /relay-execute is autonomous. Mixing them into one would collapse the boundary and invite confusion.
  • Approved PRD is a persisted artifact. Status APPROVED in the PRD file is the signal that the interactivity boundary has been crossed. A PRD with DRAFT cannot be fed to /relay-execute.
  • Every autonomous stage writes its artifact before handing off. Plans in PRPs/plans/, Test Runner records in PRPs/reports/. The audit trail is real, not abstract — you can reconstruct any run from disk.
  • No silent state. Every abort writes a reason. Every retry writes a record. If the human has to come back in, they find a full trail of what was attempted and why it stopped.

How this compares to other approaches

vs. fully interactive (prp-core and similar)

Every stage requires a command. The human is always the scheduler. Good for learning and auditing; bad for shipping volume.

vs. fully autonomous (AutoGPT-style)

The AI picks everything including the PRD. Great demos, but ambiguity compounds across stages and the human has no natural place to correct course. Risky in production.

relay's boundary

Human owns the "what" (PRD). AI owns the "how" (plan through PR). The hand-off happens once, at the natural choke point where a few minutes of dialog saves hours of downstream rework.
