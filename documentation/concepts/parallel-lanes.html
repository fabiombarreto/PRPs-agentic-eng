Parallel lanes

How /relay-execute runs independent chains of PRD phases at the same time: what a lane is, how it is derived, when concurrency is allowed, and how lanes come back together into one branch per repository.

What a lane is

A lane is one independent dependency chain of a PRD's Implementation Phases table. Lanes are derived from the Depends column, restricted to one repository, so a lane can never contradict a stated dependency. Phases inside a lane stay sequential; only separate lanes can run together.

Canonical source

The contract lives in plugins/relay/resources/lane-model.md; the decision record is in Decisions. The feature shipped in 0.38.0 (PRPs/prds/parallel-phase-execution.prd.md, seven phases).

The Parallel cell

The optional Parallel column of the phases table is an override in one direction only. A label such as lane:qa-run merges rows into a single sequential lane, which makes the run more serial. It can never split rows that Depends ties together, so a declaration that contradicts a dependency is refused by name instead of honored.

| # | Phase | Description | Status | Repo | Parallel | Depends | PRP Plan |
| 1 | Plan contract | ... | pending | - | lane:qa-run | - | - |
| 2 | Captured seeds | ... | pending | - | lane:qa-run | 1 | - |

Isolation: one worktree and branch per lane

Each lane gets its own worktree and branch, so two concurrent phases stop sharing a working tree and a git index. The worktree slug is the feature name when no lane is supplied and <feature>-lane-<k> when one is. With a single lane the slug is the feature name, so a non-parallel run is byte-identical to a run before lanes existed.

Lanes are read-only over shared state

A lane never writes the source PRD table or orchestrator-run.json. It returns a structured outcome and the orchestrator applies every row transition and audit write serially. The design removes the shared write instead of guarding it with a lock. A registry of shared-state writers in the lane contract is checked by the lane-state-writers validation check.

When concurrency is allowed

lane_runtime_safe
A declaration in the target project's docs/context/methodology.md. Only true permits concurrent lanes. false or an absent key forces serial execution. It is a declaration, never a scan.
max_lanes_in_flight
Session-level cap, default 3. Lanes beyond the cap queue; they are never dropped.
Serial fallback
The run is serial when the gate is false or absent, when fewer than two lanes exist, or when the cap is 1. Each reason is recorded by name in orchestrator-run.json, because "ran serially" without a cause is not auditable.
Why the gate defaults to false

Concurrent lanes share the machine. A project whose tests need a database, fixed ports or shared environment variables would collide. Making that safe automatically needs per-worktree environment provisioning, which is registered but not built (see Phase status).

Budgets and halts

Retry, oscillation and dispute budgets are initialized per phase and therefore apply per lane. The wall-clock budget is one shared session clock. When one lane halts, every other lane reaches a named terminal state, so a halt never leaves a lane undescribed.

Integration in Pillar 3

/relay-commit integrates a repository's lane branches into its feature/<feature> branch before any PR is opened, so a feature built across three lanes still produces one PR per repository. For a single lane the step is a documented no-op. A merge conflict between lanes is a finding about the PRD, not something to resolve silently. /relay-approve presents concurrent pending approvals for the operator to choose instead of refusing them.

Proof

A synthetic three-phase fixture runs both in parallel and serially, with per-lane and total durations recorded. A deliberately colliding fixture must be refused. The checks lane-contract, lane-worktree-parity, lane-state-writers and lane-fixture are listed in Validation checks.
