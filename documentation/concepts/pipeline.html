Pipeline stages

Each stage of Pillar 2 has a writer/reviewer contract, a specific input shape, a specific output shape, and a well-defined recovery path when it goes wrong. This page walks the pipeline stage by stage, what each one produces, and what happens if it fails.

Overview

Pillar 2 is a chain of writer/reviewer pairs plus a Test Runner. Each writer produces an artifact with status DRAFT. Each reviewer reads the artifact and flips it to APPROVED or returns CHANGES_REQUESTED with a concrete list. The orchestrator loops writer→reviewer until approved or the stage's retry budget is exhausted.

Why this pattern? Because every generative stage in an AI pipeline has the same risk profile: the LLM can produce something that looks right but violates a constraint (business rule, convention, known decision). The reviewer is a second pass specifically looking for those violations. The Decision Gate (see reference) makes the reviewer consult docs/decisions.md, docs/anti-patterns.md, and the relevant domain files before approving. It's the structural answer to "the AI just ignored our rules again."

1 — PRD (interactive)

Input
A short description of the feature.
Output
PRPs/prds/<feature>.prd.md with status APPROVED.
Writer
PRD Writer — runs the 6-phase Q&A (see interactivity boundary).
Reviewer
PRD Reviewer — runs a 7-item structural rubric (Acceptance Criteria are concrete scenarios, Decision Gate evidence is present, hypothesis is testable, out-of-scope is explicit) plus an additive R-COH-* coherence layer that catches intra-PRD contradictions: ACs that contradict each other, metrics decoupled from the hypothesis, references to non-existent sections / ACs / phases, and decisions that contradict the proposed solution. See the coherence layer reference.
Loop
Writer ↔ human ↔ Reviewer ↔ human, until approved. This is the only interactive stage.
Failure mode
User abandons the conversation. No artifact produced; no downstream effects.

2 — Plan

Input
Approved PRD.
Output
PRPs/plans/<feature>-phase-<N>-<slug>.plan.md with status APPROVED (one plan per actionable Implementation Phases row; codified in docs/decisions.md 2026-04-25).
Writer
Plan Writer — produces a phased implementation plan with explicit test cases.
Reviewer
Plan Reviewer — runs an 8-item structural rubric (phases concrete, dependencies declared, test scenarios map to AC, PRD↔plan traceability), each check statically declared blocking or advisory — only a blocking-classed failure gates the verdict, while an advisory-only outcome approves with the open advisories recorded and passed to the Implementer (docs/decisions.md 2026-08-06) — plus an additive R-COH-* coherence layer that catches intra-plan contradictions: tasks that don't reference any AC, Files-to-Change rows untouched by tasks, VALIDATE commands mismatching declared frameworks, Patterns-to-Mirror SOURCE paths missing, Mandatory Reading paths missing, plus K=5 LLM-detected drift between Summary / Solution Statement and Tasks. See the coherence layer reference.
Loop
Writer → Reviewer. CHANGES_REQUESTED loops back up to max_plan_review_retries.
Failure mode
Retry exhausted → pipeline halts with FAILED_PLAN_REVIEW_BUDGET_EXCEEDED; orchestrator writes reason to PRPs/reports/<feature>/orchestrator-run.json.

3 — Worktree

Input
Feature name (derived from approved plan).
Output
Git worktree at .worktrees/<feature>/ on branch feature/<name>.
No writer/reviewer
Deterministic infra step — single bash invocation, no LLM involved.
Failure mode
Branch already exists or worktree creation fails — halts loud. Does not overwrite existing worktrees silently.

4 — TDD track opt-in

Input
Approved plan + PRD Acceptance Criteria.
Output
Test files written to the worktree, plus a suite manifest. In test-first the suite is red — no production code yet; in test-after it is written against code that already passed review and is expected to be green.
Activation
Whenever docs/context/methodology.md declares a non-empty test_frameworks — in both modes. tdd: selects only the ordering (true before the Implementer, false after Code Review); it never decides whether the stage runs. Empty or missing frameworks is a silent skip. Details.
Writer
test-writer — derives tests from the PRD's Acceptance Criteria, never from imagined or already-written implementation. Owns the full create/update/delete lifecycle, with every non-create operation recorded in the manifest's ledger.
Reviewer
test-reviewer — flags tests that mirror implementation, trivial asserts, mocks that hide behavior, coverage gaps against AC, and independently re-validates every recorded lifecycle operation.
Failure mode
Same as Plan — retry exhausted halts the pipeline.

5 — Implementation

Input
Approved plan + TDD suite (if active).
Output
Implementation commits in the worktree.
Writer
Implementer — executes the plan; when TDD is active, writes code to make the red tests green.
Reviewer
Code Reviewer — checks against decisions.md, anti-patterns.md, relevant domain files via an 8-item three-layer rubric (R-S* structural, R-L* lint/type/build, R-SEM semantic, R-X test-modification guard — which clears a matched test path only through a script-computed executable-content hash recorded in the verdict, never on a reviewer’s own reading of the diff) plus an additive R-COH-* coherence layer with 4 deterministic intra-diff checks (dead imports, signature drift to callers within diff + 1-hop imports, config references missing, new files unregistered) and a bounded sub-agent dispatch to code-reviewer-semantic via Task for the K=5 LLM judgment pass (comment-vs-code, test-name-vs-assert, code-vs-task contradictions). Not a style reviewer; focuses on correctness + rule violations + intra-diff coherence. See the coherence layer reference.
Loop
Writer → Reviewer. CHANGES_REQUESTED loops back.
Failure mode
Retry exhausted halts with FAILED_AFTER_N_RETRIES; wall-clock exhaustion halts with FAILED_TIME_BUDGET_EXCEEDED; oscillation halts with FAILED_OSCILLATION_DETECTED; dispute cap halts with FAILED_DISPUTE_CAP_EXCEEDED; arbitration may resolve via DISPUTE_UPHELD_TEST_WRONG, DISPUTE_UPHELD_NEW_COVERAGE or DISPUTE_UPHELD_PRD_AMBIGUOUS; D8 atomicity violation surfaces PARTIAL_D8_FAILURE.

6 — Test Runner loop

Input
Worktree with code (and TDD suite, if active).
Output
Green test state + PRPs/reports/<feature>/run.json + per-attempt records.
Agent
test-runner — runs the suite, normalizes output, classifies failures (B3), returns verdict per attempt.
Loop body
Each attempt: run → classify → if GREEN exit; if RETRY_NEEDED invoke Implementer with feedback; if RETRY_FLAKY re-run without changes; if ABORT_INFRA attempt one recovery; if ABORT_TIME exit.
Budgets
max_test_retries = 3 + max_test_minutes = 30. First to exhaust wins.
Oscillation detection
If attempt N+1 reverts files from attempt N, halt with FAILED_OSCILLATION.
Details
Test Runner agent reference; /relay-test command reference.

7 — Post-green review

Input
Green test state (run.json with outcome: GREEN).
Output
PRPs/reports/<feature>/test-review.json with verdict.
Agent
post-green-reviewer — diffs changed test files against base branch; flags removed tests, added skips, trivial assertions, coverage drops > 5%.
Verdict
APPROVED → proceed. CHANGES_REQUESTED → orchestrator decides: loop back to Implementer or halt for human review.
Why it exists
Closes the "agent reaches green by deleting the failing test" attack surface. The anti-pattern is listed in anti-patterns.

8 — Report + PR

Input
Worktree with green tests and all reviews APPROVED.
Output
PR opened on GitHub with PRPs/reports/<feature>/final-report.md as the description.
Generator
plugins/relay/scripts/generate-final-report.mjs — reads run.json, test-review.json, and every attempts/<N>/record.json, produces AC-10 compliant Markdown.
PR command
gh pr create with the report embedded and appropriate labels.
Failure mode
If gh is unavailable or auth is broken, the report is still written to disk; the user gets an instruction to open the PR manually.

What composes these stages

Each stage is an individually invocable command (see Commands reference). The orchestrator /relay-execute <prd-path> invokes them in order and handles the loop-back logic for CHANGES_REQUESTED verdicts. You can also invoke any single stage manually — useful for:

  • Re-running a stage after a hand edit. Edit a plan, invoke /relay-plan-review to validate.
  • Debugging. If the Test Runner keeps aborting on infra, invoke /relay-test alone to narrow the problem.
  • Partial adoption. Projects using relay only for tests can invoke /relay-test without adopting the orchestrator.

Per-stage retry policy

Each writer/reviewer pair has its own retry budget, configurable independently. Defaults:

max_plan_review_retries
2 (orchestrator-level, v0.9.0; 0 forbidden). Caps the /relay-plan ↔ /relay-plan-review re-plan loop when the rubric returns CHANGES_REQUESTED. Exhaustion halts the orchestrator with FAILED_PLAN_REVIEW_BUDGET_EXCEEDED.
max_tdd_review_retries
2 (orchestrator-level, v0.10.0; 0 forbidden). Caps the /relay-write-test ↔ /relay-test-write-review loop in Phase A.3.5 of /relay-execute. Exhaustion halts with FAILED_TDD_REVIEW_BUDGET_EXCEEDED.
max_implement_retries
3 (implemented v0.8.0). Caps the internal writer↔reviewer loop inside /relay-implement (4 attempts total: 1 initial + 3 retries). Wall-clock companion: max_implement_minutes = 45; first-to-expire wins.
max_disputes_per_session
2 (implemented v0.8.0). Caps the TEST_CONTRACT_DISPUTE escape valve per /relay-implement session; exhaustion halts with FAILED_DISPUTE_CAP_EXCEEDED.
max_test_retries
3 (implemented).
max_test_minutes
30 (implemented).
max_orchestrator_minutes
240 (orchestrator-level, v0.9.0; 0 forbidden). Session-level wall-clock for the entire /relay-execute run; first to expire wins independently of per-stage budgets.

The reasoning behind the numbers is the same as for max_test_retries: fewer than 3 aborts on legitimate second-pass corrections; more than 3 wastes time on stuck loops that aren't converging. See the max_test_retries decision for the full reasoning. The per-stage budgets and the two orchestrator-level budgets compose per D3 of relay-execute.prd.md — each downstream command owns its internal loop budget; the orchestrator adds max_plan_review_retries + max_tdd_review_retries + max_orchestrator_minutes; first-to-expire wins makes the failing layer unambiguous in the audit log.
