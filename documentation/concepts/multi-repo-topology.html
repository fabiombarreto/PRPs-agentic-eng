Multi-repo workspaces

How relay addresses a project directory that holds several sibling git repositories: the three roots, the declared topology table, per-member context, and the named halts for topologies it cannot serve.

The three roots

Relay used to treat one variable as both the artifact plane and the code plane. A workspace separates them.

project_root
The directory a command is invoked from. Holds the single artifact plane: PRPs/prds/, PRPs/plans/, PRPs/reports/ and the workspace's own docs/.
context_root
A member's relay context: its CLAUDE.md and docs/, including decisions.md, anti-patterns.md, context/architecture.md and context/methodology.md.
repo_root
A member's git repository root. Worktrees are created at <repo_root>/.worktrees/<feature>/.

In most members context_root and repo_root are the same directory. They are not always, so both are expressed.

Canonical source

plugins/relay/resources/repository-topology.md holds the exact header, the parsing rules and the halt codes. The feature shipped in 0.37.0 (PRPs/prds/multi-repo-topology.prd.md, eight phases).

Declaration, never detection

A workspace declares its members in its own docs/context/architecture.md. Relay never scans for .git directories and never infers a role or a base. The section heading and the table header must match byte for byte.

## Repository topology

| Repo | Path | Git root | Role | Base |
|------|------|----------|------|------|
| spe-services | spe-services | - | editable | current |
| api-escola | api-escola | api-escola/apiescola | editable | origin/develop |
| spe-ui | spe-ui | - | reference-only | - |
Repo
The member's name, unique in the table. A phase names its target repository with it (the Repo column of the PRD phases table).
Path
The member's context_root, relative to project_root.
Git root
The member's repo_root; - means the same as Path.
Role
editable members may be written to and get a worktree. reference-only members are never written to and never get a worktree.
Base
The ref a worktree is created from. current or empty resolves to the member's checked-out commit.

Per-member context

A member's governing context is read from its own context_root, never from the workspace. There is no inheritance and no overlay: a member's own declaration wins outright. This matters because declarations diverge in practice; in one measured workspace, jest, vitest and pytest coexisted, tdd was true in half the members and false in the rest, and figma_track held in exactly one.

Compatibility clause

When the ## Repository topology section is absent the project is single-repo. All three roots collapse to the working directory, nothing is emitted, and every stage behaves exactly as it did before the contract existed. No existing project needs to migrate. This repository is single-repo and declares no such section.

Named halts

Every unserviceable topology stops the run before any phase work, with an actionable message. None degrades to "proceed anyway".

FAILED_TOPOLOGY_MALFORMED_ROW
Wrong cell count, empty Repo or Path, or an unrecognized Role.
FAILED_TOPOLOGY_PATH_UNRESOLVED
A declared Path or Git root is not an existing directory.
FAILED_TOPOLOGY_NOT_A_GIT_REPO
A resolved repo_root is not a git repository.
FAILED_TOPOLOGY_ORPHANED_GITLINK
A member is a mode-160000 gitlink with no .gitmodules entry; a worktree of the parent would come up empty.
FAILED_TOPOLOGY_BASE_UNRESOLVED
A declared Base does not resolve in that member.
FAILED_TOPOLOGY_REFERENCE_ONLY_TARGET
A phase targets a reference-only member.

Who consumes it

/relay-execute reads the declaration at precondition P6. Worktrees, branches and PRs are then created per editable member. Combined with parallel lanes, the lane dimension composes with the per-repository one rather than replacing it. The topology-contract check keeps the header consistent across consumers.
