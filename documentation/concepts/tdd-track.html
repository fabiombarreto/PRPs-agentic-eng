TDD opt-in

relay has a dedicated TDD track that writes tests before production code. It's opt-in per project, activated only by an explicit declaration. This page explains why TDD is a first-class concept in relay, how projects enable it, and what the track actually does.

Why TDD is a first-class concept

When an AI writes the tests and the code in the same session, it almost always writes them together — the tests end up mirroring the implementation rather than driving it. The result looks like TDD but provides none of its benefits: tests that pass trivially, don't exercise real contracts, and don't catch regressions.

Real TDD requires two properties:

  1. Tests exist before the implementation. The suite is red at the start. Passing it means satisfying a contract, not repeating what was just written.
  2. Tests derive from requirements, not from imagined code. They name behaviors, not method signatures. it('rejects expired tokens'), not it('calls validateToken()').

relay's TDD track enforces both structurally: it has a dedicated TDD Writer that reads the PRD's Acceptance Criteria and produces tests before the Implementer runs, and a TDD Reviewer that refuses to approve tests that leak implementation details, use trivial asserts, or over-mock.

How to activate

Every project initialized by the context-builder skill gets a docs/context/methodology.md file. The default state is TDD off: 

---
tdd: false
tdd_evidence: null
test_frameworks:
  - pytest
  - vitest
  - playwright
---

# Methodology

## TDD (Test-Driven Development)

Current state: **not declared** (default).

The TDD track (agents B7 and B8) activates only when `tdd: true` in
the frontmatter above. Heuristics MUST NOT flip this value — only a
human edit or an explicit user declaration during `*init` can.

### Observed signals

[The context-builder populates this with signals it found during the
 scan — CI coverage-first rules, test-before-code commit patterns,
 mentions in CONTRIBUTING.md. None of these activate TDD on their own.]

To activate the TDD track:

  1. Confirm with the team that TDD is the project's actual methodology.
  2. Change tdd: false to tdd: true.
  3. Set tdd_evidence to "user-declared" or a path to a CONTRIBUTING doc that records the choice.
  4. Commit the change.

That's it. Next time /relay-execute runs, the TDD track activates automatically — Writer and Reviewer slot in between Plan Reviewer and Implementer.

Why only explicit activation?

Activating TDD based on heuristics (test folder exists, high coverage, etc.) is explicitly forbidden. The reason is in anti-patterns: many projects have tests without practicing TDD. Turning on the TDD track for them would surprise the team — suddenly every feature gets a red-first test suite that doesn't match their actual workflow.

The anti-pattern entry is reproduced here because it's central to the concept:

Anti-pattern: activating the TDD track by heuristic

What it is: Inferring that a project "does TDD" from the existence of a test folder, a high test count, or a CI job, and enabling B7/B8 automatically.

Why it's forbidden: TDD is a methodology, not a side effect of having tests. Activating it silently surprises teams that test a lot without practicing TDD.

What to do instead: Read docs/context/methodology.md and check exactly one key: tdd: true | false. No declaration file, tdd: false, or missing frontmatter → skip B7/B8 silently.

What happens when TDD is active

With tdd: true, the Pillar 2 pipeline gains two stages between Plan Review and Implementation:

stage 2
Plan Writer + Plan Reviewer (as usual)
↓
stage 3
Worktree creation
↓
stage 4 (TDD)
TDD Writer — reads PRD AC + plan, produces red test suite. Commits tests only — never production code.
↓
stage 4 (TDD)
TDD Reviewer — validates the suite against five known pitfalls (implementation leaks, trivial asserts, mock abuse, AC coverage, test duplication). Flips to APPROVED.
↓
stage 5
Implementer — writes production code until the red suite turns green. The suite is the contract, not a checklist of things that happen to fail.

The Test Runner downstream respects the TDD contract: B4 (auto-correction loop) explicitly refuses to weaken tests that the TDD Reviewer approved, and B5 (post-green review) uses the TDD suite as the baseline for "tests were not removed."

What doesn't change when TDD is active

  • Acceptance Criteria remain the source of truth. The PRD's AC section is the contract whether TDD is on or off. When TDD is off, the Implementer writes tests alongside the code; when on, the TDD Writer derives tests from AC before the Implementer runs.
  • The Test Runner doesn't care. It runs the suite, classifies failures, and auto-corrects. It doesn't know whether the suite was written by a TDD Writer or an Implementer; it just runs what's there.
  • The rest of the pipeline is unchanged. Post-green review, report generation, PR creation — all behave the same.

Graceful degradation

Three scenarios matter:

methodology.md missing
Treated as tdd: false. TDD track silently skipped. A note in the final report flags "methodology.md not found — consider re-running *update."
methodology.md has tdd: true but no test framework detected
Hard abort with actionable message. TDD without a test framework is a misconfiguration; the user must either install a test framework or flip tdd: false.
methodology.md has tdd: true and TDD Reviewer exhausts retries
The pipeline halts for human review. The partially-written test suite stays in the worktree for manual completion or discard.
