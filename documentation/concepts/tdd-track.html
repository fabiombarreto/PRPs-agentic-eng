The test pair

relay has a dedicated writer/reviewer pair that owns every test file in the pipeline. It runs in two orderings — test-first (TDD), where the suite is written before production code, and test-after, where it is written against code that already exists and passed review. This page explains why the pair exists, what activates it, what it does in each mode, and what it deliberately will not do.

This page was reframed on 2026-08-06

It previously described a "TDD track" that activated only on tdd: true and skipped otherwise. That model was superseded on 2026-07-10: activation is now keyed on a declared test framework and runs in both orderings, with tdd: selecting only which one. See decision 41. The page path is unchanged so existing links keep resolving.

Why the pair is a first-class concept

When an AI writes the tests and the code in the same session, it almost always writes them together — the tests end up mirroring the implementation rather than driving it. The result looks like TDD but provides none of its benefits: tests that pass trivially, don't exercise real contracts, and don't catch regressions.

Tests that carry weight require two properties:

  1. They are written by someone other than the author of the code. That separation is what stops a suite from restating the implementation. In test-first it is enforced by ordering; in test-after it is enforced by authorship — the pair writes the tests, never the Implementer.
  2. They derive from requirements, not from imagined or observed code. They name behaviors, not method signatures. it('rejects expired tokens'), not it('calls validateToken()').

relay enforces both structurally with test-writer, which reads the PRD's Acceptance Criteria and authors the suite, and test-reviewer, which refuses to approve tests that leak implementation details, use trivial asserts, or over-mock. The separation is bidirectional and enforced at the tool level: the pair writes tests but never production code, and the Implementer writes production code but never tests — the universal R-X guard rejects any test-file change in an Implementer's diff.

Test-after sharpens the first risk rather than removing it. When the code already exists, a suite can mirror what was just written just as easily as it can mirror an imagined design. That is precisely why authorship, not merely ordering, is the load-bearing rule.

How to activate

Every project initialized by the context-builder skill gets a docs/context/methodology.md file. Two keys govern the pair, and they answer different questions:

test_frameworks
The activation gate, and the only one. A non-empty list runs the pair; [] or a missing file skips it silently. This is the key that decides whether the pair runs at all.
tdd
The ordering selector. true is test-first, false is test-after. It never decides whether the pair runs — only when.

The default state after *init is no framework declared, so the pair is off: 

---
tdd: false
tdd_evidence: null
test_frameworks: []
---

# Methodology

## TDD (Test-Driven Development)

Current state: **inactive** (no framework declared).

The test pair (`test-writer` + `test-reviewer`) activates when
`test_frameworks` above is non-empty — in BOTH modes. The `tdd:`
value only selects ORDERING: `tdd: true` = test-first (the pair
authors before the Implementer), `tdd: false` = test-after (the pair
authors after the Implementer + Code Review). Heuristics MUST NOT
flip these values — only a human edit or an explicit declaration can.

To activate the pair:

  1. Add the project's real test framework(s) to test_frameworks — for example ["pytest"] or ["node:test"]. The pair needs a declared framework because it cannot author a test without knowing the idiom.
  2. Decide the ordering. Leave tdd: false for test-after, the dominant mode outside strict-TDD shops; set tdd: true only if the team genuinely practices test-first.
  3. If you set tdd: true, set tdd_evidence to "user-declared" or a path to a doc recording the choice.
  4. Commit the change.

That is it. On the next /relay-execute run the pair activates automatically, slotting in before the Implementer in test-first and after Code Review in test-after.

Declaring a framework is what turns the pair on

Setting tdd: false does not disable the pair. This repository is the worked example: it declares tdd: false and test_frameworks: ["node:test"], and the pair authors and maintains every one of its test files in test-after mode. To switch the pair off entirely, empty test_frameworks.

Why only explicit activation?

Inferring either key from the codebase — a test folder exists, coverage is high, CI runs a suite — is explicitly forbidden. The reason is in anti-patterns: having tests is not the same as wanting relay to author them, and practising test-first is not something a folder layout can reveal. Silent activation surprises teams, and a guessed ordering is worse than no ordering.

The anti-pattern entry is reproduced here because it's central to the concept:

Anti-pattern: activating the test pair by heuristic

What it is: Inferring that a project wants relay-authored tests from the existence of a test folder, a high test count, or a CI job — or inferring the tdd: value the same way.

Why it's forbidden: Activation is a methodology declaration, not a side effect of having tests. And tdd: selects ordering, which must not be guessed.

What to do instead: Read docs/context/methodology.md. The single activation gate is a declared framework: a non-empty test_frameworks runs the pair in both modes; test_frameworks: [] or missing frontmatter skips it silently. tdd: only selects ordering, never whether the pair runs.

What happens when the pair is active

The pair contributes the same two stages in both modes; only their position moves. With tdd: true they sit between Plan Review and Implementation, so the Implementer inherits a red suite as its contract:

stage 2
Plan Writer + Plan Reviewer (as usual)
↓
stage 3
Worktree creation
↓
stage 4 (pair)
test-writer — reads PRD AC + plan, produces a red test suite. Authors tests only — never production code.
↓
stage 4 (pair)
test-reviewer — validates the suite against five pitfalls (implementation leaks, trivial asserts, mock abuse, AC coverage, duplication) plus R-RED-LEGITIMATE and the lifecycle-ledger check. Flips the manifest to APPROVED.
↓
stage 5
Implementer — writes production code until the red suite turns green. The suite is the contract, not a checklist of things that happen to fail.

With tdd: false the same two stages run after the Implementer and Code Review, against code that already exists. The reviewer's mode-selected legitimacy check flips accordingly — R-GREEN-LEGITIMATE instead of R-RED-LEGITIMATE, because a suite authored against shipped code is expected to be green, and a red result there signals an implementation bug or a bad test rather than a healthy starting point.

The lifecycle ledger

The pair owns the full test-file lifecycle, not just creation. Alongside writing new tests it may update a test whose contract changed under a live criterion, or retire one that is obsolete (its behavior is gone from the in-scope criteria) or redundant (a proven duplicate naming its survivor). Every non-create operation is recorded in the suite manifest's lifecycle ledger with a classification and a justification, and test-reviewer's R-LIFECYCLE-LEGITIMATE re-validates each one independently.

The ledger is a positive authorization signal, never a blanket exemption. The post-green reviewer downstream accepts a removal or a skip only when it matches an APPROVED ledger entry; an unmatched removal — and every removal when no manifest exists — still blocks. The auto-correction loop refuses to weaken tests the pair approved, and neither it nor the Implementer authors any test-file change at all.

Foundation phases (compiled languages)

Test-first has a structural blind spot: the very first phase of a feature often creates the seam — the entities, repositories, resolvers, interfaces, schema types, and migrations that every later phase builds on. A test for that phase has nowhere to stand. It either references types that do not exist yet, or it invents the production signatures the Writer is forbidden to guess.

In an interpreted language this is survivable: a reference to a not-yet-created symbol fails at run time, one test at a time. In a compiled language (Java/JUnit, Go, C#/.NET) it is fatal — a reference to a missing type breaks compilation of the entire test source set, so no test can run at all. The result was a dead end: test-writer returned AMBIGUOUS for the seam phase's Acceptance Criteria even though those ACs were perfectly precise. The problem was never AC quality; it was ordering.

relay resolves this with a plan-metadata value: phase_type: foundation.

What it marks
A phase that creates the seam later phases depend on, where the phase itself introduces the types its ACs name. Distinct from scaffold (config-only, no application source) and from feature (exercises existing types).
What it does
The TDD track skips test-first for that phase. /relay-write-test self-skips at precondition P5; /relay-execute logs skipped_foundation_phase and proceeds straight to the Implementer, which materializes the seam. The feature phases that follow run fully test-first against the now-existing types.
How it's set
Inferred conservatively by the Plan Writer and the Plan Reviewer's Phase 0 pre-pass, and honored when a human annotates it explicitly. Its legitimate validation is a compile/build/migration check (mvn test-compile, go build, dotnet build), so it is also exempt from the framework-mismatch coherence check.
Red-by-design is first-class in compiled languages

For the feature phases that follow a foundation phase, test-reviewer's red-legitimacy check applies a seam-set discriminator: a compile error whose unresolved symbols are all in the plan's ## Files to Change CREATE/UPDATE set is a legitimate red-by-design failure — the test drives a production symbol that does not exist yet. Only unresolved symbols outside that set (typos, wrong imports, missing dependencies) or a pure test-source syntax error count as broken setup.

If a foundation phase is misclassified

When test-writer returns AMBIGUOUS for ACs that are clearly written (they have Given/When/Then), the phase is usually a foundation phase that was tagged feature. The fix is not to rewrite the PRD — it is to mark the plan phase_type: foundation and re-run. /relay-execute's halt message now surfaces this recovery path explicitly.

What doesn't change between the two modes

  • Acceptance Criteria remain the source of truth. The PRD's AC section is the contract in both orderings. The pair walks every in-scope criterion either way; only the moment it does so moves.
  • The Implementer never writes tests. This holds in both modes and is not a test-first-only rule. R-X rejects any test-file change in an Implementer's diff, so a test-after project's tests come from the pair, not from the Implementer writing them alongside the code.
  • The Test Runner doesn't care. It runs the suite, classifies failures, and auto-corrects. It does not know which mode produced the suite; it just runs what is there.
  • The rest of the pipeline is unchanged. Post-green review, report generation, PR creation — all behave the same.

Graceful degradation

Three scenarios matter:

methodology.md missing
Treated as no declared framework. The pair self-skips silently, and a note in the final report flags "methodology.md not found — consider re-running *update."
test_frameworks: [], whatever tdd: says
The pair self-skips silently and exits 0. This is the sole self-skip of the gate: with no declared framework there is no idiom to author a test in, so the skip is correct rather than a misconfiguration. It is not an abort, and tdd: true does not change it.
test-reviewer exhausts its retry budget
The pipeline halts for human review. The partially-written suite stays in the worktree for manual completion or discard.
