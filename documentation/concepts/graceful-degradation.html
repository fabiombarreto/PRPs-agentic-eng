Graceful degradation

Every component in relay detects its own preconditions at the start of its run. Missing infrastructure, absent dependencies, or unsupported configurations result in a clear skip with a reason — never a silent failure, never a crash in the middle.

The principle

relay is a plugin that runs against real projects with real infrastructure maturity gradients. Some projects have Docker, some don't. Some have full E2E suites, some have unit only. Some declare TDD, most don't. A pipeline that assumes the ideal scenario and crashes when reality doesn't match is useless for adoption.

The answer is graceful degradation: every stage detects what's available, opts in only what's supported, and reports skips explicitly.

Two invariants

The pipeline never fails because an optional capability is missing. It may skip a stage, but it does not abort.

The pipeline fails loud when a mandatory capability is missing. Missing Python interpreter for a Django project is not "graceful" — it's an actionable misconfiguration the user needs to fix.

Scenarios

The planning document enumerates the scenarios relay must handle. Each has a specific expected behavior, listed below.

Project without Docker

What's missing
docker CLI or Docker daemon not reachable.
What relay does
Infra components A1–A4 are skipped. The Test Runner falls back to running tests in the local environment. A warning is added to run.json: degraded: true, reason: "contamination_between_runs".
What that means for the user
Tests still run; results are still collected; the final report includes a note that between-run isolation wasn't enforced. If a test is flaky because of leftover state, the report flags it.

Project without E2E tests

What's missing
No Playwright, Cypress, or equivalent detected.
What relay does
Only the unit/integration layers of the test suite run. B5 (post-green review) reduces its severity — it can't verify E2E coverage didn't drop if there's no E2E to drop from.
What that means for the user
Features ship without E2E validation. The final report lists "E2E not available" as a known limitation.

Project without any tests at all

What's missing
No test framework detected anywhere.
What relay does
Test Runner is skipped entirely. The orchestrator proceeds to PR with a "not verified by tests" badge prominently on the report.
What that means for the user
The PR opens but with an explicit warning that nothing was verified. The team decides whether to merge without tests (their call, not relay's).
If TDD is declared
TDD Writer (B7) still runs — it produces the initial suite from AC. That's the other direction of test-first; relay can bootstrap tests for a project that doesn't have any, if the team declared TDD.

TDD declared but no test framework installed

What's missing
methodology.md has tdd: true but no test framework is detected (no pytest, no Vitest, no Playwright, nothing).
What relay does
Hard abort. TDD without a test framework is a misconfiguration, not a graceful degradation case. The error message is actionable: "TDD declared but no test framework detected. Either install a test framework and re-run the context-builder, or flip tdd: false in methodology.md."
Why not skip?
Because silently skipping would let the team think TDD is active when it's not. That would surprise them the first time a PR merges with no tests after they'd written a PRD expecting the TDD track.

Project doesn't declare TDD

What's missing
methodology.md has tdd: false or is absent.
What relay does
TDD Writer and TDD Reviewer are silently skipped. No warning emitted — this is the expected state for non-TDD projects, not a degradation.

Project without GitHub access

What's missing
gh CLI not installed or not authenticated.
What relay does
C2 (hooks) and C3 (worktree interface) continue working. The final /relay-pr step is replaced by instructions in the final report: "Run gh pr create --title '...' --body-file PRPs/reports/<feature>/final-report.md manually to open the PR."
What that means for the user
The pipeline produced everything except the final PR creation. The user opens it by hand.

Project without the pre-approved permissions

What's missing
.claude/settings.json absent or incomplete.
What relay does
The plugin still runs, but the user is interrupted on every bash command with a permission prompt. This is documented in the plugin README as a configuration requirement for autonomous use, not a graceful-degradation case.
Fix
Run the context-builder skill in *update mode to regenerate settings.json with the correct allowlist.

Project hasn't been through the context-builder

What's missing
docs/context/ doesn't exist. No methodology.md. No settings.json.
What relay does
Warns that the project hasn't been initialized. Attempts a heuristic stack detection (looking at package.json, pyproject.toml, etc.). Quality of failure classification and redaction degrades significantly — the heuristic surface is smaller than what the context-builder produces.
TDD heuristic activation
Even under this fallback, TDD is never activated heuristically. tdd: false is always assumed when methodology.md is absent.
Strong recommendation
Run the context-builder first. The quality of the autonomous run depends on the quality of the context tree.

MCP Context7 unavailable

What's missing
The Context7 MCP server isn't registered in the Claude Code session.
What relay does
During context-builder init, a warning is printed: "⚠️ Context7 MCP not available. /libs will not be generated." The SKIP_LIBS=true flag is set and Phase 4 (generate docs/libs/) is skipped. All other phases run normally.
What that means
Agents still have the target project's own context but lack deep library docs. Reviewers may be less effective at catching library-specific misuse. Can be remediated by running *libs mode once Context7 is available.

Reporting degradation

Every degradation gets surfaced in two places:

  1. The Final Report footer (final-report.md) has a dedicated "Skipped components" section listing every skipped stage with its reason.
  2. The run.json skipped[] field carries machine-readable entries with component and reason keys. Downstream tooling reads this rather than parsing the report.

Example from a phoenix run with no Docker:

{
  "skipped": [
    {
      "component": "A1-A4 isolated test env",
      "reason": "docker_not_running",
      "risk": "contamination between runs; flakiness may be misattributed"
    },
    {
      "component": "B7 TDD Writer",
      "reason": "tdd: false in methodology.md",
      "risk": null
    }
  ]
}

Why this is the design

The alternative — crash on any missing capability — fails in every adoption scenario. A team evaluating relay will try it against whatever they have right now: maybe no Docker, maybe no E2E, maybe no GitHub integration. If the plugin blows up on the first missing piece, they conclude relay doesn't work and move on. With graceful degradation, they get a partial run and a clear report of what was skipped and why. They can then decide: is this capability gap worth closing, or is this run good enough?

Crucially, graceful degradation is not graceful silence. Every skip is reported. The team always knows what wasn't verified. That's what keeps the pipeline honest.
