The three pillars

relay's pipeline is organized in three pillars. Each has a distinct responsibility, a clear input and output, and a clear handoff to the next. This page explains what each pillar does and why the split exists.

Overview

Pillar 1
Initialization — document the project for the AI so agents can operate autonomously. Produces docs/, PRPs/redaction-extensions.txt, .claude/settings.json, and methodology.md.
↓
Pillar 2
Implementation — take a feature from PRD to opened PR. Interactive up to PRD approval; autonomous from there.
↓
Pillar 3
Approval — merge the PR, clean up the branch and worktree, update docs/ to reflect what was built, and flag ambiguous new rules for human confirmation.

Pillar 1 — Initialization

Purpose

Before relay can run a pipeline against a project, the project needs to be documented for the AI. Stack, conventions, domain rules, past decisions, methodology choices, and permitted commands — all of it has to be in a predictable place where every agent can find it.

Pillar 1 delivers that documentation via a single skill: context-builder. The skill scans the project, infers what it can, and produces the canonical file layout the rest of relay depends on.

What it produces

# in the target project's repository
CLAUDE.md                                 # Tier 1: essentials, always loaded
docs/
├── KNOWLEDGE_BASE.md                     # Tier 2: TOC pointing at everything below
├── decision-gate.md                      # mandatory AI control mechanism
├── decisions.md                          # stable decisions the AI must not re-evaluate
├── anti-patterns.md                      # patterns the AI must not implement
├── context/
│   ├── architecture.md                   # stack, folder structure, inviolable rules
│   ├── conventions.md                    # naming, file layout, imports
│   ├── integrations.md                   # external services (no secret values)
│   ├── constraints.md                    # runtime versions, tech debt, what NOT to do
│   └── methodology.md                    # methodology frontmatter (test pair, docs sync)
├── domain/
│   ├── glossary.md                       # business terms
│   ├── flows.md                          # main user journeys
│   └── areas/                            # one file per business area
└── libs/                                 # lib docs fetched via Context7 MCP

.claude/
└── settings.json                         # permission allowlist + invariant denylist

PRPs/
└── redaction-extensions.txt              # per-project secret-redaction rules
Why two tiers plus details

Tier 1 (CLAUDE.md) is always loaded at session start, so it stays small (< 2000 tokens). Tier 2 (KNOWLEDGE_BASE.md) is a table of contents pointing at the detailed Tier 3 files in docs/. Agents load only what they need. This keeps token cost manageable in long sessions.

When it runs

  • Once at adoption time — *init mode scans the project and produces the full tree with items marked [INFERRED - VALIDATE] where the skill couldn't be confident. You review those and either confirm or correct.
  • Periodically as the project evolves — *update mode re-scans, adds missing artifacts, and flags drift, but never overwrites human-validated content.
  • Targeted modes — *domain, *libs, *gate refresh individual subtrees.

Pillar 2 — Implementation

Purpose

Take a feature described in a short prompt and deliver a merged-ready pull request. This is where most of the work happens, and it's where relay's biggest bet is concentrated: the human participates only at PRD authoring. From PRD approval onward, the pipeline runs autonomously.

The interactivity boundary

The single most important design choice in Pillar 2 is the boundary between the interactive PRD stage and the autonomous rest of the pipeline. The interactivity boundary page explains the rationale; the short version is: resolving ambiguity during PRD authoring costs minutes, resolving it after implementation cascades into plan, test, and code rework costing hours or days.

The agents

Pillar 2 is a chain of writer/reviewer pairs plus a Test Runner:

  • PRD Writer & PRD Reviewer — interactive 6-phase Q&A; produces an approved PRD in PRPs/prds/
  • Plan Writer & Plan Reviewer — autonomous; produces an approved plan in PRPs/plans/
  • Worktree creation — isolated branch and working copy for the run
  • TDD Writer & TDD Reviewer — opt-in; active only when methodology.md declares tdd: true
  • Implementer & Code Reviewer — writes the production code; looped with the Test Runner until tests pass or budget exhausts
  • Docs pair (docs-updater & docs-reviewer) — dispatched non-interactively immediately after Code Reviewer approves and before the plan/PRD state advances; syncs docs/ in the worktree with the change so the knowledge base does not depend on reaching approve
  • Test Runner — runs the suite, classifies failures, coordinates auto-correction, produces the execution report (see Agents)
  • Post-green Reviewer — after green, validates tests weren't weakened to reach there
  • Report + PR Creator — assembles the final Markdown report and opens the pull request

Built-in budgets

The autonomous portion has two hard limits that prevent runaway sessions:

max_test_retries
Default 3. One initial run plus up to 3 correction retries. Value 0 is forbidden.
max_test_minutes
Default 30. Total wall-clock of the Test Runner loop. Value 0 is forbidden.

Whichever budget exhausts first wins, with a distinct outcome code (FAILED_AFTER_N_RETRIES vs FAILED_TIME_BUDGET_EXCEEDED) so the human knows why the run stopped. See Commands reference for more.

Pillar 3 — Approval

Purpose

Once Pillar 2 has opened a PR, the remaining work is: merge it, clean up, update docs. Pillar 3 wraps that work into a single command (/relay-approve) so merging a relay-produced PR stays as low-friction as possible while guaranteeing the project's documentation stays in sync with reality.

What it does

  1. Merges the PR and deletes the feature branch and the worktree.
  2. Invokes the Docs Updater agent — reads the merged changes, compares against docs/context/ and docs/domain/, and proposes updates where the docs no longer reflect reality (e.g., a new domain area, a renamed convention, a new integration).
  3. Invokes the Docs Reviewer agent — reviews the proposed doc updates and asks the human about ambiguities (new business rules that the code introduces but don't belong to a clearly-defined area, etc.).

Why it matters

The governance files (decisions.md, anti-patterns.md, docs/domain/areas/*.md) are what make Pillar 2 reliable over time. If they drift, every subsequent Pillar 2 run gets worse. Pillar 3 is the feedback loop that keeps them fresh.

Status

All three pillars have shipped. Pillar 3's three commands (/relay-commit, /relay-pr, /relay-approve) shipped v0.14.0–v0.17.0. Since then, primary docs-sync moved to Pillar 2 — the docs pair now runs non-interactively inside /relay-implement right after Code Reviewer approves — so Pillar 3's docs cycle is now a low-delta safety-net reconciliation pass that catches only decisions made after implementation. See Phase status for the current state.

Why three pillars, not two or four?

Why not two (init + implement)? Because doc drift is the silent killer. If implementation lands without a feedback step that refreshes the governance files, the project's documented reality diverges from its actual reality — and the next run uses stale rules. Pillar 3 is the correction.

Why not four (split init from config, for example)? Because context-builder already handles both documentation scaffolding and config emission (.claude/settings.json, redaction-extensions.txt). Splitting them would create artificial boundaries without adding clarity.

Why clear pillar boundaries at all? Because each pillar has a different user interaction model:

  • Pillar 1 runs once or periodically; the human reviews inferred items.
  • Pillar 2 runs many times; the human is interactive only at PRD.
  • Pillar 3 runs once per merge; the human approves doc changes.

Having the three as separable commands (*init / /relay-execute / /relay-approve) lets you run them at different cadences and inspect them independently.
