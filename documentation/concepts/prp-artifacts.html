PRP artifact paths

Why every pipeline artifact — PRDs, plans, reports, reviews — lives under PRPs/ at the repo root and never under .claude/. And why .claude/settings.json is the one explicit exception.

The rule

Canonical artifact root

All relay pipeline outputs land under PRPs/ at the repo root of the target project. No exceptions during pipeline runs.

<repo-root>/
├── PRPs/
│   ├── prds/<feature>.prd.md                  # PRD Writer output
│   ├── plans/<feature>.plan.md                # Plan Writer output
│   ├── reports/<feature>/
│   │   ├── run.json                            # /relay-test state
│   │   ├── test-review.json                    # /relay-test-review verdict
│   │   ├── final-report.md                     # generate-final-report.mjs output
│   │   ├── coverage-baseline.json              # optional, team-committed
│   │   └── attempts/<N>/
│   │       ├── record.json                     # normalized + classified
│   │       ├── stdout.log                      # redacted execution log
│   │       └── diff.patch                      # per-attempt diff
│   ├── reviews/                                # ad-hoc reviews
│   └── redaction-extensions.txt                # per-project redaction extras
└── .worktrees/<feature>/                       # ephemeral per-feature worktree

Why not .claude/?

The upstream prp-core plugin writes its artifacts under .claude/PRPs/. relay deliberately chose differently. The reason is a concrete property of Claude Code: any write to .claude/ triggers a hardcoded permission prompt. The prompt is intentional (Claude Code protecting its configuration surface) and there's no configuration to bypass it.

For a manual workflow, that's fine — one prompt per run is tolerable. For relay's autonomous pipeline, it's fatal: the Plan Writer would prompt to write its output, then the TDD Writer would prompt to write test files, then the Implementer would prompt on each commit, then the Test Runner would prompt on every attempt, then the final report would prompt. A supposed-to-be-autonomous run would turn into a permission-approval marathon.

Moving the artifact root one level up, to PRPs/, sidesteps the prompt entirely. Writes to PRPs/ are governed by the project's own .gitignore and .claude/settings.json allow patterns like any other path.

The one exception: .claude/settings.json

The context-builder skill generates .claude/settings.json at *init time with the project's allowlist and denylist. That one write to .claude/ is acceptable because:

  • It happens once, at setup time, not per pipeline run.
  • The user is interactive at that moment (running *init), so the one permission prompt from Claude Code is a deliberate user action, not an interruption of an autonomous loop.
  • It's setup configuration, not a pipeline artifact. The distinction matters: setup config is written to enable future autonomous runs. Pipeline artifacts are produced by autonomous runs.

Writing anything else under .claude/ during a pipeline run is explicitly an anti-pattern:

Anti-pattern: writing pipeline artifacts under .claude/

What it is: An agent writes a PRD, plan, Test Runner report, TDD suite, or any other pipeline artifact somewhere under .claude/.

Why it's forbidden: Claude Code enforces hardcoded permission prompts on writes to .claude/. Each prompt interrupts the autonomous portion of the pipeline. The permission guards are intentional and have no bypass.

What to do instead: Write to PRPs/ at the target repository root. Every agent that produces an artifact MUST use this root.

Scope / exception: This rule applies to pipeline artifacts. It does NOT apply to .claude/settings.json, which is setup configuration written once by the context-builder during *init.

Consequences for .gitignore

Because PRPs/ is the artifact root, and because the autonomous pipeline needs to be able to write there, you don't want PRPs/ gitignored. Artifacts SHOULD be committed so PR descriptions can link to them (the final report lives at PRPs/reports/<feature>/final-report.md and is referenced from the opened PR).

On the other hand:

  • .worktrees/ should be gitignored — those are ephemeral per-feature directories, not tracked content.
  • .claude/settings.json should be committed, but the rest of .claude/ (session state, scheduled tasks, local overrides) should be ignored.
  • .claude/settings.local.json should be gitignored — per-user overrides.

The exact .gitignore pattern that achieves this correctly is:

# Claude — ignore session/cache/local artifacts, but commit project-wide settings
# Use /* (not /) so git still traverses the directory and honors the negation below
.claude/*
!.claude/settings.json

# relay — per-feature worktrees (ephemeral)
.worktrees/
Git gotcha: .claude/ vs .claude/*

A bare .claude/ rule ignores the whole directory — and because git refuses to traverse an ignored directory, the !.claude/settings.json negation is silently ignored. You end up with settings.json still hidden from git despite the negation looking correct.

The fix is to use .claude/* instead. The star form tells git to ignore each file inside rather than the directory wholesale, and the negation then works as expected.

Artifact lifecycle

Per-feature

A single feature run produces a whole PRPs/reports/<feature>/ directory. Those reports should stay committed: they're the audit trail. If a reviewer asks "why did the AI make this choice in attempt 2?", you open attempts/2/stdout.log and read the diff.

After approval

When /relay-approve merges the PR, the feature branch and .worktrees/<feature>/ are cleaned up. The PRPs/ artifacts stay — they're part of the main-branch history now. The Docs Updater may reference them when proposing updates to docs/context/.

Long-term

PRPs/ grows monotonically. A project that's been using relay for a year has hundreds of report directories. That's fine — they're small (each under 1 MB typically) and text-based (diff-friendly). If the total size becomes a problem, archive old reports to a separate repo rather than deleting in-place (the git history still references them).
