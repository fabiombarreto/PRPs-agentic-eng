Phase status

Where relay is today. Two levels of tracking: the five project-level phases (Foundation → CI/CD) that structure the overall rollout, and the per-PRD phase tables inside each feature's PRD. This page covers both.

Legend

  • done — artifact delivered, validated as working
  • partial — artifact delivered; some aspect (usually a runtime signal) still pending validation
  • pending — not started or explicitly deferred

Planned: runnable worktree environments planned

/relay-worktree (v0.11.0) established the worktree as a file-isolation boundary. It explicitly deferred everything that makes the application actually runnable inside that folder — port allocation, dependency installation, Docker Compose project-name isolation, and per-stack environment replication are all delegated to a project-owned scripts/worktree-bootstrap.sh hook with no relay-level strategy.

A registered future feature picks those deferrals back up: evolve each .worktrees/<feature>/ into a self-contained runnable environment so the autonomous agents (implementer, test-runner) can start and exercise the application inside the worktree with zero cross-pipeline collision. The feature's PRD must define explicit strategies for per-worktree env/secret replication, dependency installation, deterministic port allocation, container / Compose project-name isolation, data/DB isolation, and how the runnable-environment handle is threaded through /relay-execute down to the agents.

Planned: planning-document track planned

relay's interactive entry point, /relay-prd, authors one feature at a time. Everything upstream of a single feature — the multi-feature planning documents that decide which features exist and in what order — sits outside the pipeline. This repository's own docs/planning/ documents were hand-authored, are cited by the 2026-04-19 phased-rollout decision as the source of the five project-level phases above, and have no writer/reviewer pair, no rubric, no status lifecycle, and no mechanical path from a planning statement to a PRD. Every other authoring stage in relay has all four.

A registered future capability closes that gap: a planning-document track covering three steps — write the planning document, review it against a rubric, then decompose it into per-feature PRDs — with its own commands and agents, following the writer/reviewer shape every other stage already uses.

The capability's PRD must decide six things, none of them settled by the registration:

Artifact shape
A canonical Markdown artifact and its location, mirroring PRPs/prds/ and PRPs/plans/, plus the trailing *Status: DRAFT|APPROVED* block every relay artifact carries.
Interactivity boundary
Whether the writer is interactive like prd-writer or autonomous like plan-writer, and correspondingly whether the reviewer flips status autonomously or requires explicit human confirmation. relay admits exactly three human-confirmed surfaces today; a fourth is a conscious decision, not an inherited default.
Rubric
The review check ids and their blocking / advisory materiality classes. Every rubric added after 2026-08-06 inherits that taxonomy, where new checks default to advisory.
Decomposition contract
How one approved planning document yields N PRDs: whether it carries its own feature table acting as a state machine, how a generated PRD links back to its originating row, and whether decomposition is a third command or a mode of the reviewer's approval.
Orchestration reach
Whether an orchestrator may ever drive planning through to implementation end to end, or whether the human gate at the planning/PRD seam is permanent.
Existing documents
Whether the current docs/planning/ files are migrated, kept as historical artifacts, or treated as the informal predecessor of the new format.
Registered, not scheduled

Recorded in docs/decisions.md (2026-08-13, "Planning-document track"). Not implemented and not yet placed in a numbered project phase. No agent builds any part of it — and in particular no "planning mode" branch is added to /relay-prd or /relay-plan — ahead of a dedicated PRD authored via /relay-prd and approved.

Plugin-usage metrics artifacts phases 1–4 shipped phase 5 deferred

Shipped 2026-08-14 — four of five phases

What exists: plugins/relay/resources/usage-metrics-schema.md (the codebook — four relations, a closed field contract, an explicit closed-versus-open enum split), plugins/relay/scripts/usage-metrics.mjs (a dependency-free materializer plus a query subcommand), a tracked PRPs/metrics/ directory with its .gitattributes and .gitignore, and metrics-isolation as the 13th npm run validate check. Backfilled against this repository's own corpus on first run: 15 shards, roughly 5,600 rows.

Phase 5 (automated emission) is deferred, not dropped — see the note at the end of this section. The prose below describes the problem the feature was built to solve and remains accurate; it is kept because the reasoning still explains why the artifact has the shape it does.

relay already emits a per-run audit trail inside every target project: orchestrator-run.json, run.json, test-review.json, per-attempt diff.patch files, and the verdict logs *.review.jsonl, *.code-review.jsonl, and *.test-write-review.jsonl. Two instruments read them — scripts/efficiency.mjs and the efficiency-report skill — but both are repo-local and run-scoped. No portable artifact exists that a target project accumulates for the express purpose of being reviewed later.

The cost of that gap is on the record. The 2026-08 cross-project measurement over roughly 370 artifacts from 6 repositories, and the 353-verdict audit across 7 repositories behind the materiality work, were both assembled by hand from scattered logs. The 2026-07-31 degraded-timestamp fix is the same gap in another form: the trail was designed for per-run debugging, so its measurement-critical fields were never contractual, and 45 percent of verdicts carried a placeholder timestamp before the fix landed.

A registered future capability defines a versioned, portable metrics artifact that projects using relay accumulate over time, reviewed periodically and fed back into improving the plugin. Its PRD must decide the schema and its version field, the emission point and format, the location and retention lifecycle, the opt-in and redaction posture, backward compatibility with corpora already accumulated, which instrument consumes the artifact, and which fields are contractual so a future agent-definition change cannot silently degrade them.

Local files, no telemetry

Nothing in this capability transmits data anywhere. Metrics artifacts sit inside other people's repositories, so any aggregation across projects is a manual, human-initiated act of collecting files. No automatic telemetry, upload, or network call is authorized, and none may be introduced without its own explicit decision entry.

Phase 5 — deferred, and why

The fifth phase (automated emission via hooks) is marked deferred in the source PRD's Implementation Phases table rather than left pending. It is not blocked by cost or difficulty — it is gated on evidence that does not yet exist. The PRD's own Phase Details say its scope is "deliberately unspecified until Phases 1–4 have run in practice" and that entering it "requires evidence that the manual cadence is insufficient", and its content is classified MoSCoW Won't. The orchestrator halted with FAILED_PHASE_SCOPE_UNPLANNABLE rather than invent scope the PRD deliberately withheld.

What remains for it has narrowed twice since. The 2026-08-14 token-budget decision replaced the hard zero-token constraint with a 1 percent budget, which makes a command writing into an artifact it already produces both cheaper and structurally safer than a hook. And duration columns added the same day captured test and correction timing by pure derivation. Only per-agent wall-clock and unterminated sessions still require the phase.

To enter it later, hand-edit the row's Status cell back to pending — the same escape hatch that governs re-running any phase. Recorded in docs/decisions.md (2026-08-13 registration; 2026-08-14 shipped entry and token budget).

Known gaps

The corpus holds exactly one project, so the cross-project value proposition — the founding motivation, given the 2026-08 six-repository measurement was assembled by hand — is untested against real data. The mechanism has tests, but on synthetic input. And the scan relation's version axis is nominal so far: every row is from one day at one plugin version, so it bounds nothing yet. Materializing at each release cut, now part of the efficiency-report ritual, is what starts making it real.

Known gaps

Honest list of things documented but not yet realized:

Coverage baseline

The post-green reviewer detects coverage drops >5% when a baseline file exists at PRPs/reports/coverage-baseline.json. The baseline is team-committed (opt-in); no automatic generation yet. When baseline is missing, the reviewer notes the limitation in its verdict and proceeds with structural checks only.

Weak-test detection

B3 classifier intentionally skips the weak_test category for MVP. Detecting a poorly-written test requires reading the test's source code; the heuristic surface is too small to catch most cases. B5 (post-green review) is the actual guard — it catches tests that were removed or skipped, which covers the common weakening patterns.
