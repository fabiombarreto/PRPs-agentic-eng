Phase status

Where relay is today. Two levels of tracking: the five project-level phases (Foundation → CI/CD) that structure the overall rollout, and the per-PRD phase tables inside each feature's PRD. This page covers both.

Legend

  • done — artifact delivered, validated as working
  • partial — artifact delivered; some aspect (usually a runtime signal) still pending validation
  • pending — not started or explicitly deferred

Phase 4 (Approval cycle)

All three Pillar 3 commands and both Docs agents shipped in v0.14.0–v0.17.0, completing the full commit → push → PR → merge → docs-sync lifecycle:

  1. /relay-commit [<feature> | target description] shipped v0.14.0; dual-mode v0.16.0 — local commit only; reversible; no push. Worktree mode commits the pipeline worktree; current-branch mode reviews the diff and commits the current branch. Safe to run immediately after manual testing.
  2. /relay-pr <feature> shipped v0.15.0 — pushes the branch and opens the PR via gh pr create; writes final-report.md into the PR body.
  3. /relay-approve <pr> shipped v0.17.0 — merges the PR, deletes the feature branch and worktree in collision-safe order, then runs Docs Updater and Docs Reviewer agents as a safety-net pass to keep docs/context/ and docs/domain/ in sync with what was merged — the pair's primary sync now happens earlier, during /relay-implement (Pillar 2).

Phase 5 (CI/CD)

Integration with real CI: GitHub Actions workflows that invoke relay, external-service gating, automated merge rules. Last phase, furthest out.

Planned: runnable worktree environments planned

/relay-worktree (v0.11.0) established the worktree as a file-isolation boundary. It explicitly deferred everything that makes the application actually runnable inside that folder — port allocation, dependency installation, Docker Compose project-name isolation, and per-stack environment replication are all delegated to a project-owned scripts/worktree-bootstrap.sh hook with no relay-level strategy.

A registered future feature picks those deferrals back up: evolve each .worktrees/<feature>/ into a self-contained runnable environment so the autonomous agents (implementer, test-runner) can start and exercise the application inside the worktree with zero cross-pipeline collision. The feature's PRD must define explicit strategies for per-worktree env/secret replication, dependency installation, deterministic port allocation, container / Compose project-name isolation, data/DB isolation, and how the runnable-environment handle is threaded through /relay-execute down to the agents.

Registered, not scheduled

Recorded in docs/decisions.md (2026-05-15, "Runnable worktree environments"). Not implemented and not yet placed in a numbered project phase. No agent builds any of the six strategies ahead of a dedicated PRD authored via /relay-prd and approved; until then the project-owned bootstrap-script delegation (D6, 2026-05-11) remains the only operative contract.

Known gaps

Honest list of things documented but not yet realized:

Coverage baseline

The post-green reviewer detects coverage drops >5% when a baseline file exists at PRPs/reports/coverage-baseline.json. The baseline is team-committed (opt-in); no automatic generation yet. When baseline is missing, the reviewer notes the limitation in its verdict and proceeds with structural checks only.

Weak-test detection

B3 classifier intentionally skips the weak_test category for MVP. Detecting a poorly-written test requires reading the test's source code; the heuristic surface is too small to catch most cases. B5 (post-green review) is the actual guard — it catches tests that were removed or skipped, which covers the common weakening patterns.
