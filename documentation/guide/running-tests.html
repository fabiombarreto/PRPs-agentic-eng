Running tests

How to use /relay-test directly — as a standalone Test Runner with auto-correction, without adopting the rest of the pipeline. Useful for teams piloting relay, for iterating on flaky tests, and for understanding what the autonomous pipeline will see when it reaches your suite.

When to invoke /relay-test manually

  • Piloting relay on a real project. Running /relay-test against a branch validates that .claude/settings.json, the redaction policy, and the framework integration all work — before you commit to the full orchestrator.
  • Debugging flakiness. The classifier (B3) labels each failure and the report surfaces oscillation patterns. Running the command against a branch that's been flaky in CI often tells you where to focus.
  • Iterating on tests. If you're editing test code and want to re-validate without re-running the whole pipeline.
  • Inside the orchestrator. /relay-execute invokes /relay-test internally — understanding what it does in isolation is the clearest way to debug orchestrator failures.

Step 1 — Invoke it

/relay-test <worktree-path> [--max-retries N] [--max-minutes M] [--tier unit|integration|e2e] [--feature <name>]

Typical minimal invocation:

/relay-test .

Runs against the current working tree, default budgets (3 retries, 30 minutes), auto-detected tier and feature name (from current branch).

Common overrides

  • --max-retries 2 — tighter budget if your suite is slow and you want to fail fast
  • --max-minutes 60 — looser budget for heavy E2E
  • --tier unit — skip integration/E2E, run only unit tier (forces layered execution off if not detected)
  • --feature my-branch — override the feature slug (the command derives from git branch by default)

Step 2 — What happens

The command runs the Test Runner loop (stage 6):

  1. Precondition checks — worktree valid, .claude/settings.json present, methodology.md readable, PRPs/ writable. HALTs loud if anything's missing.
  2. Initialize loop state — new run_id, start timestamp, deadline from max_test_minutes.
  3. For each attempt (up to max_test_retries + 1):
    1. Invoke the test-runner agent with the attempt number and previous records.
    2. Agent runs the suite (make test-pytest or the detected equivalent), normalizes JUnit XML, classifies failures.
    3. Agent returns a verdict (GREEN, RETRY_NEEDED, RETRY_FLAKY, ABORT_INFRA, ABORT_TIME).
    4. Command dispatches:
      • GREEN → exit successfully.
      • RETRY_NEEDED → invoke Implementer with feedback, then loop. (Currently HALTS if the Implementer isn't yet implemented — see below.)
      • RETRY_FLAKY → rerun without changes.
      • ABORT_INFRA → attempt one recovery (make test-down && make test-bootstrap). If still failing, exit with FAILED_INFRA_UNRECOVERABLE.
      • ABORT_TIME → exit with FAILED_TIME_BUDGET_EXCEEDED.
  4. Write PRPs/reports/<feature>/run.json with full session state.
Current gap: /relay-implement

When a failure is classified as legitimate, the loop tries to invoke /relay-implement with the feedback. That command isn't yet implemented (it's part of Pillar 2's upcoming orchestrator). Until it lands, /relay-test HALTS on the first RETRY_NEEDED and writes the failure feedback to PRPs/reports/<feature>/attempts/<N>/implementer-feedback.json so you can apply the fix manually.

This is documented behavior, not a bug. You do the fix, re-run /relay-test, and the loop proceeds.

Step 3 — Read the outputs

Every run produces a directory:

PRPs/reports/<feature>/
├── run.json                  # session state, budgets, outcome
└── attempts/
    ├── 1/
    │   ├── record.json       # normalized + classified failures
    │   ├── stdout.log        # redacted execution log
    │   └── diff.patch        # git diff (empty on attempt 1)
    └── 2/
        └── ...

run.json is the summary. Open it to see: final outcome, elapsed time, budget state at exit, per-attempt verdicts, secrets_redacted counts, skipped components.

For each attempt, record.json is the authoritative state — normalized per the schema v1, with failures[].category filled in by the B3 classifier.

stdout.log has the raw test output with secret values already replaced by [REDACTED] / [REDACTED_URL]. Safe to commit, safe to paste into PR comments, safe to share.

Interpreting the verdict codes

GREEN success

All tests passed (or all failures were flaky-retry-resolved). Next step: run /relay-test-review to verify nothing was weakened to reach green. See Post-green review guide.

FAILED_AFTER_N_RETRIES

The retry budget exhausted with the same legitimate failure persisting. Three typical causes:

  • Requirement gap — the PRD is ambiguous or contradictory; the Implementer can't converge. Clarify the PRD and rerun.
  • Weak test — the test itself is broken, blocking progress. Fix the test.
  • Too-tight budget — the fix needs more iterations than the budget allows. Rerun with --max-retries 5.

FAILED_TIME_BUDGET_EXCEEDED

Wall-clock exhausted. Usually means E2E is slow. Options:

  • Rerun with --max-minutes 60 or higher.
  • Check run.json.time_breakdown to see which phase consumed the budget. If infra_setup is the culprit, Docker cold start is the issue.
  • Enable layered execution — if the unit tier fails, E2E gets skipped, saving time.

FAILED_OSCILLATION

The Implementer's fix in attempt N+1 reverted files from attempt N. Signals a PRD-level conflict — the code can't satisfy two ACs simultaneously. Look at the two attempts' diffs (attempts/N/diff.patch and attempts/N+1/diff.patch); the conflict usually maps to a specific requirement pair.

FAILED_INFRA_UNRECOVERABLE

Common subcauses (reported in run.json.abort_reason):

  • missing_settings_json — re-run *update of the context-builder skill.
  • docker_not_running — start Docker Desktop, then rerun.
  • db_unreachable — check docker-compose.test.yml; usually a port conflict or a stale container.
  • normalizer_failure — the test framework didn't produce JUnit XML. Verify the framework config (pytest --junitxml, Playwright reporter: junit, Vitest reporters: junit).
  • no_test_framework — the project has no test framework relay could detect. Not a bug — document it in the final report.

Running inside the orchestrator

When you invoke /relay-execute <prd>, the Test Runner runs the same way it would standalone — same budgets, same verdicts, same reports. The only difference: on RETRY_NEEDED, the orchestrator has the Implementer available and loops automatically.

This means iterating on the Test Runner in isolation is a safe way to validate the integration before handing off.
