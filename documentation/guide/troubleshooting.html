Troubleshooting

Known issues, common pitfalls, and concrete fixes. When a run behaves unexpectedly, check here first — most problems fall into one of these categories.

Installation issues

Plugin doesn't appear in Claude Code

Symptom
After enabling the marketplace, *init does nothing; no slash commands work.
Cause
The running session didn't pick up the newly-enabled marketplace. Claude Code reads the marketplace list at session start.
Fix
Close and reopen Claude Code. In the new session, the plugin is loaded.

${CLAUDE_PLUGIN_ROOT} doesn't resolve

Symptom
Agents fail trying to read files under ${CLAUDE_PLUGIN_ROOT}/docs/context/ or ${CLAUDE_PLUGIN_ROOT}/scripts/; bash commands show the literal string instead of expanding it.
Cause
Your Claude Code version predates the variable's introduction, or the variable isn't passed to the Bash tool's shell environment.
Fix
Upgrade Claude Code to the latest version. If the issue persists, file a report — this is infrastructure relay depends on.

Node.js scripts fail with "command not found"

Symptom
node: command not found when the Test Runner invokes normalize-test-output.mjs.
Cause
Claude Code bundles Node but the Bash tool uses the shell's PATH. If Node isn't in your shell PATH, it's invisible.
Fix
Add Node's binary directory to PATH in your shell config. Verify: which node should print a path. On Windows, check that the Node installer added itself to the system PATH; on macOS/Linux, check your .zshrc / .bashrc.

Context-builder issues

"Found existing artifacts" prompt is confusing

Context
Running *init on a project that already has docs/context/ or docs/domain/.
What to choose
[U] Switch to update mode unless you explicitly want to throw away existing docs. [U] is the same as running *update directly and will preserve human-validated content, adding only missing files.

[R] is data-destructive — pick it only when you want a clean slate.

[S] aborts the run. Useful if you hit the prompt by accident.

Too many [INFERRED - VALIDATE] markers

Symptom
The final report lists dozens of items requiring validation.
Cause
The skill is being honest: most of what it wrote is inferred from code scan rather than explicit evidence. This is normal for the first *init on a project with substantial code.
Fix
Work through them incrementally. Start with docs/decisions.md and docs/anti-patterns.md (these drive the Decision Gate). Then the domain area files. The [INFERRED - VALIDATE] markers are reminders that the AI should not treat these as settled yet — once you validate, remove the marker.

Domain areas detected incorrectly

Symptom
The skill created docs/domain/areas/foo.md when foo isn't a real business area; or split something that should be one area into two.
Fix
Edit the files directly. Merge two area files into one by concatenating. Delete a file that shouldn't exist and remove its entries from docs/KNOWLEDGE_BASE.md and CLAUDE.md. The next *update run preserves your edits.

Permission and settings issues

Permission prompts interrupt the pipeline

Symptom
Running /relay-test, Claude Code prompts for approval on every bash command. Completely defeats autonomous operation.
Cause
.claude/settings.json is missing, incomplete, or not recognized.
Fix
  1. Verify the file exists: cat .claude/settings.json.
  2. Check it has an allow array with the patterns your stack needs (pytest, docker compose, etc.) — see Settings allowlist.
  3. If absent or incomplete, run *update in the target project to regenerate from the current catalog.

.claude/settings.json isn't tracked by git

Symptom
git status doesn't show .claude/settings.json after creating it; git add .claude/settings.json says "ignored by one of your .gitignore files."
Cause
Your .gitignore has a bare .claude/ rule (without the star). Git refuses to traverse an ignored directory, so the !.claude/settings.json negation doesn't work.
Fix
Change .claude/ to .claude/*: 
# Before (broken):
.claude/
!.claude/settings.json

# After (correct):
.claude/*
!.claude/settings.json
Then git add .claude/settings.json works as expected.

Test Runner issues

Normalizer can't parse JUnit XML

Addressed in handling failures: normalizer_failure. Verify the framework is configured to emit JUnit XML, and the output file exists at the expected path.

Classifier picks the wrong category (infra instead of legitimate, etc.)

Symptom
A real bug is labeled infra and triggers a recovery attempt instead of being sent to the Implementer.
Cause
The failure message accidentally matched one of the infra regexes — e.g., your test prints "connection refused" as part of a legitimate assertion.
Fix
  1. Rephrase the test message to avoid infra keywords when asserting on non-infra behavior.
  2. If the pattern is genuinely ambiguous, the classifier heuristics in plugins/relay/agents/test-runner.md need refinement. File an issue with the false-positive example.

Flakiness not detected

Symptom
A test that passes on retry-without-change is being treated as legitimate and sent to the Implementer.
Cause
The B3 classifier's flakiness detection requires the same failure to appear across attempts with the test file unchanged. If the Implementer modifies the test file between attempts (even unrelated changes), flakiness detection fails.
Fix
The Implementer shouldn't be modifying test files (that's an anti-pattern). If it is, investigate why — usually the PRD is unclear about whether tests should change.

Post-green review issues

test_removed false-positive on a rename

Symptom
You renamed a test file; the reviewer reports all its tests as removed.
Cause
The reviewer diffs file-by-file. A rename appears as "all tests deleted from old file" + "all tests added in new file." The in-file offset only tolerates renames within the same file.
Fix
  1. Verify the rename is legitimate (file was moved, not its contents dropped).
  2. If legitimate, manually flip the verdict in test-review.json to APPROVED and document the rename in the PR description. Or: use git mv so the rename is clearer in history.

Coverage baseline drift

Symptom
Every PR triggers a coverage_drop concern even when the PR adds tests.
Cause
The baseline is stale. Main has moved forward since the baseline was captured; your PR's coverage is being compared against an old number.
Fix
Re-capture the baseline on current main: run the full suite with coverage, write the result to PRPs/reports/coverage-baseline.json, commit to main as a separate chore. Not in a feature PR — that would hide real regressions.

Docker-related issues

First Docker run takes forever

Symptom
make test-bootstrap takes 3+ minutes the first time.
Cause
Image builds (backend + Playwright) download layers on first run.
Fix
This is one-time cost. Subsequent runs hit the cache and complete in under 30 seconds. If it's happening every time, your Docker cache is being cleared — check for docker system prune in CI or elsewhere.

DB port conflict

Symptom
make test-bootstrap fails with "port is already allocated."
Cause
Another service on your machine uses the port the test DB wants to expose.
Fix
Either stop the conflicting service, or change the port in docker-compose.test.yml (the ports section maps host:container — change the host side).

Artifact / reporting issues

PRPs/ artifacts are being gitignored

Symptom
PRPs/reports/<feature>/ doesn't show up in git status after a run.
Cause
Your .gitignore has an unqualified reports/ rule (common in Django/Rails projects for local test output) that matches PRPs/reports/ too.
Fix
Scope the rule to the root: 
# Before:
reports/

# After:
/reports/
The leading slash restricts the pattern to the repo root, leaving PRPs/reports/ alone.

A secret leaked into a report

Symptom
You notice a credential value in a committed stdout.log or final-report.md.
Cause
The secret wasn't matched by Layer 1 (name pattern, exact env match, or value regex) or by Layer 2 (per-project extensions).
Fix
  1. Immediate: rotate the leaked secret. Don't try to rewrite git history; the secret is already out.
  2. Add a pattern to PRPs/redaction-extensions.txt so the same secret format won't leak again.
  3. If the format is likely to affect other projects (e.g., a new cloud provider's key format), contribute it to docs/context/redaction-policy.md in the plugin repo so it becomes Layer 1.

When nothing here matches

  • Re-read run.json — outcome and abort_reason usually narrow the problem space.
  • Check handling failures for per-outcome recovery.
  • Check anti-patterns — some "issues" are the Decision Gate working as designed.
  • File a GitHub issue with run.json and the last attempt's stdout.log attached. Both are redacted; safe to share.
