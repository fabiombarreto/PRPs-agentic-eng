Writing a PRD

The PRD (Product Requirement Document) is the only interactive stage of the relay pipeline. Everything downstream runs autonomously against an approved PRD, so the PRD is effectively the contract — you want it concrete and unambiguous before the pipeline starts.

When to write a PRD

A PRD is the entry point for any non-trivial feature. If the work takes more than a few hours and touches more than one file, start with a PRD. Examples:

  • New API endpoint with a data model
  • New page with associated routes and business logic
  • Non-trivial refactor crossing module boundaries
  • Bug fix requiring changes in tests + source + docs

A PRD is overkill for:

  • Typo fixes, label changes
  • Bumping a dependency version with no API change
  • Single-file cleanup that touches nothing external

(Those are exempt from the Decision Gate entirely, so you can do them with any normal tool.)

Step 1 — Invoke /relay-prd

Two forms, depending on what you have to start with:

Starting from a description

/relay-prd "add a weekly digest email for every active user summarizing their completed assessments in the last 7 days"

Short is fine. A paragraph is also fine. The PRD Writer expands it during the Q&A.

Starting from a draft

/relay-prd PRPs/prds/digest-email-draft.md

If you've already written something in Markdown, point at it. The PRD Writer reads it first, then asks targeted questions about ambiguous parts.

Step 2 — Work through the 6-phase Q&A

The PRD Writer doesn't generate the document and then ask you to review it. It dialogs with you in six phases, each a clear gate. You can't skip phases.

Phase 1 — Initiate

The writer restates what it understood from your initial description:

Agent

I understand you want to build: a scheduled weekly email to active users with their last-7-days assessment activity. Is this correct, or should I adjust my understanding?

Short answer. "Correct" or "not quite — it's about X instead." Don't type paragraphs here.

Phase 2 — Foundation

Five questions in one block:

  1. Who has this problem? Specific role, not "users".
  2. What problem are they facing? Observable pain, not assumed need.
  3. Why can't they solve it today? What alternatives exist and why do they fail?
  4. Why now? What changed?
  5. How will you know if you solved it? Success signal.

Answer all five. This is where most ambiguity gets flushed out. Be honest — "we don't have data on this yet, it's a hypothesis" is a valid answer and gets the PRD tagged accordingly.

Phase 3 — Market / codebase grounding

The writer dispatches research sub-agents (a web researcher and a codebase explorer). It returns with findings:

Agent

What I found:
— Competitors X and Y send similar digests weekly; Z abandoned the feature after low open rates.
— Your codebase has a NotificationsService in apps/notifications/ with existing templated-email infrastructure. The digest could reuse it rather than build parallel.
— Known pattern: scheduled tasks use Celery beat (see apps/scheduling/).
Does this change or refine your thinking?

A single answer: "continue" if the findings don't change your approach; "adjust — let's use NotificationsService instead of a new service" if they do.

Phase 4 — Vision & users

Five more questions:

  1. Vision in one sentence — ideal end state if this wildly succeeds.
  2. Primary user — specific description, context, what triggers the need.
  3. Job to Be Done — "When [situation], I want to [motivation], so I can [outcome]."
  4. Non-users — who is explicitly NOT the target?
  5. Constraints — time, budget, technical, regulatory.

Phase 5 — Technical feasibility

The writer dispatches the codebase-analyst sub-agent for a deeper technical read. Returns with feasibility rating, what you can leverage, and the main technical risk. One answer: "any technical constraints I should know about?"

Phase 6 — Decisions

Five final questions before generating:

  1. MVP definition — absolute minimum to validate the idea.
  2. Must-have vs nice-to-have — what MUST be in v1? What can wait?
  3. Key hypothesis — "We believe X will Y for Z. We'll know we're right when [measurable outcome]."
  4. Out of scope — what are you explicitly NOT building?
  5. Open questions — uncertainties that could change the approach.

Don't skip the "out of scope" — it's the single best tool for preventing feature creep during implementation.

Step 3 — The PRD is generated

The PRD Writer produces PRPs/prds/<feature>.prd.md with status DRAFT. Structure:

  • Decision Gate evidence block at the top (the writer consulted docs/decisions.md, docs/anti-patterns.md, docs/context/architecture.md).
  • Problem Statement, Evidence, Proposed Solution, Key Hypothesis, What We're NOT Building, Success Metrics.
  • Acceptance Criteria (test scenarios) — the concrete given ... when ... then behaviors the implementation must satisfy.
  • Users & Context, Solution Detail (MoSCoW), MVP Scope, User Flow.
  • Technical Approach (feasibility, architecture notes, TDD routing, technical risks).
  • Implementation Phases — a table with phase number, name, description, status, parallelism hints, dependencies.
  • Decisions Log, Research Summary.

Step 4 — The PRD Reviewer runs

Once the draft is produced, the PRD Reviewer reads it against the project's governance files and runs a two-layer check.

Structural rubric (R1–R7)

  • Decision Gate evidence block present and referencing real entries
  • Acceptance Criteria are concrete scenarios, not vague goals
  • Hypothesis is testable with a measurable outcome
  • Out-of-scope is explicit
  • No violation of existing decisions or anti-patterns

Coherence layer (R-COH-*)

After the structural rubric, the reviewer runs an additive coherence layer to catch intra-PRD contradictions that pass shape-based checks but cause cascading rework downstream. Two parts:

  • Deterministic — table-vs-prose number drift (table says "5 phases", prose says "4 phases"), references to non-existent sections / ACs / phases.
  • Bounded LLM judgment (K=5) — at most 5 contradictions flagged per run, each with verbatim quotes from both contradicting sides. Catches: ACs that contradict each other in prose, Success Metrics decoupled from the Key Hypothesis, Solution Detail that drifts from Proposed Solution, Decisions Log entries that contradict the Proposed Solution.

The K=5 pass returns an empty list when no contradictions exist — it does not pad to 5. This is by design: a clean PRD should produce zero coherence findings.

See the coherence layer reference for the full ID taxonomy.

If any structural or coherence check fails, the reviewer loops back with specific issues:

Reviewer

Issues:
— AC-3 says "the email should be fast" — that's not measurable. What p95 delivery latency target?
— The hypothesis lacks a measurable success condition. "Engagement increases" how much, measured how?
— docs/decisions.md says all scheduled tasks must run via Celery beat; the draft proposes a cron in Docker. Which is it?

Address each issue (edit the PRD or clarify with the reviewer in chat) and the reviewer re-reads. Loop until approved.

Step 5 — Status flips to APPROVED

When the reviewer is satisfied, the PRD's status line at the bottom flips from DRAFT to APPROVED. This is the signal that the interactivity boundary has been crossed — you can now hand off to the autonomous pipeline.

Writing good Acceptance Criteria

The AC section is the most important part of the PRD because it's what the downstream agents consume as a contract. A vague AC leads to vague implementation and ineffective tests.

Bad

  • "The digest email looks good."
  • "Users can unsubscribe."
  • "The email is performant."

Good

  • "AC-1 Active user with activity: Given a user with is_active=true and at least one completed assessment in the last 7 days, when the weekly job runs, then an email is sent within 60 seconds containing their assessment count and the top 3 by completion time."
  • "AC-2 Unsubscribe: Given a user clicks the unsubscribe link in a digest email, when they confirm on the landing page, then user.receives_digest is set to false and subsequent weekly jobs exclude them."
  • "AC-3 Delivery latency: The weekly job completes for a cohort of 10k users within p95 latency of 120 seconds."

Pattern: given [precondition] → when [action] → then [observable outcome]. Include concrete numbers (latencies, counts) when applicable.

Tip

When TDD is active, the ACs become the TDD Writer's input directly — each AC ends up as one or more tests. When TDD is not active, the ACs still drive the Implementer's tests. Either way, the more concrete the AC, the more useful the tests.

Next step

With an approved PRD in hand, you have two options:

  • Run the whole pipeline — /relay-execute PRPs/prds/<feature>.prd.md. The orchestrator takes the PRD through plan, implementation, tests, review, and PR autonomously. Walk away; come back to a PR or a clear abort.
  • Run stages individually — /relay-plan, /relay-implement, /relay-test, etc. Useful when you want to inspect each stage's output before moving on.
