Post-green review

After the Test Runner reaches GREEN, you run /relay-test-review to verify the green wasn't achieved by weakening the tests. This page explains why that matters, how the command works, what each concern type means, and how to set up the optional coverage baseline.

Why this step exists

The auto-correction loop optimizes for "all tests pass." Without a guardrail, an agent might "pass" tests by deleting them, or by marking them @skip, or by replacing assertions with assert True. The resulting GREEN is meaningless — the code isn't validated, it just avoided being tested.

Post-green review catches the three most common forms of this weakening:

  1. Removed tests — test functions deleted from the suite.
  2. Added skips — tests marked @pytest.mark.skip, .skip(), xit(), etc.
  3. Trivial assertion downgrades — expect(true).toBe(true), assert True, etc.

Plus an optional fourth: coverage drops greater than 5% when a baseline is available.

When to invoke

Always invoke /relay-test-review after a GREEN /relay-test run, before opening the PR. Either:

  • Manually, right after you see outcome: GREEN in run.json.
  • Automatically, as part of /relay-execute which invokes it as the penultimate step (before /relay-pr).

Step 1 — Invoke it

/relay-test-review <worktree-path> [--base <branch>] [--feature <name>]

Defaults: base branch is main, falling back to master; feature name is derived from the current git branch.

Step 2 — Preconditions check

The command halts loud if any of these aren't satisfied:

  • The worktree path exists and is a git worktree.
  • The base branch resolves (git rev-parse --verify succeeds).
  • PRPs/reports/<feature>/run.json exists.
  • run.json's outcome field is GREEN.

If the last precondition fails (e.g., outcome is FAILED_AFTER_N_RETRIES), the message tells you: "post-green review requires a GREEN outcome; got FAILED_AFTER_N_RETRIES. Either re-run /relay-test until it passes, or fix the underlying failure."

Step 3 — What the reviewer does

The post-green-reviewer agent:

  1. Runs git diff --name-only <base>..HEAD -- <test-file-patterns> to find changed test files.
  2. For each changed test file, gets the diff and scans the + and - lines for per-language heuristics.
  3. Checks for coverage drop if PRPs/reports/coverage-baseline.json exists.
  4. Emits a verdict JSON.

The review is read-only. It never modifies code or tests; it just reports what it found.

Step 4 — Read the verdict

Two outcomes, written to PRPs/reports/<feature>/test-review.json:

APPROVED

{
  "verdict": "APPROVED",
  "run_id": "...",
  "analyzed_files": 7,
  "concerns": [],
  "notes": [
    "coverage baseline unavailable (no PRPs/reports/coverage-baseline.json)"
  ]
}

The green is trustworthy — no structural weakening detected. Safe to proceed to /relay-pr.

CHANGES_REQUESTED

{
  "verdict": "CHANGES_REQUESTED",
  "run_id": "...",
  "analyzed_files": 7,
  "concerns": [
    {
      "type": "test_removed",
      "file": "frontend/tests/e2e/assessment-list.spec.ts",
      "net_removed": 2,
      "evidence": ["- it('filters by institution', async () => {",
                   "- it('filters by date', async () => {"]
    },
    {
      "type": "test_skipped",
      "file": "backend/tests/e2e/test_public_review.py",
      "net_added": 1,
      "evidence": ["+ @pytest.mark.skip(reason='flaky in CI')"]
    }
  ],
  "notes": []
}

The green is not trustworthy — something was weakened. Fix the concerns before opening the PR.

Understanding the four concern types

test_removed

A test function was deleted from a file, net of renames. The evidence is the removed - lines showing the test signatures.

Legitimate case
You intentionally removed a test because the feature it tested was removed. If that's the case, the test removal should be part of a broader cleanup — document it.
Illegitimate case
The test was removed because it was inconvenient. Re-add it. If it was truly broken, fix it instead of removing.

test_skipped

A test was marked as skipped (@pytest.mark.skip, .skip(), xit(), etc.), net of unskips.

Legitimate case
A test is genuinely flaky in CI and being skipped pending investigation. This should have an issue link in the skip reason: @pytest.mark.skip(reason='GH-1234 investigating intermittent failure').
Illegitimate case
Skipping was a shortcut to green. Remove the skip; fix the underlying issue.

trivial_assertion

Best-effort detection of crystal-clear no-op assertions: expect(true).toBe(true), assertTrue(True), assert True. The reviewer doesn't over-fire — it only flags when the pattern is unambiguous.

Legitimate case
Rare. Possibly a placeholder test that was supposed to be filled in but was committed early.
Illegitimate case
Almost always illegitimate. Replace the assertion with an actual behavioral check.

coverage_drop

Only flagged when PRPs/reports/coverage-baseline.json exists. The reviewer compares current coverage to the baseline; absolute drop greater than 5% (e.g., 78% → 72%) is a concern.

Legitimate case
The new feature added significant code that's untested relative to baseline. If the feature is small and the uncovered code is trivial, probably fine — but should be documented.
Illegitimate case
Tests were removed without replacement, or new code skipped testing entirely. Add tests.

Setting up the coverage baseline (opt-in)

Coverage drop detection is off by default — if PRPs/reports/coverage-baseline.json doesn't exist, the reviewer just notes "coverage baseline unavailable" and proceeds with structural checks only.

To enable:

  1. Run the test suite on main (or your baseline branch) with coverage enabled.
  2. Capture the coverage result into the standard format: 
    {
  "lines_pct": 78.4,
  "branches_pct": 65.1,
  "measured_at": "2026-04-21T17:00:00Z",
  "source": "pytest --cov on main"
}
  3. Commit the file at PRPs/reports/coverage-baseline.json.

Update the baseline periodically (every few weeks, or after major test-adding PRs) by re-running coverage on main and overwriting the file. Don't update it as part of a feature PR — that would hide coverage drops.

Step 5 — Fix CHANGES_REQUESTED concerns

  1. Read each concern's evidence to understand what changed.
  2. For each concern, decide: legitimate or illegitimate? (See categories above.)
  3. Fix illegitimate concerns:
    • Re-add removed tests.
    • Remove the skip markers (or add issue references justifying them).
    • Replace trivial assertions with real ones.
  4. Re-run /relay-test to confirm still green after the fixes.
  5. Re-run /relay-test-review — it should APPROVE now.

What consumes the verdict

test-review.json is read by /relay-pr (when it lands) to decide whether to open the PR at all. A CHANGES_REQUESTED verdict blocks PR creation; the report in the PR description flags what was wrong.

The orchestrator (/relay-execute) loops back to the Implementer with the concerns as feedback when CHANGES_REQUESTED comes from the post-green reviewer. The Implementer treats them like any other set of failures — restore the removed tests, remove the skips, fix the assertions — then the loop continues.
