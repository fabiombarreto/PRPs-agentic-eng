Validation suite

The plugin tests itself. npm run validate runs a set of consistency and cross-reference checks over the relay plugin, and npm run eval checks the reviewer agents against golden fixtures. This is the plugin's own self-test — distinct from Running tests, which covers the /relay-test Test Runner that runs a target project's suite.

Two different meanings of "tests"

This page is about the checks that verify the relay plugin repository is internally consistent. The Running tests page and the Test Runner are about running the suite of a project that relay is delivering a feature into. Same word, different subject.

Why the suite exists

The relay repository is almost entirely markdown prompts and JSON config. There is no compiler and no application code to unit-test, so correctness lives in consistency invariants and cross-reference integrity: a command that dispatches an agent by name, a doc that cites a script path, a changelog that must match the plugin manifest version, a site index that must list every shipped command.

Those invariants rot silently. A rename leaves dead references; an edit desynchronizes an index; a malformed frontmatter field makes an agent load with empty metadata at runtime. Nothing catches it until the plugin misbehaves in a user's environment. Several written contracts (the three-file registration rule and the version lock-step rule in AGENTS.md) existed only as prose with no machine enforcement.

It found real bugs on day one

Beyond the known cross-reference gaps it was built to catch, the first full run surfaced six agent/command files whose YAML frontmatter failed to parse (they loaded with empty metadata at runtime) and two agents missing their required tools field — latent defects no one had noticed.

Why it is built this way

The suite is two layers with deliberately different cost and trigger, because deterministic structural checks and LLM-judgment checks do not belong on the same gate.

Layer 1 — static validation (npm run validate)
Deterministic. No LLM, no network, runs in seconds. Parses files and asserts invariants, exiting non-zero with a named check and a file:line on any violation. Cheap enough to run on every commit, so it is wired into a pre-commit hook.
Layer 2 — behavioral evals (npm run eval)
Non-deterministic. Uses promptfoo to feed the reviewer agents' own instructions plus a golden fixture to the Anthropic API and asserts the verdict token (a clean fixture must produce APPROVED, a flawed one CHANGES_REQUESTED). Costs API tokens, so it is manual and on-demand, never on the commit gate.

Other deliberate choices:

  • Node / ESM. Parity with the existing scripts/*.mjs tooling, and promptfoo is Node-native. No new language was added to the repo.
  • Scoped to plugins/relay/. Every structural check reads only the relay plugin surface (plus docs/ and documentation/ as targets). It never treats plugins/prp-core/ — the upstream reference plugin — as relay code.
  • Precision over recall. A check that fires on legitimate content is worse than useless: it can never let the tree go green, and it trains people to ignore it. Checks are anchored to narrow, must-resolve reference classes rather than broad greps, so example paths, historical citations, and target-project artifacts are not flagged.
  • The tests are authored by relay's own test pair. docs/context/methodology.md declares test_frameworks: ["node:test"] with tdd: false (test-after). Under R-X strict the Implementer authors zero test files; the test-writer / test-reviewer pair authors and maintains the checker unit tests after the implementation is code-reviewed. See the test track.

The twelve static checks

npm run validate runs each check module under scripts/validate/checks/ and aggregates the findings. Each check is a pure function returning { name, ok, findings } plus a thin file-reading wrapper.

CheckWhat it asserts
version-parityplugins/relay/.claude-plugin/plugin.json version equals the latest released heading in documentation/changelog.html (the AGENTS.md lock-step rule).
native-validateWraps claude plugin validate ./plugins/relay --strict and surfaces its failures (malformed frontmatter, kebab-case, wrong-type fields). Degrades cleanly if the claude CLI is absent.
registration-parityThe set of shipped commands and agents matches what the doc site registers — NAV, the search index, and the changelog stay in sync (the three-file rule).
path-existenceReferenced paths that must resolve in this repo actually exist (script paths, plugin-asset references, intra-repo doc links).
dispatch-graphEvery subagent_type a command dispatches, and every Next: /relay-x pointer, resolves to a real agent or command file.
frontmatter-schemaFrontmatter conforms to a per-type JSON Schema (via ajv): commands, agents, and skills each have their required fields.
artifact-namingPipeline artifacts under PRPs/plans/ follow the naming convention (no doubled .plan.review.jsonl segment).
bootstrap-parityThe context-builder skill emits both a .sh and a .ps1 worktree-bootstrap template, so Windows hosts have parity.
gating-structureEvery registered opt-in methodology key (figma_track, visual_first_approval) documents all three non-heuristic properties in the context-builder skill: default-off emission on *init, preserve-on-*update, and backfill only when the key is entirely absent.
feedback-chainThe prior_feedback contract stays intact end to end: each registered pair's command forwards it, its writer declares it and defines a ## Targeted revision mode, and plan-writer holds its three specific invariants (the input declared in both mode groups, the grounding carve-out naming all four grounding-dependent rubric ids, and the re-grounding anti-pattern agreeing with the Phase 2 short-circuit).
timestamp-contractThe review_started_at contract is mechanically enforced across its registry of jsonl-appending reviewers, dispatching commands, and consumers — each reviewer declares the input and carries a fallback branch matched to its own clock capability, each dispatching command captures the UTC instant and passes it through, and each registered consumer reads timestamp_degraded in executable code. Beyond prose, no post-marker jsonl verdict entry may carry a T00:00:00 stamp without an accompanying timestamp_degraded flag.
plugin-root-resolvableEvery plugin-owned resource template is cited under plugins/relay/ with its packaged ${CLAUDE_PLUGIN_ROOT}/resources/ prefix, never bare, and no literal <target_root>/plugins/relay/… path or npm install --prefix plugins/relay/… invocation leaks the source monorepo layout into the packaged artifact.

Running it

Prerequisites: Node 18+ and npm install once (this is the repo's first package manifest — the plugin itself still ships no runtime dependency).

npm install                 # one-time, installs the suite's dev dependencies
npm run validate            # run all twelve static checks
node --test scripts/validate/checks/*.test.mjs scripts/eval.test.mjs plugins/relay/scripts/*.test.mjs   # the unit tests for the checks and Test Runner scripts
npm run eval                # behavioral evals of the reviewer agents (needs ANTHROPIC_API_KEY)
npm run setup-hooks         # one-time: install the pre-commit gate
node --test silently drops a non-matching path segment

If any of the three glob segments above stops matching a file, node --test exits 0 and simply runs fewer tests — it does not fail or print a warning. Re-check the printed test count after moving or renaming a test file, especially across the scripts/ / plugins/relay/scripts/ boundary; there is no shell-level safety net for this.

npm run validate prints one line per check and a summary, and exits non-zero if any check found a violation:

[PASS] version-parity
[FAIL] registration-parity
  documentation/assets/data/search-index.json — command "relay-worktree" is registered under plugins/relay/commands/ but is not referenced in the search index
...
5 passed, 6 failed (11 checks run)

After npm run setup-hooks, the same command runs automatically on every git commit and blocks the commit on any violation. The hook is committed under .githooks/; setup-hooks points git's core.hooksPath at it (a per-clone git-config step, not auto-applied on clone).

npm run eval without ANTHROPIC_API_KEY set exits cleanly with a guidance message rather than failing — the eval layer is optional and never blocks a routine task.

What it costs to run

Static layer (npm run validate + unit tests)
Effectively free — no network, no LLM, a few seconds of local CPU. Run it as often as you like; the pre-commit hook does.
Eval layer (npm run eval)
One Anthropic API call per fixture case. That is real token spend and takes on the order of seconds-to-minutes per model, which is exactly why it is a separate, manual command and not part of the commit gate. Run it when you change a reviewer agent's prompt, not on every edit.
Rebuilding the suite through the relay pipeline is expensive

The suite was built by dogfooding relay on itself (/relay-prd then /relay-execute). That autonomous run spanned roughly fifty agent invocations across five phases — every phase runs a writer/reviewer pair, and the semantic code-review layer is strict enough that trivial changes can take several implement attempts. Extending the suite through the full autonomous pipeline is therefore a meaningful token spend. A small, well-scoped change — adding one check, tightening one regex — is far cheaper to do by hand and then let the test pair cover test-after.

Maintaining the suite

Adding a check

  1. Create scripts/validate/checks/<name>.mjs. Export a pure function check<Name>(inputs) that returns { name, ok, findings: [{ message, file, line }] }, plus a thin wrapper that reads the real files and delegates to it. Mirror an existing check, for example version-parity.mjs.
  2. Register it in the runner's check list in scripts/validate/index.mjs.
  3. Scope every file read to plugins/relay/, docs/, or documentation/. Never read plugins/prp-core/.
  4. Let the test pair add the unit test (scripts/validate/checks/<name>.test.mjs) test-after — the Implementer must not author test files (R-X strict). If you are hand-editing, mirror the pure-function-with-in-memory-fixtures style of the existing *.test.mjs.

Keeping it green

  • Fix the cause, not the check. When a check turns red, the finding is almost always a real inconsistency — fix the underlying file. The suite has already caught broken frontmatter and dead references this way.
  • When a check false-positives, tighten it — do not weaken it. Narrow the reference class or add a precise exclusion for legitimate content (examples, historical citations). Never broaden it into a shape that can never go green, and never delete a test to force a pass — the post-green reviewer blocks that.
  • Renames ripple. If you add, rename, or remove a command or agent, registration-parity will fail until you update the three coupled doc-site files (NAV, search index, changelog) per AGENTS.md §6. That is the check doing its job.
  • Cutting a doc-site release bumps the plugin manifest. version-parity enforces the AGENTS.md §7.5 lock-step rule: a minor or major changelog release must bump plugin.json to the same value in the same commit.

Using it in day-to-day development

  • Let the hook run. After the one-time npm run setup-hooks, every commit is validated automatically. A blocked commit is the suite telling you a contract is broken — read the named check and file:line, fix it, and re-commit.
  • Run it before opening a PR. npm run validate is fast; running it (and the unit tests) before pushing keeps reviewers focused on substance instead of consistency nits.
  • Run the evals when you touch a reviewer prompt. If you edit test-reviewer.md (or another reviewer agent), npm run eval checks that a clean fixture still earns APPROVED and a flawed one CHANGES_REQUESTED — a cheap guard against a prompt edit that silently changes a verdict. Mind the token cost.
  • Treat a red check as signal, not noise. The checks are deliberately narrow, so a failure is very likely a genuine problem rather than a false alarm.
