First run

Walking through the first invocation of the context-builder skill against a new project. What it does, what you need to review, and what you end up with after the first commit.

When to run this

Run the context-builder once per project, at the moment you decide to adopt relay. The skill produces the documentation tree every downstream agent depends on — no other relay command will work correctly without it.

Run it again in *update mode:

  • When major dependencies change (new framework, major version bumps)
  • When you add a new business area / Django app / module
  • Periodically (monthly-ish) to catch drift between the documented state and reality

Step 1 — Invoke it

Open Claude Code in the target project's root directory. Type:

*init

The skill announces which mode it's entering and starts Phase 0. If the project already has docs/ or .claude/ artifacts, you'll be prompted: 

Found existing docs/context, docs/domain, docs/libs. Choose:
  [R] Recreate from scratch    — data-destructive, will overwrite
  [U] Switch to update mode    — preserve what's there, add missing
  [S] Skip and abort           — do nothing, exit

For a first run on a fresh project, there's no prompt — it just proceeds. For adopting relay on an existing project with docs, choose [U] unless you're certain you want to overwrite.

Step 2 — Watch the phases run

The skill announces each phase and what it's producing. In a typical run:

Phase 0
MCP Context7 availability check. If absent, docs/libs/ generation is skipped with a warning (proceeds otherwise).
Phase 1
Project scan — reads manifests, README, folder structure, representative code files. Prints detected stack.
Phase 1.5
Generates .claude/settings.json from the stack signals.
Phase 1.75
Creates PRPs/redaction-extensions.txt empty (with a header comment).
Phase 2
Creates docs/context/ files — architecture, conventions, constraints, integrations, methodology.
Phase 3
Creates docs/domain/ — glossary, flows, one file per detected business area.
Phase 4
Creates docs/libs/ via Context7 (when available).
Phase 4.5
Creates docs/decision-gate.md, decisions.md, anti-patterns.md.
Phase 5
Creates Tier 3 developer docs (docs/architecture.md, development.md, etc.).
Phase 6
Creates docs/KNOWLEDGE_BASE.md — the TOC.
Phase 7
Creates CLAUDE.md — Tier 1.
Phase 8
Prints the final report.

Total time: 2–10 minutes for a medium-sized project, most of it in Phase 3 (domain inference) and Phase 4 (Context7 fetches).

Step 3 — Read the final report

The skill's final report is where you spend the most attention. It's structured like this:

## Context Builder — Report

### Mode
init

### Files created
[15-30 files listed with relative paths]

### Domain areas identified
accounts
billing
catalog
...

### Methodology declaration
docs/context/methodology.md created with tdd: false
Test frameworks detected: pytest, vitest, playwright
Observed signals: 3 entries in body

### Autonomous-pipeline permissions
Emitted 28 allow patterns across: pytest, npm scripts, docker compose,
git non-destructive, gh CLI read, python manage.py, pip install -r,
linters (ruff, black, eslint, prettier, tsc), relay plugin scripts.
Denylist: 32 invariant patterns.

### Items requiring human validation
[all [INFERRED - VALIDATE] items grouped by file]

### Open questions
[from domain/areas/*.md "Open Questions" sections]

### .gitignore follow-ups (init mode)
Add these lines to .gitignore:

  # Claude — ignore session/cache/local artifacts, but commit project-wide settings
  .claude/*
  !.claude/settings.json

  # relay — per-feature worktrees (ephemeral)
  .worktrees/

### Skipped
/libs skipped: Context7 unavailable

Don't skim this. The two critical sections are Items requiring human validation and Open questions — they're where the skill honestly admits what it couldn't figure out on its own.

Step 4 — Validate the inferred items

The skill marks every uncertain inference with [INFERRED - VALIDATE]. These appear in docs/decisions.md, docs/anti-patterns.md, and most domain area files.

Go through them one by one:

  1. Open the flagged file.
  2. Search for [INFERRED - VALIDATE].
  3. For each occurrence: is the inference correct?
    • Yes → remove the [INFERRED - VALIDATE] marker. The decision/anti-pattern/rule is now validated.
    • Partially → fix the wording, then remove the marker.
    • No → delete the entry entirely, or rewrite from scratch.

Don't leave [INFERRED - VALIDATE] markers in place long-term. They signal to downstream agents (via the Decision Gate) that the rule isn't trusted yet — if they stay forever, the Gate's value erodes.

Step 5 — Answer the open questions

Each docs/domain/areas/*.md has an Open Questions section at the bottom with the things the skill couldn't figure out. These are typically business rule ambiguities: 

## Open Questions

- What happens when payment fails a second time? Does the subscription downgrade immediately?
- Is there a grace period before access is blocked?
- Does the team's `active_institution` election persist across logout/login?

For each question: get the answer from whoever knows (product manager, tech lead, the PR author who originally wrote that module). Then either:

  • Add the answer as a rule to the area file's main body (above the Open Questions section).
  • Record it as a decision in docs/decisions.md if it's a cross-cutting choice.
  • Record it as an anti-pattern if it's a rule about what not to do.

Then delete the bullet from the Open Questions section. The list should shrink to zero over time.

Step 6 — Update .gitignore

The skill tells you in the final report exactly what to add. Copy it verbatim into your project's .gitignore: 

# Claude — ignore session/cache/local artifacts, but commit project-wide settings
# Use /* (not /) so git still traverses the directory and honors the negation below
.claude/*
!.claude/settings.json

# relay — per-feature worktrees (ephemeral)
.worktrees/
Don't use .claude/ — use .claude/*

The leading-slash trailing-slash form (.claude/) ignores the whole directory, which makes git skip traversal entirely — the !.claude/settings.json negation then has no effect. The form with the star (.claude/*) ignores each file inside, letting the negation work as expected. See PRP artifact paths for the full gotcha.

Step 7 — Commit everything

At this point you have a fair number of new files. A single commit with all of them works fine:

git add CLAUDE.md docs/ PRPs/redaction-extensions.txt .claude/settings.json .gitignore
git commit -m "chore(context): initialize relay context tree"

This is your project's first relay commit. All subsequent agent activity will consult the files this commit added.
