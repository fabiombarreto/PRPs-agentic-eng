Handling failures

What to do when the autonomous pipeline stops short of a PR. Each abort type has a specific recovery path — this page walks through all of them with concrete diagnostic steps.

Always start with run.json

Every /relay-test or /relay-execute run produces PRPs/reports/<feature>/run.json. When the run aborts, this file tells you why in one line: 

{
  "run_id": "...",
  "outcome": "FAILED_OSCILLATION",
  "abort_reason": "attempt 3 reverted files from attempt 2",
  "attempts": [...]
}

The outcome field is the primary signal. Each known outcome has a dedicated section below.

FAILED_AFTER_N_RETRIES

The retry budget exhausted with failures still present. Something isn't converging.

Diagnose

Open each attempt's record.json and look at the failures[]:

  • Are the same tests failing across attempts? → likely a requirement gap or weak test. Same failure, same location, repeatedly: the Implementer doesn't have enough info to fix it.
  • Are different tests failing each attempt? → the Implementer is thrashing. Each fix breaks something else. This is closer to FAILED_OSCILLATION but didn't trip the file-set reversion detector.
  • Are the failures getting progressively closer to passing (e.g., expected 3, got 2 → expected 3, got 2.5 → expected 3, got 2.9)? → the Implementer is making progress but needs more attempts. Raise --max-retries.

Recover

Same failure, every attempt
Go back to the PRD. Is the affected AC concrete enough? Is there a contradictory AC elsewhere? Fix the PRD (re-run /relay-prd in update mode if major; edit directly if minor), then re-run.
Progressive convergence stopped by budget
/relay-test <worktree> --max-retries 5. Don't go higher than 5 without investigating — at that point something's likely wrong beyond budget.
Weak test
The test itself is broken (asserting the wrong thing, relying on timing, using wrong mocks). Fix the test manually, then re-run.

FAILED_TIME_BUDGET_EXCEEDED

Diagnose

Open run.json.time_breakdown:

{
  "time_breakdown": {
    "infra_setup_ms": 28000,
    "attempt_1_suite_ms": 480000,
    "attempt_2_suite_ms": 470000,
    "attempt_3_suite_ms": 490000
  }
}

Which phase dominated?

  • infra_setup_ms > 60000 — Docker cold start or image build is slow. Solution: pre-warm the images with make test-bootstrap before invoking /relay-test; Docker caches the layers.
  • attempt_N_suite_ms > 120000 each — the suite itself is slow. Solution: enable layered execution (the unit tier fails fast, saves E2E time) or lower suite scope via --tier unit for the first pass.
  • attempt_N_correction_ms > 60000 — the Implementer is spending a lot of time on each fix. Sometimes unavoidable for complex features; sometimes the PRD is unclear. Check the Implementer's reasoning in the attempt's stdout.

Recover

Heavy E2E project
Permanently raise the default in .relay.yaml: max_test_minutes: 60.
One-off long run
/relay-test <worktree> --max-minutes 60 for this invocation only.
Unit tier sufficient for this PR
/relay-test <worktree> --tier unit for fast-feedback loops; re-run without the flag before merging.

FAILED_OSCILLATION

The Implementer's fix in attempt N+1 reverted files the Implementer changed in attempt N. Detected via file-set intersection + content reversion check.

Diagnose

Open the two conflicting attempts' diffs:

cat PRPs/reports/<feature>/attempts/2/diff.patch
cat PRPs/reports/<feature>/attempts/3/diff.patch

Compare them. The pattern is almost always: attempt 2 made change X to satisfy test A; attempt 3 reverted X to satisfy test B. Tests A and B are asking for mutually-exclusive things.

Recover

This is a PRD-level conflict, not a code bug. The fix happens in the PRD:

  1. Identify which two ACs correspond to tests A and B (from the failures in the respective attempts).
  2. Reconcile them in the PRD. Usually one of three:
    • One AC is wrong — delete it.
    • The ACs are both right but need a conditional (given state X, behavior A; given state Y, behavior B).
    • The feature as specified is impossible — reshape the PRD.
  3. Re-run the pipeline from /relay-plan or /relay-execute.

FAILED_INFRA_UNRECOVERABLE

The abort_reason in run.json tells you which subcause. Each has a specific fix:

missing_settings_json

The Test Runner expected .claude/settings.json to exist but didn't find it. The project hasn't been through the context-builder, or the file was accidentally deleted.

Fix: run *update in the target project. The skill (re)generates settings.json from current stack signals.

docker_not_running

Docker Desktop or the Docker daemon isn't reachable.

Fix:

  1. Start Docker Desktop (or the daemon).
  2. Verify: docker ps should return a list (empty is fine).
  3. Re-run /relay-test.

db_unreachable

The DB service in the test compose didn't come up or isn't reachable from the app container.

Fix:

  1. Tear down any leftover containers: make test-down.
  2. Check port conflicts: the compose typically exposes DB on a non-default port. If another service on your machine uses that port, the test DB won't bind.
  3. Bring up fresh: make test-bootstrap.
  4. Tail the DB container: docker compose -f docker-compose.test.yml logs db. Look for startup errors.

normalizer_failure

The test framework produced output the normalizer couldn't parse. Usually: the framework didn't emit JUnit XML at all.

Fix:

  • pytest: add --junitxml=/app/reports/results.xml to the pytest command (usually in docker-compose.test.yml or setup.cfg).
  • Playwright: set reporter: [['junit', { outputFile: '/reports/playwright-junit.xml' }]] in playwright.config.ts.
  • Vitest: set reporters: [['junit', { outputFile: './reports/vitest-junit.xml' }]] in vitest.config.ts.

Verify by running the suite directly and checking the file exists.

no_runner_detected

The Test Runner couldn't figure out which command to invoke for the suite. Phoenix projects usually have a Makefile with make test-pytest; Node projects use npm run test. If neither is detected, the command gives up.

Fix: add a Makefile target or npm script the Test Runner can find. Re-run *update to refresh .claude/settings.json allow patterns if needed.

no_test_framework (defensive — superseded by Phase 0 self-skip in v0.11.1)

As of v0.11.1 (2026-05-12), projects with test_frameworks: [] in docs/context/methodology.md (or no methodology.md at all) self-skip at /relay-test's Phase 0 gate. The command emits the verbatim line Test framework inactive (test_frameworks: []). Skipping. and exits 0; orchestrator_run_log records {"stage": "test", "outcome": "skipped_no_test_framework"}. No run.json is produced; /relay-test-review inherits the self-skip. This eliminates the dogfood-A vs dogfood-B path divergence observed on 2026-05-11.

This FAILED_INFRA_UNRECOVERABLE sub-reason is retained in the agent's verdict enum for defensive symmetry, but it is no longer reachable when methodology.md declares the framework state correctly. If you genuinely want test coverage, add a test framework, then re-run context-builder *update to declare it in test_frameworks.

Symmetric precedent: /relay-write-test's test_frameworks: [] self-skip (P4.a) — see docs/decisions.md entries 2026-05-06, 2026-05-12, and 2026-07-10.

HALTED on RETRY_NEEDED (known gap)

Currently — until /relay-implement lands — the /relay-test command halts the first time the verdict is RETRY_NEEDED. It writes PRPs/reports/<feature>/attempts/<N>/implementer-feedback.json and stops.

Recover

  1. Open the feedback JSON.
  2. It lists the failing tests with hints. Apply the fix manually.
  3. Commit the fix in the worktree.
  4. Re-run /relay-test <worktree>.

The loop picks up with attempt N+1. If the fix was correct, you get GREEN; if not, another RETRY_NEEDED with updated feedback.

FAILED_PLAN_REVIEW_STUCK

Consecutive plan-review attempts failed on the identical set of rubric item IDs. The orchestrator detected that a re-plan did not change the failing items, indicating the plan-writer cannot resolve the issue mechanically, so it halts before burning the full retry budget.

Diagnose

Open PRPs/reports/<feature>/orchestrator-halt.json:

{
  "outcome": "FAILED_PLAN_REVIEW_STUCK",
  "stuck_rubric_items": ["R-COH-VALIDATE-FRAMEWORK-MISMATCH"],
  "stuck_attempts_count": 2
}

The stuck_rubric_items array names exactly which rubric items could not be resolved. The most common cause after v0.12.0 is a missing phase_type annotation combined with a scaffold phase:

  • R-COH-VALIDATE-FRAMEWORK-MISMATCH — the plan's VALIDATE commands use OS/filesystem tools (e.g. Test-Path, Get-ChildItem, npm install) but the rubric requires a declared test-framework invocation as the first token. This is expected for scaffold or docs phases where no test-framework invocation is meaningful. The plan-reviewer's Phase 0 pre-pass auto-populates phase_type from the plan body signals, but when the plan body is ambiguous the wrong type may be inferred — verify the ## Metadata table in the plan file.

Recover

Wrong or missing phase_type
Open the plan's ## Metadata table and add or correct the phase_type row. For a bootstrap/config/install phase use scaffold; for a docs-only phase use docs. Re-run /relay-plan-review <plan-path> to validate, then re-run /relay-execute (the PRD state machine re-reads on every invocation; no manual reset needed).
Genuine framework-mismatch on a feature phase
If the plan is a feature or refactor phase but its VALIDATE commands don't invoke a declared test framework, update the VALIDATE lines in the plan to call the declared framework (e.g. npx vitest run or pytest). Re-run /relay-plan-review.
Implement manually (scaffold phases)
If the plan is structurally sound but the rubric still cannot be satisfied, follow Path 1 from the halt artifact's manual_recovery_paths — implement the plan tasks manually. This is the recommended path for scaffold phases where test-framework VALIDATE invocations would be performative boilerplate.

FAILED_PLAN_REVIEW_BUDGET_EXCEEDED

The plan-review retry budget (max_plan_review_retries = 2) exhausted before the plan reached APPROVED. Unlike FAILED_PLAN_REVIEW_STUCK, the failing rubric items changed between attempts (the writer was making partial progress) but ran out of attempts before converging.

Diagnose

Open PRPs/plans/<basename>.review.jsonl. Each line is a verdict; the last line shows which items were still failing. Compare across lines to confirm the item set varied.

Recover

Minor rubric items outstanding
Open the plan file and fix the remaining issues directly (e.g. a missing AC reference, a TBD in a mandatory section). Re-run /relay-plan-review <plan-path> to validate without regenerating.
Structural problems
Delete the DRAFT plan file and re-run /relay-plan <prd-path>. The PRD state machine will pick up from the same pending phase. Adjust the PRD or add grounding notes in the source PRD's Open Questions section to guide the plan-writer on the next attempt.

When nothing matches

If run.json.outcome is something not listed above, check the troubleshooting page and the GitHub issues. File a report with run.json + the last attempt's stdout.log (already redacted).
